# Examine2 当前项目重整方案

## 1. 结论

当前工程不适合继续在旧产品面上横向补功能。采用“基础设施选择性复用、旧产品面冻结、按阶段建立 vNext 纵向闭环”的方式，不做无盘点的全量删除：

| 现有内容 | 处理 |
|---|---|
| Maven 多模块、Java 21/Spring Boot/MyBatis-Plus、Vue/Vite 基础、Flyway、通用认证组件 | 通过当前阶段合同验证后复用 |
| `base.entity/base.mapper/base.service` 与生成器 | 保留并强化；普通 CRUD 必须从这里开始 |
| 大量 `manage/service` 内联 JDBC/SQL、超大 Service | 禁止继续扩展；模块被当前阶段触及时按 repository + use-case 边界替换 |
| 旧导航、110 个旧 Vue 页面、运营/独立报表/模块收藏/重复详情等产品面 | 冻结，不作为 vNext 需求或完成证据；按阶段重建真实入口 |
| 118 个旧 cycle、`fast-*` evidence、旧 94% 进度和性能目录 | 只作归档，不进入 Agent 默认上下文，不定义当前进度 |
| 已证明与新合同一致的局部实现 | 逐项通过受影响测试和真实读回后复用，不能按文件存在直接认领完成 |

当前四个 vNext 前端文件说明旧 UI 的可复用比例很低；后端生成层可用，但业务层被架空。重建重点不是重写所有技术基础，而是停止给旧边界继续加债。

新后端边界审计扫描 `examine-module` 的 496 个主源码文件，当前得到 26 个 SQL/JDBC 越层错误和 5 个复杂度警告；其中 `ConfigDraftService` 为 1088 行、`StructuredPropertyValidator` 为 1170 行。这些结果不要求 P1 先做全仓重构，但明确禁止继续沿旧边界扩展，P2 触达时按用例和数据归属替换。

## 2. 当前项目约束

- 唯一需求源：`docs/user_requirement.md`，其中 A.13 是 2026-08-10 的最新收敛，冲突时优先。
- 默认平台超级管理员：`admin / 123123aa`。只存哈希，初始化幂等，不在日志或证据中回显密码。
- Base 公共方法来自 `.base`，项目特有决定只写在 `.cursor` 或项目代码。
- 当前实现 Agent 只能消费 accepted requirement、accepted case 和 accepted artifact；不得自行新增导航、按钮、表、状态或业务语义。
- 性能、容量、百万/千万数据和长并发不进入核心计划。

## 3. 项目阶段

阶段数量按依赖和可用结果确定，不机械限制为四期。当前按五个用户可理解的大期推进，机器交付合同为了控制单期规模拆成七个 delivery phase；每个 delivery phase 再包含若干最多四小时的周期。

### P1 工程骨架、认证和系统入口

退出结果：干净数据库可启动；默认超管可登录；新用户可注册并原子创建第一个系统；用户能看到授权系统并进入上下文正确的系统壳。

四小时周期：

1. 工程/生成边界 + 数据库基础 + 默认 `admin` + 登录/刷新/当前账号 + `/login` 真实演示。
2. 注册账号 + 首个系统/默认租户/成员/超级管理员原子初始化 + `/register` 演示。
3. 我的系统 + SystemSwitchContext + 系统壳 + 重新登录读回演示。

### 第二大期：核心平台与第一个可用业务系统（delivery P2 + P3）

退出结果：管理员可维护系统、组织、成员和角色；可视化创建并发布一个业务模块；普通成员能在该模块新增、检索并从右侧标签详情读回数据；系统首页显示可视化发布的仪表盘。第二大期结束即具备基础可用性。机器合同中的 delivery P2 负责平台/组织/配置/仪表盘，delivery P3 紧接着负责运行态 CRUD/详情/权限，它们不是两个彼此割裂的产品大期。

建议周期按真实合同滚动展开：

1. 平台系统管理与系统基础设置。
2. 部门、成员、角色和基础权限。
3. 模块组、模块、字段和页面发布的最小配置链。
4. 运行态新增/编辑/模糊搜索/高级筛选/表头/右侧标签详情。
5. 字段与数据范围权限正反例。
6. 可视化拖拽仪表盘、数据源绑定、预览和发布。

### 第三大期：Flow 与对外应用（delivery P4）

退出结果：管理员可视化发布审批流程，成员能完成提交/审批/退回等核心动作；系统对外应用以明确 scope 和凭证安全边界调用已授权能力。平台 Flow/应用与系统 Flow/对外应用保持不同上下文。

### 第四大期：工作、任务、日报及其他丰富能力（delivery P5 + P6）

退出结果：成员可管理项目任务、普通任务和日报；待办、消息、评论和成员选择使用统一身份/权限来源；日报自动草稿只读取本人有权数据并在提交前人工确认。随后补齐文件、打印、模块导入导出及当前需求中仍保留的高级可视化配置。AI 只有在核心业务稳定后进入，并遵守权限、人工确认、审计和失败降级。

独立报表运行导航和报表工作室不在当前核心范围；统计和趋势由仪表盘承接，导出属于具体模块。未来确有独立报表需求时重新立项。

### 第五大期：统一 hardening、交付和用户验收（delivery P7）

退出结果：在功能完成基础上统一处理响应式、关键断点、跨模块视觉一致性、可访问性、部署、升级、备份、恢复、回滚和全项目真实角色旅程；最终由用户确认。

## 4. P1 并行计划

第一个周期使用模块 DAG，而不是角色串行接力：

```text
并行 A: examine-generator / Base 生成合同
并行 B: clean migration / startup dependency / default admin bootstrap
并行 C: vNext 登录页面与会话状态（消费已冻结 UI/API artifact）

A + B 完成
  -> D: login/refresh/current-account 后端用例

C + D 完成
  -> E: 周期唯一一次组合测试、持久化读回和 /login 演示
```

最多同时使用多少 Agent 由执行环境决定；只要 A/B/C 的写集、migration、测试数据库和端口已隔离就并行。D 有明确前置，不能为了“多 Agent”假并行。P2 以后不同 Maven 模块同样默认并行，公共 schema/API artifact 先单写冻结。

## 5. 原子任务合同

每张任务卡必须能让一个不了解聊天历史的 Agent 直接完成：

```yaml
result: 一个可验证结果，不写“完善模块”
requirement_ids: []
acceptance_case_ids: []
input_artifacts: []
module_scope: 一个模块/聚合
write_scope: []
resource_scope: []
depends_on: []
allowed_changes: []
forbidden_changes: []
base_bindings: []
estimate_minutes: 10..120
owner: 专业实现角色
verifier: 与 owner 不同
affected_checks: []
new_semantics_allowed: false
```

需求仍有歧义时不创建 coding task。Agent 做错通常不是 Agent 失去基础能力，而是任务把产品判断、设计判断、数据判断和实现混在一起，又允许它读取历史噪声。新合同通过单一事实源、精确输入和 `new_semantics_allowed=false` 消除这种猜测空间。

## 6. 页面合同示例：客户列表

```text
同一页头行: 客户                                      [导入] [导出] [新建客户]
工具栏:      [模糊搜索________________] [高级筛选]
勾选后:      已选择 N 项 [批量编辑] [转移] [删除] [导出]
表格:        勾选 | 客户名称 | 联系人 | 手机 | 状态 | 负责人 | 更新时间 | 必要行操作
行点击:      右侧详情工作区
详情标签:    概览 | 关联数据 | 评论/协作（有需求时） | 文件（有需求时） | 历史
```

不显示搜索/视图/草稿等同义入口，不显示常驻批量动作，不保留重复“查看详情”，不显示模块收藏。关注若进入需求，只能是具体客户记录的详情能力。客户关系页右侧无来源按钮全部删除。

## 7. 后端整改规则

后端不做一次性全仓重写，按阶段触达模块替换：

1. 先检查表结构、聚合和事务原因。
2. 运行生成器得到 Base Entity/Mapper/Service。
3. 普通 CRUD 使用 MyBatis-Plus Base 能力。
4. 特殊查询进入具名 mapper XML 或 repository adapter。
5. `manage/application` 每个服务只负责一个用例，不出现 SQL、JdbcTemplate、ResultSet 和动态表名。
6. 对现有 `ConfigDraftService` 一类超大服务，不继续追加；P2 触及时按模块定义、字段、页面、动作、规则、发布等用例拆分，并先复审数据归属。
7. 每个后端任务运行 `implement-backend-module` 审计和受影响单测；旧模块未触达时不为追求全仓一次通过而阻塞 P1。

## 8. 测试计划

- task：后端受影响单测/编译或前端受影响组件测试；一次。
- cycle：四小时结束一次组合测试和一次真实入口；一次。
- module page：页面功能完整后验证搜索、筛选、表头、表单、右侧标签详情、权限、错误恢复和持久读回；一次。
- phase：验证本期退出结果；一次。
- project：功能全部完成后做全项目功能、权限、数据、部署和角色旅程；一次。
- hardening：完整响应式/视觉/可访问性统一执行，不复制到每个功能任务。
- performance：当前不存在；功能完成且用户单独确认目标后另建计划。

## 9. 当前停止与启动条件

立即停止：旧导航和旧页面继续加功能；在大 Service 中追加 SQL；为每个小任务打包/重启/全量回归；创建性能或大数据任务；从旧 evidence 推导完成度。

允许启动 P1 的条件：

- A.13 已进入唯一需求源。
- P1 需求、用例、UI/API/data 合同包含默认 admin、登录、注册、系统列表和系统上下文。
- 每张 P1 任务卡不超过 120 分钟，写集和依赖明确。
- UI、后端和测试 Skill 均已同步到项目实例并通过自测。
- 周期结束的真实入口和成功业务结果已冻结。

## 10. 首批反哺 Base

本项目已经验证并应进入 Base 的规则：

1. Agent 调用 Skill；Skill 不调度 Agent。
2. 需求—用例—任务三联单和双向追踪。
3. 阶段从可登录、可使用到丰富；四小时周期只交付一个 demo 结果。
4. 无依赖、不同模块和不重叠写集默认并行。
5. 管理列表与右侧标签详情采用可验证 UI 合同。
6. 后端 Base 优先、SQL/Repository 边界和复杂 Service 止损审计。
7. task/cycle/module/phase/project 分层测试，性能专项后置。

这些规则进入 Base 后必须带负例验证，防止下一个项目再次出现同类混乱。
