# 公共技能执行手册

## 统一执行纪律

1. 调用者声明 `skill`、触发原因、输入路径、输出路径、检查范围、通过条件和失败责任人。
2. 执行者先验证输入和工具可用性；缺少必需输入时输出 `blocked`，不得猜测或伪造检查结果。
3. 检查必须作用于真实产物和声明环境。命令、版本、结果、证据路径和未覆盖边界必须落盘，但不得记录密码、token 或 Secret。
4. `pass` 只表示本 skill 的条件满足，不自动推进 Gate。`fail` 必须给出事实、影响、owner、复核条件；检查者不得在同一次检查中静默修改被检查产物。
5. 输出统一包含 `verdict`、`checked_inputs`、`checks`、`evidence`、`issues`、`coverage_boundary` 和 `next_owner`。

## compile-project-delivery

- 必需输入：唯一权威需求文件、文件 SHA-256、Base 当前合同和项目技术边界。
- 执行：完整读取 `skills/compile-project-delivery/SKILL.md`；生成 typed delivery JSON；运行其验证器。
- 通过：阶段从骨架到丰富；需求/用例/任务双向闭合；任务不超过 120 分钟；周期不超过 240 分钟；无冲突 ready 任务并行；核心计划无性能专项。
- 失败输出：未决决定、单向追踪、任务越界、周期超时、错误串行或性能越级，owner 为 product/planner/PM。

## build-management-ui

- 必需输入：committed 原子需求、验收用例、角色入口和当前管理页面合同。
- 执行：完整读取 `skills/build-management-ui/SKILL.md`；生成页面合同；运行其验证器后才允许前端编码。
- 通过：页面头紧凑；搜索和高级筛选分工明确；批量动作选择后出现；表头和密度清楚；整行打开右侧标签详情；无来源入口和重复动作被删除；仪表盘以可视化操作为主。
- 失败输出：臃肿、重复、安置不明、状态缺失或 JSON-first 设计，owner 为 uiux/product/frontend。

## verify-by-delivery-level

- 必需输入：当前交付层级、验收用例、受影响模块和已执行命令记录。
- 执行：完整读取 `skills/verify-by-delivery-level/SKILL.md`；生成测试计划；验证后执行每条命令一次。
- 通过：task 只测受影响项；cycle 只做一次结合测试和真实入口；module 按页面旅程；phase/project 按对应结果；测试通过、业务达成和需求接受分别记录。
- 失败输出：重复全量测试、错误状态冒充成功、层级越界或未授权性能专项，owner 为 test/PM/对应实现者。

## implement-backend-module

- 必需输入：committed 原子需求、验收用例、数据/API 合同、模块和写集、Base 绑定、允许/禁止变化。
- 执行：完整读取 `skills/implement-backend-module/SKILL.md` 和分层合同；先复用/生成 Base，再实现单一用例服务；运行静态边界审计和受影响单测。
- 通过：普通 CRUD 使用 Base；manage/application/controller 无 SQL/JDBC/ResultSet；特殊查询位于 repository/mapper；事务有单一业务原因；复杂度未掩盖聚合或表结构问题。
- 失败输出：Base 被绕过、SQL 泄漏、大 Service、重复映射或数据模型疑点，owner 为 backend/dba/architect。

## source-trace

- 必需输入：全部声明来源、来源优先级和当前需求包。
- 执行：为每个来源建立稳定 ID、文件/章节锚点和摘要；把每条需求映射到来源；记录重复、冲突、过期、缺失和无法读取项。
- 通过：所有正式需求至少一个可复核来源，冲突均有决定或 issue，未把历史实现误当当前需求。
- 失败输出：未映射条目、冲突双方、影响范围和 `analyst/product` owner。

## requirement-consolidation

- 必需输入：来源映射、角色、业务目标和已生效决定。
- 执行：逐条补齐角色、触发、前置、正常行为、异常、状态、数据、权限、审计、非功能和可验收结果；分配稳定 REQ ID；检查同义重复和范围遗漏。
- 通过：下游不需猜测关键业务规则；每条需求可映射旅程和验收；用户专属决定没有被默认代签。
- 失败输出：模糊条目、缺失维度、冲突、推荐澄清路径和 `product/pm` owner。

## journey-review

- 必需输入：需求 ID、角色、真实入口、设计/API/数据契约和验收环境。
- 执行：从入口走到可见业务结果，覆盖主路径、拒绝路径、空/错误/禁用/重试状态、持久化读回和副作用；记录每一步跨层证据。
- 通过：旅程端到端闭合，权限和数据结果正确，真实 API/数据库替代 mock，重新加载后结果仍成立。
- 失败输出：断点步骤、缺失状态、错误结果、受影响 REQ/JRN 和责任角色。

## scope-check

- 必需输入：当前节点、冻结需求/设计、变更内容和 blocked scope。
- 执行：把变更分为 in-scope、required-enabler、deferred 或 out-of-scope；检查来源、依赖、写入所有权、验收和后续影响。
- 通过：所有工作服务当前节点或明确获批变更；没有假入口、顺手重构或静默删减最终范围。
- 失败输出：越界文件/行为、原因、回退或变更建议和 `pm/leader` owner。

## decision-review

- 必需输入：待决问题、事实、约束、候选方案、各角色证据和权力边界。
- 执行：比较收益、成本、风险、可逆性、兼容性和验收影响；区分工程决定、产品决定和用户专属决定。
- 通过：决定有明确 authority、理由、拒绝方案、受影响合同和同步行动。
- 失败输出：缺失事实、无法收敛分歧和升级到 `pm/leader/user` 的条件。

## design-review

- 必需输入：角色旅程、信息架构、页面/交互规格、状态矩阵和原型。
- 执行：检查入口、导航、任务顺序、字段/动作、反馈、权限、空/错/加载/禁用状态、桌面/移动替代布局和视觉一致性；用真实内容验证长文本和密度。
- 通过：核心旅程无断链或重复入口，页面不是原型占位，状态和响应式规则可直接实现和测试。
- 失败输出：页面/步骤、用户影响、设计修正、验收视口和 `uiux/product` owner。

## architecture-review

- 必需输入：需求/NFR、模块图、依赖、数据 ownership、部署和演进约束。
- 执行：检查模块职责、公开契约、依赖方向、事务边界、数据 owner、副作用、故障隔离、安全、性能、运维和未来拆分；对关键选择形成决定记录。
- 通过：不存在循环 ownership 或跨模块私有实现依赖；关键质量属性有可验证机制和失败恢复。
- 失败输出：耦合点、失败模式、候选方案、迁移影响和 `architect` owner。

## contract-check

- 必需输入：UI 交互、API、数据模型、权限、状态机、错误码和版本合同。
- 执行：以动作/字段/状态为行对比前端、后端、数据库和测试；检查类型、可空、枚举、ID、分页、幂等、错误、权限和兼容策略。
- 通过：同一概念跨层名称和语义一致；所有差异有版本或适配决定；测试覆盖正反合同。
- 失败输出：不一致矩阵、破坏性影响、owner 和重新冻结条件。

## data-contract-review

- 必需输入：实体生命周期、表/字段/关系、查询模式、隔离和保留策略。
- 执行：检查主键、唯一性、外键/引用、状态约束、租户/系统隔离、逻辑删除、版本、审计、索引、并发和读回；用目标数据量审查查询路径。
- 通过：非法状态受约束，关键查询命中设计索引，跨 scope 数据不可混读写，迁移和生成边界明确。
- 失败输出：DDL/查询风险、复现 SQL、数据影响和 `dba/backend` owner。

## security-review

- 必需输入：信任边界、身份/权限模型、敏感数据、外部入口和威胁场景。
- 执行：检查认证、会话、CSRF、授权、数据范围、输入、上传、Secret、加密/哈希、限流、防重放、日志脱敏和审计；执行允许与拒绝用例。
- 通过：服务端独立授权，敏感值不明文持久化/回显/入日志，跨用户/系统/租户攻击被拒绝并可追踪。
- 失败输出：攻击步骤、严重级别、受影响资产、临时控制和 `backend/ops` owner。

## failure-mode-review

- 必需输入：关键流程、状态机、事务、副作用、外部依赖和恢复目标。
- 执行：逐点注入超时、重复、乱序、部分失败、并发、进程/Redis/数据库重启；检查幂等、补偿、重试、死信、状态解释和人工恢复。
- 通过：失败不会产生不可解释的半成品；可重试与不可重试错误明确；恢复后事实可读回。
- 失败输出：故障点、残留状态、恢复缺口、数据修复方案和 owner。

## performance-review

- 必需输入：目标数据量、并发、响应目标、关键查询/页面/作业和环境规格。
- 执行：建立基线场景；采集延迟、吞吐、SQL/索引、内存、包体和资源使用；检查分页、批处理、缓存失效、背压和容量上限。
- 通过：指标达到已冻结目标或有明确容量边界；无全表扫描、无界加载和随数据量线性恶化的主路径。
- 失败输出：场景、数据规模、指标、瓶颈证据和 `architect/dba/backend/frontend/ops` owner。

## accessibility-check

- 必需输入：可运行 UI、目标浏览器/视口和交互状态。
- 执行：检查语义标签、键盘顺序、焦点、名称/角色/值、错误提示、对比、缩放、动态状态和触控目标；使用自动检查加人工键盘流程。
- 通过：核心旅程无需鼠标可完成，控件可识别，错误和状态可感知，无焦点丢失或内容遮挡。
- 失败输出：元素定位、操作步骤、标准影响和 `uiux/frontend` owner。

## dependency-check

- 必需输入：任务、输入输出、owner、写入范围、前置 Gate、合同 hash 和资源约束。
- 执行：构建 DAG 并计算关键路径；发现缺失前置、循环依赖、共享写入和环境竞争；比较并行节省与合同冻结、沟通、集成成本；标出 execution mode、排程理由、集成 owner 和合并顺序；并行组逐项核对 migration、生成目录、lockfile、DB schema、测试数据、端口和运行环境隔离。
- 通过：每项任务可由声明输入启动；同一主产出单 owner；串行任务有依赖/集成理由；并行组内部无依赖边、写集不重叠、共享合同 hash 一致、运行资源隔离且预计净缩短关键路径。
- 失败输出：依赖边、冲突资源、重排建议和 `planner/pm` owner。

## meeting-check

- 必需输入：issue、提交人证据、必要角色的独立意见和会议记录。
- 执行：检查参与人是否覆盖 product/uiux/技术影响；核对分歧、方案、authority、决定、行动、owner、复核和升级。
- 通过：没有角色被冒充；决定可追溯到证据；所有行动有关闭条件；越权问题已升级。
- 失败输出：缺席意见、未决分歧、无 owner 行动和 `pm` owner。

## gate-review

- 必需输入：节点合同、主产出、任务状态/估算/overrun history、issue、会议、独立证据和签字边界。
- 执行：逐项核对必需产出和完成定义；验证 P0/P1、证据时效/环境/独立性、状态同步和下一节点前置；检查超过估算的原任务仍保持完成责任、重估记录连续且没有丢范围，并抽查关键声明。
- 通过：目标业务结果有足够证据，P0/P1 关闭，状态与事实一致，acceptor 有权签署当前 task/slice/phase/journey/release/final 层级且没有越级声明。
- 失败输出：缺失门禁项、退回 owner、复核命令和阻断范围。

## record-sync

- 必需输入：最新决定、issue、任务、Gate、状态文件和相关合同。
- 执行：比较 ID、状态、时间、owner、输出、证据、开放问题和下一节点；把同一决定同步到全部受影响记录，并检查 JSON/链接有效。
- 通过：不存在同一事项多种状态、悬空路径、已关闭问题仍阻断或未签 Gate 被推进。
- 失败输出：不一致位置、权威来源、修正 owner 和同步顺序。

## research-check

- 必需输入：明确问题、适用产品/版本/日期、允许来源和决定影响。
- 执行：优先官方文档、标准、源码或论文；核对发布日期和版本；至少交叉检查关键不稳定事实；区分来源事实与工程推断。
- 通过：结论有可访问的一手来源、适用边界和检索日期，足以支撑当前决定。
- 失败输出：未知事实、来源冲突、保守默认值和 `leader/user` 升级条件。

## build-check

- 必需输入：锁定依赖、工具链版本、源码、构建命令和目标制品。
- 执行：在声明工具链执行 clean 或等价隔离构建、静态检查、类型检查和单测；核对锁文件、制品清单、警告和退出码；禁止依赖开发机残留输出。
- 通过：全部命令退出 0，制品来自当前源码，版本满足约束，警告已关闭或进入明确 issue。
- 失败输出：命令、首个根因、日志路径、受影响模块和实现 owner。

## api-readback-check

- 必需输入：API/权限/数据合同、可运行服务、真实数据库和隔离账号。
- 执行：执行创建/查询/更新/删除或状态动作；核对 HTTP、envelope、幂等、并发、允许/拒绝、数据库事实、审计和副作用；重新请求确认持久化。
- 通过：API 结果与数据库和权限合同一致，重复/伪造/跨 scope 请求得到预期结果，无残留半事务。
- 失败输出：脱敏请求、响应、数据库读回、预期差异和 `backend/dba` owner。

## browser-check

- 必需输入：真实前后端、业务旅程、测试账号/数据和目标视口。
- 执行：用真实浏览器完成入口到结果；验证路由、刷新/重登、加载/空/错误/禁用、键盘、布局、控制台、失败请求和持久化；至少覆盖桌面和移动目标视口。
- 通过：用户能完成旅程，无遮挡/横向溢出/假数据/未处理异常，非预期 console error 和 HTTP 4xx/5xx 为零。
- 失败输出：视口、步骤、截图/trace、网络或控制台证据和 `frontend/backend/uiux` owner。

## acceptance-check

- 必需输入：任务/批次合同、实现输出、全部要求证据、开放 issue 和独立验收人。
- 执行：验收人复现关键命令并抽查产物；按需求/旅程/权限/数据/失败/重启矩阵检查；明确证据能证明和不能证明什么。
- 通过：完成定义全部满足，关键证据可重复，验收人不是实现者，未超出当前 Gate 声明。
- 失败输出：未满足条款、证据缺口、退回 owner 和再验收条件。

## regression-check

- 必需输入：变更 diff、影响分析、关联需求/旅程、历史缺陷和基线测试。
- 执行：选择直接、相邻和共享契约用例；执行单元、集成和关键浏览器回归；比较 API、schema、权限和性能基线。
- 通过：目标修复成立且既有已接受能力无回退；新增风险已有自动测试或明确人工 Gate。
- 失败输出：回归用例、首次坏版本/变更、影响范围和实现 owner。

## migration-check

- 必需输入：前后版本 schema、migration、数据量、兼容窗口、备份和回滚策略。
- 执行：在空库和前一版本副本分别执行校验/迁移；读回表、索引、约束和关键数据；测试重复启动、失败中断、恢复和不可逆声明。
- 通过：空装与升级均成功，migration 有唯一版本且可重复验证，数据无丢失，回滚或前滚恢复路径经过演练。
- 失败输出：失败版本、SQL/数据差异、恢复步骤、不可逆风险和 `dba/ops` owner。

## release-check

- 必需输入：版本化制品、校验和、配置模板、migration、运行脚本、运维/用户文档和发布计划。
- 执行：在干净环境安装；验证配置无 Secret、启动、健康、主旅程、重启、日志/指标、备份恢复、升级/回滚和卸载清理；核对制品哈希。
- 通过：声明环境可仅凭发布包运行和恢复，关键旅程通过，发布/回退条件清楚，无开发机隐含依赖。
- 失败输出：阶段、命令、日志、业务影响、停止/回滚决定和 `ops/leader` owner。
