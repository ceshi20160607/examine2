# 当前产品真实可用性审查（2026-09-05）

结论：不符合需求文件定义的完整交付预期。当前是已有大量基础能力、能完成部分简单业务的开发版本；不能认定为普通管理员和员工能够独立使用的完整业务平台。主要缺口同时存在于业务实现、配置与运行的一致性、导航衔接和移动布局，并非只需要换皮。

本报告以 `docs/user_requirement.md` 为唯一需求来源，以当前工作区（含已有未提交修改）的代码、重新构建后的本地页面和本次执行结果为事实来源。不采信 README、周期状态或旧截图中的完成声明。

## 审查范围与边界

- 全局盘点前端路由、58 个产品视图、后端 20 个一级目录及 295 个 manage Java 文件的位置和能力分布；重点追踪账号、系统进入、模块配置、运行表单、流程绑定、权限、平台后台和工作管理实现。盘点不等于逐行审查每个文件。
- 阅读部署配置、实际容器挂载和工作区边界；workspace-validate 本次通过。
- 从当前源码执行前端构建、前端测试、后端打包；启动已有本地 MySQL、Redis、后端和 Nginx 容器，使用重新生成的构建产物访问 `http://127.0.0.1:15174`。数据库实际为 V39，启动时没有执行新的迁移。
- 使用现有本地平台管理员、系统管理员和普通成员三类账号；走查首页、系统目录、客户列表、新建与详情、模块配置、流程绑定、平台组织架构、平台审计、平台任务；检查桌面及 390 像素手机布局。
- 真实新增一条“现场走查临时客户20260905”，验证保存、列表和详情读回。保留这条明确标记的本地记录，未修改既有业务记录或角色授权。
- 没有逐一实际运行所有 SSO 身份源、外部 AI/应用调用、审批分支、导入导出、备份恢复及生产部署；这些不能据此认定完整通过。

## 已确认问题（按影响排序）

### 1. 严重：配置支持的字段类型与业务写入实现不一致

证据：`frontend/src/product/views/ModuleConfigurationView.vue:37` 列出邮箱、多选、日期范围、子表、签名、富文本等类型；`backend/.../moduleconfig/manage/ModuleConfigurationService.java:38` 接受这些类型；`ModulePublicationService.java:443` 只按该配置类型集合检查。

但是 `backend/.../runtimedata/manage/RuntimeDataService.java:2136` 的普通业务写入 normalize 只处理文本、手机号、单选/状态、数字/金额、日期/时间、布尔、人员/部门/关联、级联等少量类型，其他类型在第 2226 行抛出“当前阶段不支持该字段类型”。例如非空 EMAIL、MULTI_SELECT、SUBTABLE 值走到该分支会被拒绝。这是当前代码路径确认，未宣称逐类型浏览器提交过。

前端运行表单第 1324—1336 行同样只有少量专用控件，其余退化为普通输入框。采购明细、多选分类、复杂业务表单不能凭设计器里有相应名称就算可交付。应以“能配置、能发布、能录入、能修改、能读回”作为每类字段的通过标准。

### 2. 严重：平台组织架构等核心后台入口仍是通用键值配置页

实测路径：平台管理 → 组织架构 → 新建配置。页面只出现“配置键”“配置值”、JSON 文本框和敏感配置开关，没有部门树、成员邀请、岗位或组织关系操作。

平台“审计日志”同样显示“当前分类还没有配置”，其页面实际维护审计策略与参数，不展示审计事件。

根因：`PlatformConfigurationsView.vue:50` 将这些分类统一交给 `FixedConfigurationsView`；后者只有系统级运维/字典专用分支（第 147 行附近），其余走键值编辑。`ContextSettingManagementService.java:108` 保存的是 CoreSetting，并非创建平台部门、成员或角色。

因此平台组织、角色、字典、审计等不能按导航标题计为已完成。截图：`platform-organization-keyvalue.png`；审计页面文字：`platform-audit-state.txt`。

### 3. 严重：平台任务页丢失整个应用导航

实测路径：平台首页 → 任务。进入 `/platform/tasks` 后只剩“普通任务/项目任务/每日日志/日历统计/工作配置”和任务内容；平台顶栏、系统入口、账号上下文与返回入口消失。

根因：`routes.ts` 直接挂载 WorkHubView；`WorkHubView.vue:14` 没有 PlatformShell 包装，子视图也不提供平台壳。用户需要依赖浏览器后退恢复导航。

截图：`platform-tasks-no-shell.png`。

### 4. 严重：手机业务列表被桌面侧栏挤到极窄区域

390 像素实测：左边仍占据固定宽度的模块栏，右侧客户卡片、名称和手机号挤成逐字竖排，搜索栏被截断。不是推测性的“可能不兼容手机”。

根因：`product.css:890` 虽然在手机断点改为单列，但 `design-system.css:315` 的 `.runtime-page .runtime-layout` 以更高优先级重新固定为 `190px minmax(0, 1fr)`，没有对应覆盖。

截图：`mobile-customer-390.png`。验收不能只检查根页面有没有横向滚动，还应检查内容区实际宽度及文字可读性。

### 5. 严重：模块配置跳到 Flow 后丢失来源模块

实测路径：模板配置 → 售后工单 → 模块 Flow → 配置模块 Flow → 触发绑定。最终“已发布模块”默认显示“客户”，不是售后工单。

根因：`ModuleConfigurationView.vue:873` 仅传 `section=flow`；`FlowBindingsView.vue:73` 默认选择模块列表第一项。管理员必须重新选择模块，存在给错误模块绑定流程的风险；返回模板页也不能依赖地址恢复原模块/步骤。

证据：`flow-binding-state.txt`。应把来源模块、触发点、返回位置作为明确路由状态，绑定完成后回到同一模块并展示配置结果。

### 6. 严重：Flow 绑定仍要求理解代码表达式，预演固定为金额场景

实测看到命中条件默认是 `amount > 10`，下方固定“测试金额 8000”。当前客户模块实际字段只有客户名称和联系电话。

`FlowBindingsView.vue:24` 写死默认表达式，第 27 行写死测试金额，第 124 行附近只提交 `variables: { amount: ... }`。模块字段与测试输入没有接通。Flow 设计器也仍让用户手填人员字段编码、状态英文值、变量名和字段回写编码。

这不满足“不懂代码的管理员能配置审批”。截图：`flow-binding-amount.png`。

### 7. 高：页面设计预览和真正运行表单不是同一套渲染

配置器 `ModuleConfigurationView.vue:460` 保存组件标题、columns、density 等属性，并在第 1007 行用于预览。运行页 `RuntimeWorkspaceView.vue:142` 只消费 fieldCodes；实际表单在第 1320 行使用固定布局。

管理员设置桌面列数或布局密度，不能据预览推定运行页相同。字段默认值也在配置器保存，但新建表单第 868 行统一初始化为 undefined/false，没有读取该配置。应使用同一发布 Schema 渲染预览与运行表单。

### 8. 高：注册缺少正确落点，找回密码没有完整入口

需求第 340—341 行要求真实找回/重置页面，以及注册后进入系统后台配置引导。当前 AuthView 登录页面无找回入口，routes.ts 无找回/重置路由；注册成功第 76 行直接进入 `/systems/{id}` 运行首页。

本次检查了实际登录页面和注册跳转代码，没有新注册账号。问题是第一条管理员搭建链的引导不符合要求，而不是认定注册 API 无法创建系统。

### 9. 高：无权限的快捷入口仍显示，点击结果与用户意图不一致

普通成员平台首页导航不显示待办，但首页仍显示“0 待处理事项”。实测点击后进入 `/platform` 的系统目录，而不是待办，也没有解释原因。

`WorkspaceHomeView.vue:165` 的快捷卡片没有按 canViewTodos/canViewMessages 隐藏；`routes.ts` 对无权限待办重定向到 `/platform`。系统内同样的卡片还可能进入没有相应子视图的状态。

普通成员与管理员实际可见客户数量不同、电话字段也有隐藏，这说明部分权限实现有效；本问题是入口与权限体验不一致，不能把它夸大为后端越权。

### 10. 高：工作使用态仍混有配置态

`WorkHubView.vue:23` 无条件显示“工作配置”，进入后展示字段草稿、发布、回滚等管理能力，或无权限警告。需求要求工作字段配置归入相应后台“其他业务参数”。

普通任务、项目、日志、日历可以同处使用区；配置入口应按角色放到后台，并明确配置作用范围。

### 11. 中：基础 CRUD 通了，但业务动作仍围绕通用记录而非业务对象组织

实测新建客户同时要求“标题”和“客户名称”，列表两列显示同一名称。客户详情关联页只有空提示，没有就地创建跟进的入口，需要返回模块导航，再自行选择跟进模块与关联客户。

这部分能完成简单录入，但在“客户 → 跟进 → 负责人 → 下一次联系 → 待办”的连续工作中依然存在额外选择和中断。固定通用标题来自 `RuntimeWorkspaceView.vue:1320`，并不随模块主展示字段调整。

### 12. 中：展示层用命名正则隐藏业务数据

`presentation.ts:138` 的 isVerificationArtifactName 把 C+数字开头或“验收系统”结尾等名称当作验收数据；PlatformHomeView 与 WorkspaceHomeView 用它过滤系统、待办和消息。

例如真实业务名“C2026客户系统”也会匹配。应把测试环境/样例数据隔离作为显式数据属性或环境策略，不能通过业务名称猜测并隐藏结果。这是静态确认，没有为复现额外创建系统。

## 已实际确认的正向结果

- 当前前后端可以构建，现有本地服务可以启动；数据库与 Redis 启动自检通过。
- 三类账号可以真实登录和进入相应上下文。
- 管理员能新增客户，并在列表和详情读取保存结果。
- 同一系统普通成员只看到一条获权客户且看不到电话列；管理员能看到更多记录和电话。部分数据/字段权限与管理入口隔离确实起作用。
- 模块组、模块目录、草稿/发布入口、字段配置器和流程画布等已有实现基础，不能说整个仓库都是空壳。

## 为什么现有“通过”不足以证明完成

- 本次前端构建通过，34 个测试文件、100 项测试通过；主 JS 包约 3.07 MB（gzip 约 938 KB），构建提示包过大。
- lowcode-workflow.test.ts、all-routes-experience.test.ts 等用 readFileSync 与字符串包含断言验证页面源码。它们能防止文案/结构回退，不能证明业务写入或配置后的运行效果。
- c75-route-visual-acceptance.cjs 的页面检查主要验证内容长度、根横向溢出、部分技术字样；手机普通成员路径还写成 workspace=todo，而实现识别的是 todos，可能实际检查了首页。它也没有覆盖“手机客户列表可读”以及“平台任务页保留导航”等已复现问题。
- 后端本次完整测试：62 项，12 通过、3 断言失败、47 错误、0 跳过。三项断言分别是权限决策条目数和两个表数量预期不一致；错误涉及本机 Undertow/loopback/Redis 启动。详见本目录 test-summary.md，不能把环境错误一概算作产品业务缺陷。

## 完成度判断与修复顺序

不建议给一个缺乏权重依据的百分比。按交付层次判断：工程边界和构建具备基础；简单业务录入部分可用；无代码搭建、真实业务闭环、完整平台管理和移动端交付未达到要求。

优先顺序：

1. 对齐配置、发布、前后端读写所支持的字段类型；阻止发布无法运行的配置，补齐需求要求的字段，而不是永久隐藏它们。
2. 将平台组织、权限、字典、审计等入口落实为对应业务页面；恢复平台任务壳，解决手机固定侧栏覆盖。
3. 接通注册配置引导、模块到 Flow/应用的上下文、业务字段条件选择、配置预览到运行渲染。
4. 以客户跟进、采购申请/明细审批、普通任务与工作日志三条代表流程，由管理员配置，再切换普通成员完成业务、审批/处理和结果回看。
5. 最后统一密度、间距、文案和移动交互。页面美化不能替代上述闭环。

真正的验收应当从干净业务配置开始：不会写代码的人能按界面完成搭建；普通员工不借助 SQL、接口工具、手填内部 ID 或开发者解释，能连续完成工作并找到下一步。每条链同时检查权限、错误反馈、刷新/返回和手机使用结果。
