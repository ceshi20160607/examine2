# 混合时区历史的恢复约束

当前 API 将 LocalDateTime 按 Asia/Shanghai 输出，数据库连接和默认时间为 +08:00。过去的 UTC 容器 JVM 默认时区未同步，Java 手工填写的部分完成、更新时间和作业期限与数据库默认的开始、创建、历史时间可能混用。早期启动扩展只统一此后的运行时钟；不改变操作、流程快照、共享审计及任何历史值。

本次变更前已只读核对全库：PENDING/RUNNING/RETRYING 的 Flow 作业为 0，具有截止时间的 PENDING 审批任务为 0，因此当前环境没有需在切换时恢复的活动期限。迁移到其他环境前必须再次核对，不能沿用本地计数。

历史修复须按以下步骤执行，不允许给全部 DATETIME 统一增加八小时：

1. 备份相关行及版本，保留 SQL 导出与原运行日志。确认部署窗口、JVM 时区、数据库会话时区和每个字段的写入方法。数据库 DEFAULT/ON UPDATE、Java LocalDateTime、Java Date/Timestamp 和用户录入的截止时间不能混为一类。
2. 用实际日志和原动作/outbox/流程关联确定受影响记录及列。`flow_instance.finished_at`、`flow_execution.left_at`、`flow_task.completed_at/due_at`、`flow_job.next_run_at` 等只是核对入口，不代表这些列的全部历史都需偏移。新命名继续使用 *_time；本文仅引用既有列。
3. 对已证明由 UTC Java 墙上时间写入、当前需恢复为 +08:00 的具体行，生成带主键、原值和版本条件的事务修复 SQL，并保存旧值。校验开始/完成、进入/离开、任务截止/作业计划与真实日志吻合，再提交。活动任务和作业需暂停相关消费、恢复计划时点并验证只执行一次。
4. 对无法证明写入时区的历史值保留原值和异常记录，待补充日志或可信业务证据。回滚按备份及版本条件恢复具体字段，不删记录、不重建表、不重新启动历史审批。

完整历史时间恢复及全部超时策略尚未验收。当前短前置只验证新流程时间一致、当前环境无活动期限迁移和既有共享期限判断；不能据此宣称 B03/B10 完成。
