# 第 15 次重构：按业务旅程分阶段落地

## 输入与边界

- `docs/user_requirement.md` 是产品范围和验收的唯一来源。
- `docs/表意义.md` 是用户给出的表模型参考。它列出 94 张逻辑表，不要求首装时全部创建。
- `docs/old_table1.sql` 只供研究早期审批节点、审批人和实例的关系；含旧数据与 `DROP TABLE`，不得作为迁移执行。
- `template_base/` 提供工程规则、脚手架和 MyBatis-Plus Base 生成器。新业务代码在 `projects/unexamine/`，不引用旧项目源码、旧台账或旧验收结果。
- 复用本机已有 Docker `mysql`（3306）和 `redis`（6379）；后端固定 9999，一个前端、一个后端，不引入 Nginx 或 Compose。新库使用 `unexamine_r15`，旧库不改动。

## 实现顺序

| 顺序 | 可观察结果 | 本阶段才设计的表 |
| --- | --- | --- |
| 1. 基础骨架与数据模型 | 新库空库迁移、Base 生成、前后端构建通过；明确账号、系统、模块、记录的最小契约 | 仅创建首条业务旅程所需表 |
| 2. 管理员建模 | 管理员登录、创建系统和主租户、建模块组/模块/字段、发布并在页面读回 | 根据页面行为补齐配置和发布表 |
| 3. 成员运行 | 邀请成员、按授权打开模块、录入、编辑、查询和查看记录 | 根据权限和查询实测补齐成员、授权与索引表 |
| 4. 基础审批 | 管理员配置简单审批，成员发起和办理，同一记录状态可读回 | 参照早期审批模型，设计 Flow 定义、节点、实例与待办 |
| 5. 后续能力 | 文件、导出、应用、仪表盘、任务、AI 等按 `user_requirement.md` 逐项落地 | 每项能力进入实施时再建必要表 |

每个步骤都从需求原文和实际页面用例进入；数据库、生成的 `base`、`manage`、前端和持久化读回在同一业务对象上闭合。表数不作为进度。配置发布后的历史快照和权限隔离按对应阶段验收，不为尚未实现的功能预建整套表。

## 当前断点

基础旅程已在真实页面、双账号 API 和隔离 MySQL 中验证：账号与系统、模块建模发布、成员菜单权限、动态记录、单节点审批、业务附件、按当前权限筛选的 CSV 导出、Excel 预检查与导入，以及现有页面动作和列表菜单名称的草稿与发布控制。动作关闭后页面与 API 同时生效，角色权限不能绕过；旧发布快照保持不变。流程版本快照、拒绝后重提、越权和重复办理、附件访问隔离、导出权限、导入整批回滚与失败原因均有本轮证据。当前执行步骤以 `rebuild-state.json` 为准；这仍只是 `docs/user_requirement.md` §2.3 的一部分，不等于 §10 的全量产品交付。下一步补普通用户消息入口和审批通知，再核对自定义字段唯一匹配、开放接口、应用访问、权限中心、复杂流程、移动端及部署包等明确缺口。上一版已作为 Git 提交 `da80e971` 和标签 `pre-rebuild-15-20261017` 保存，不作为本轮需求或完成证据。
