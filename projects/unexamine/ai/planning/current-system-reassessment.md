本文件是对当前实现可复用性的重新评估，不是产品需求源。产品范围与验收仍只来自 `docs/user_requirement.md`、已校验的原子需求和用例。

## 1. 为什么必须回退复审

历史 Git 记录至少经历 P9、P12、P14、P15、P16、P17、P18 以及当前 `temp 2.x` 至 `temp 6.0` 多轮页面和产品重构。多次失败记录重复出现相同原因：平台、系统与运行态混杂；页面按接口和表结构组织；内部 ID、状态码和 JSON 外泄；原型或局部页面替代连续系统旅程；构建、HTTP 与浏览器可点击被当成完成。

当前框架虽已建立 184 条原子需求、60 个用例、206 个任务和周期证据，但仍存在三个结构性失效：

1. 原子用例分别通过后，没有一条不可拆分的跨能力“建立并使用一个业务系统”总旅程否决整体完成。
2. 周期证据接受测试、构建、局部截图和数据读回，却没有验证需求目录是否被缩减实现；例如 Flow 用例通过时，实际节点目录和审批人来源仍远少于需求。
3. 用户明确否决当前系统后，任务图只追加前端体验 Hardening，默认后端能力已经完整，没有触发 `review_before_reuse` 的重新评估和任务重排。

## 2. 直接证据

- `DEC-20260817-004` 已决定使用 TanStack Table、Vue Flow、ECharts 和 Monaco；当前 `frontend/package.json` 仍只有 Ant Design Vue、Pinia、Vue 和 Vue Router。
- `REQ-FLOW-DESIGN-VERSION` 与 `REQ-UI-FLOW-DESIGNER` 要求完整节点目录、可拖拽缩放画布、小地图、条件分支、审批人预览和错误高亮；当前 `FlowDesignerView.vue` 是线性纵向节点列表，前端仅实现 8 个节点入口，类型声明与页面实现还不一致。
- `REQ-FLOW-APPROVAL-NODE` 与 `REQ-ORGANIZATION-MEMBER` 要求人员、角色、部门、负责人、上下级、人员字段和上一处理人等审批人来源；当前设计器让管理员填写“审批人账号 ID”，运行页转办和加签同样填写账号编号。
- `REQ-VISUAL-PAGE-DESIGN` 要求管理员无需编辑 JSON；当前 Flow 运行、工作配置、消息测试、固定参数和 KPI 页面仍把 JSON、字段编码和账号 ID 作为主要输入。
- `REQ-CONFIGURABLE-DASHBOARD` 与 `REQ-DASHBOARD-DATA-COMPONENTS` 要求组件拖拽、尺寸、图表与多类数据源；当前仪表盘从编码/模块编码表单开始，运行图表只绘制 CSS 横条，未接入图表库，外部 API 与数据库直连数据源未进入实现目录。
- `REQ-AI-RIGHT-ASSISTANT` 要求右侧上下文助手；当前只有未使用的 `.system-ai-rail` 样式，业务页面没有挂载右侧助手。没有已发布助手时，运行页仍展示整张禁用查询表单。
- `REQ-ORGANIZATION-MEMBER` 要求统一部门成员目录和选择器；当前客户运营中心只有一个成员、没有部门，页面显示“成员 #20”，授权控制器只有部门创建与现有成员分配，没有形成管理员可理解的成员开通主链。

## 4. 任务图纠正规则

1. `CYCLE-058` 不能直接进入样式和文案 Hardening；先完成本复审、任务目录和依赖重排。
2. 新任务必须服从 `system-reconstruction-sequence.md` 的“先骨架、后血肉”顺序，优先形成可运行的纵向系统链，而不是再次按孤立页面横向扫尾。
3. 每条纵向链同时包含必要的数据库评估、manage、前端、真实角色操作、持久化读回、权限/失败结果。
4. 最终总旅程至少连续完成：组织成员 → 模块建模发布 → 业务记录 → Flow 审批回写 → 仪表盘更新下钻 → 助手查询与确认写入 → 待办消息审计。
5. 用户明确否决页面清晰度或正常使用感时，该旅程立即失败并回到对应任务，不允许通过新增截图、改状态文件或只修文案补偿。
6. 只有完整系统旅程通过后，才允许从本项目的真实过程提炼并回写 `template_base`；Template Base 不再提前承载 Unexamine 的产品结论。
7. 当前实现没有沉没成本保护；只保留能服务正确主链且通过行为测试的实现，产品结构错误的部分允许直接替换。每轮重构必须通过 `system-reconstruction-sequence.md` 的 2024 业务基线与当前需求增量，禁止功能倒退。

## 5. 2024 年实现对当前重构的约束

本节只审阅 2024 年最后一个提交 `e189fe5d` 的工程形态，用来识别后来重构丢失的业务结构；它不是需求源，也不允许把旧接口、旧表结构或旧缺陷直接搬回当前实现。

### 5.1 应恢复的设计原则

1. **先有业务域，再有技术能力。** 当时的根模块直接对应 `core`、`module`、`upload`、`web/examine`；模块、组织权限、审批、文件各自承担明确职责。当前实现必须恢复这种业务归属，不能继续让用户在“能力中心”之间拼装一件工作。
2. **模块是业务运行载体。** `un_module` 同时表达系统、分组和数据模块，客户、项目、合同等业务对象处于清晰层级；字段、记录、菜单动作、角色和数据权限都围绕模块关联。当前的系统建模、运行页面、动作、Flow、统计和文件必须围绕同一个已发布模块闭环。
3. **组织权限先形成统一上下文。** `ModuleAuthManageService` 一次汇总当前成员、部门、角色、菜单和本人/下属/本部门/子部门/全部等数据范围；审批再复用人员上下级、部门和角色映射。当前实现不能让不同页面分别输入账号 ID、成员 ID、部门 ID 或各自维护人员来源。
4. **审批是一个聚合和事务链。** `ExamineSaveBO` 一次承载审批基础信息、设置、可发起人、节点和节点人员；发布修改时旧版本下线、新版本保存。`ExamineContext` 一次装入组织映射、模板、节点、实例、处理输入和待更新结果，`create/process/queryById` 是清晰的发起、处理、查询入口。当前 Flow 必须恢复“设计发布—业务绑定—实例发起—人员处理—业务回写—全程追踪”的聚合边界。
5. **普通操作使用业务语义。** 当时接口和表名直接表达客户、项目、合同、审批、角色、部门、字段、记录等对象。当前界面和 API 可以保留稳定编码作为内部标识，但不能再让普通用户通过编码、JSON 和裸 ID 完成日常业务。
6. **文件是业务附件，不是独立技术表单。** 2024 年已把本地、FTP、OSS、AWS、七牛、腾讯等存储实现收敛在统一文件服务之后；当前文件入口应回到记录、任务、审批和消息上下文，存储提供方保持后台配置。

### 5.2 不能继承的旧实现问题

- 角色字段、角色菜单等服务存在明显复制式 CRUD，甚至错误复用模块记录扩展数据逻辑；当前必须按领域规则实现，不能照搬类结构。
- 旧数据模型混用了固定槽位字段和扩展键值表，SQL 中缺少完整约束与版本治理；当前继续使用现有元数据和发布模型，但要通过统一领域服务对外提供稳定语义。
- 旧审批处理器虽已有模板/实例分离和处理器分派，但存在空集合假设、人员映射方向错误、状态比较错误、处理节点推进不完整等问题；它只能证明业务骨架清晰，不能证明引擎可直接复用。
- 条件表达式和菜单动作仍把 JSON 放进持久化结构；JSON 可以作为内部存储，但当前管理员必须通过可视化规则、字段选择器和动作向导编辑。
- 旧代码缺少当前需求中的多租户治理、完整审计、可视化设计、数据源、仪表盘、AI 助手和运维闭环；这些仍以当前唯一需求为准重新实现。

### 5.3 对后续任务图的直接结论

后续不再按“组织页、Flow 页、仪表盘页、AI 页”孤立修补，而按以下聚合和依赖重建：

1. `IdentityOrganizationContext`：成员开通、部门、岗位/上下级、角色、统一人员选择器、数据范围预览。
2. `BusinessModuleDefinition`：系统内模块、字段、页面、动作、版本、发布和运行导航。
3. `FlowDefinitionAndInstance`：节点目录、规则、审批人策略、版本、业务绑定、实例、任务、回写和异常补偿。
4. `BusinessRecord`：记录增删改查、关联、文件、评论、动作、Flow 状态和审计时间线。
5. `AnalyticsDashboard`：业务数据源、指标、图表、编排、权限过滤、下钻和首页呈现。
6. `ContextualAssistant`：系统内可见助手、当前业务上下文、来源解释、结构化确认写入和审计。
7. `WorkInbox`：审批待办、任务、消息、通知和对象跳转的统一工作入口。

任何聚合都不能仅凭接口存在或单页可点击判定完成；必须在同一套客户运营中心数据中串联验证。
