# 第 15 次重构：同一候选系统验收与全产品缺口

核对依据：`docs/user_requirement.md` §2.3、§10、A.15–A.20。`docs/表意义.md` 只帮助理解表的业务关系；旧 SQL 和旧实现不作为完成依据。2026-10-17 在新系统 `85`、模块 `75`、三名新账号及记录 `81`–`83` 上，用真实 Edge、API 和独立 MySQL 连接交叉读回。证据：`ai/evidence/r15-11-integrated-readback.json` 及两张页面截图。该结果只覆盖下述基础旅程。

## 已可实际操作的基础流程

1. 注册登录、创建系统与主租户；创建模块组、模块和常用字段；发布模块。模块组与模块创建由 API 完成，本轮管理员在 Edge 页面配置字段并发布；此前两项已有独立页面验证。
2. 授予角色模块菜单与新增、编辑、导出权限，邀请已有平台账号；成员进入该系统的已发布模块，创建、查看、编辑本人记录并按标题或可搜索字段查询。当前数据范围主要按记录负责人隔离。
3. 同一模块的记录上传附件、下载 Excel 模板、预检查并确认导入、按当前筛选异步导出 CSV；导出只含该成员有权查看的数据。
4. 管理员发布指定审批人单节点流程；成员发起审批，审批人在消息里进入待办查看记录与附件并同意，申请人在消息里进入审批结果对应记录。
5. 撤销角色查看权限后，已有消息仍显示，但记录详情、附件和新的导出请求被 API 拒绝；页面再次打开消息目标也提示无权访问。MySQL 读回同一候选系统的记录、导入、导出、审批、消息和文件引用。

## 必须先纠正的工程偏差

- A.18 要求固定平台能力的表结构在关系梳理后一次定稿，SQL 先行、生成 Base 再写业务；当前只有基础旅程相关的 28 张实体表，平台固定能力并未完整设计。这是后续扩展前的结构阻塞，不应把 28 张表或某次迁移当作设计完成。
- A.19 要求首装表按后端模块维护最终定义、统一业务域表名，并由工程工具生成 `init.sql`、`update.sql`、`final.sql`。当前三个组合文件虽能生成，但首装 SQL 集中在 `V1__foundation.sql`，后续能力分别追加至 `V4`–`V9`；`un_module_record`、`un_message` 等旧式命名尚未收敛到要求的业务域。应先做结构和数据迁移设计，再修改已有测试库，不通过删库规避迁移。
- 需求包含 AI、打印模板、任务、仪表盘等产品能力；它们未实现。现阶段不得将基础旅程或工程门禁通过表述为全产品完成，也不引入需求没有提出的身份源或历史打印文件概念。
