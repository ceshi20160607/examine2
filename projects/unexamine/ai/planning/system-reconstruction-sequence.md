# 系统重构实施顺序

> 2026-09-05：本文件停止作为执行指令。当前唯一执行入口为同目录 `spark-execution-plan.md` 和 `spark-state.json`。下文旧周期安排、历史版本基线及替换建议均不得直接执行；禁止恢复已移除的历史代码作为需求或实现基线。

状态：`approved direction / execution pending`

本文件约束当前实现顺序，不新增产品需求。唯一产品需求源仍为 `docs/user_requirement.md`。2024 年提交 `e189fe5d` 只用于恢复清晰的模块业务骨架；原型只用于交互参照。

## 总原则：先骨架，后血肉

完整系统不是把 20 个能力各做一个页面，而是让能力按依赖逐层长在同一个可运行系统上。后续周期必须遵循以下顺序，上一层没有用真实角色和真实数据跑通，下一层不得以“接口已存在”提前宣告完成。

现有实现没有沉没成本保护。复审结果为 `replace` 的前端壳、Flow 设计运行模型、技术配置表单和错误业务聚合可以直接推倒；只有已证明正确、边界清楚且能服务新主链的数据库约束、Base、认证安全和通用基础设施允许保留。

## 不可退化基线

每次重构必须与前一条有效业务基线比较，而不是只与本轮任务描述比较：

- 新模块骨架未达到 2024 年版已经具备的“新建模块、配置字段、形成表单/列表、保存并查询模块数据”能力，不得判定 S1 完成。
- 在达到 2024 业务基线后，还必须增加当前唯一需求要求的系统/租户初始化、草稿与不可变发布版本、权限、可视化页面、真实运行壳和失败恢复。
- 删除或替换现有实现前记录其仍可用的行为测试；新实现必须通过这些保留行为及新增需求测试。
- 任何重构如果让完成同一业务任务需要更多页面跳转、更多技术输入或更多开发人员解释，视为回退并立即否决。

## S0 纠偏和实施基线

目标：撤销当前“核心能力已完成、只剩前端 Hardening”的错误假设。

完成标准：

- 2024 年模块、组织权限和审批代码完成工程审阅，明确保留原则和禁止照搬的问题。
- 当前数据库、Base、manage、API、前端和测试逐项重新标记 `reuse / modify / replace / delete`。
- 任务目录和四小时周期按本文件重排；原 C58-C64 体验任务移动到功能骨架和血肉之后。
- 任一用户否决或跨能力旅程失败都会回到源码和任务图，不允许用状态文件、截图或文案修改补成完成。

## S1 最小完整系统骨架

连续旅程：

`登录 → 创建系统 → 自动初始化系统管理员/主租户/根部门 → 进入系统 → 新建模块组和模块 → 配置核心字段/列表/表单/详情 → 检查并发布 → 普通用户新建和查看业务记录`

这一层恢复 2024 年已经跑通过的低代码核心概念，并以当前需求补齐版本、租户和界面约束。它必须先于 Flow、应用、任务、仪表盘和 AI。

完成标准：

- 用户不接触系统 ID、模块编码、JSON 或内部状态码。
- 创建系统后不是空壳，至少具有系统首页、组织根节点、管理员成员、模板配置入口和运行导航。
- 模块以业务名称、所属分组和用途创建；字段、页面和动作是模块内部步骤，不是并列技术中心。
- 发布前给出可理解的检查结果；发布后导航立即出现真实模块。
- 使用“客户运营中心”真实创建客户模块，并完成客户记录新建、列表、详情、编辑和审计读回。

## S2 组织、角色和统一人员上下文

连续旅程：

`创建部门 → 开通/邀请成员 → 设置负责人和上下级 → 创建角色 → 配置页面/字段/动作/数据范围 → 发布 → 预览最终权限 → 用目标成员登录验证`

组织不是独立后台页，而是 Flow 审批人、任务负责人、记录归属、消息收件人、KPI 责任人的共同来源。

完成标准：

- 全系统统一成员、部门、角色和人员选择器。
- 页面中不再出现“成员 #20”、审批人账号 ID、转办账号 ID、任务目标账号 ID 等输入。
- 本人、本人及下属、本部门、本部门及子部门、全部及自定义规则形成统一可解释的数据范围。
- 多角色并集、限制交集、字段脱敏和动作范围能在一个最终权限预览中解释。

## S3 Flow 定义、运行和业务回写

连续旅程：

`从模块选择触发点 → 可视化设计 Flow → 配置人员/条件/动作 → 模拟 → 发布不可变版本 → 创建业务记录触发实例 → 待办审批 → 状态回写 → 历史追踪`

实现不照搬 2024 年处理器。参考 Flowable 的分层模型，把流程定义与运行明确拆为：

- `Definition / Deployment`：草稿、校验、不可变发布版本和激活状态；
- `Instance / Execution`：绑定业务键和发布快照的运行实例与执行游标；
- `Task / IdentityLink`：候选人、候选角色/部门、领取、转办、加签、退回和撤回；
- `Variable / BusinessBinding`：流程变量与业务记录字段、状态和动作的显式映射；
- `History`：实例、节点、任务、人员、变量和操作的不可抵赖历史；
- `Job / Incident`：定时、异步、Webhook、通知、重试、人工恢复和补偿。

设计器仍按当前需求使用 Vue Flow 构建适合本产品的画布，不把 BPMN XML 或引擎内部 ID 暴露给普通管理员。开源模型只用于约束正确的引擎边界。

完成标准：

- 节点目录、连线、缩放、小地图、分支条件、属性面板、错误定位和模拟结果完整。
- 审批人来自统一组织上下文，支持人员、角色、部门、负责人、上下级、人员字段、发起人自选和上一处理人等需求来源。
- 已运行实例固定引用发布快照，新发布版本不改变历史实例。
- 审批、驳回、转办、加签、退回、撤回、手工加节点、超时和失败重试均有明确状态机和审计。
- 审批结果在同一事务/可靠补偿链中回写客户记录状态，并生成待办与消息。

参考实现：Flowable 的 Repository/Runtime/Task/History/Management 服务边界、部署版本和运行/历史表分离；bpmn-js 的可扩展建模器结构。是否引入引擎依赖由数据库与后端设计任务根据当前需求复杂度决定，不能仅因开源项目功能多而扩大本产品范围。

## S4 应用、任务、待办、消息和文件协同

连续旅程：

`在客户详情发起动作/Flow → 生成负责人任务与审批待办 → 发送可跳转消息 → 在对象上下文上传文件和记录工作日志 → 返回客户详情看到完整时间线`

完成标准：

- 应用和动作依附于已发布模块，不形成另一套“应用”概念。
- 任务、待办、消息都是业务对象的投影和入口，不要求用户复制编码或 ID。
- 文件只在记录、任务、Flow 和消息等对象上下文出现；存储提供方留在后台。
- 所有操作可从工作入口跳回准确对象，并在对象时间线读回。

## S5 数据源、仪表盘、KPI 和系统首页

连续旅程：

`选择已发布客户模块 → 可视化定义指标/图表 → 编排系统首页 → 按当前权限查看 → 点击图表下钻到客户列表 → 记录变化后刷新指标 → KPI 触发提醒`

完成标准：

- 数据源、维度、指标、过滤和权限以业务名称配置，不以编码表单作为首屏。
- ECharts 呈现真实统计，组件可拖拽和调整尺寸，空/错/加载状态完整。
- 内部模块、外部 API、数据库直连按需求分别具备连接测试、版本和权限边界。
- 系统首页展示真实业务指标、我的任务/待办和继续工作入口，不展示验收说明。

## S6 上下文 AI 助手

连续旅程：

`在客户详情打开右侧助手 → 助手只读取当前用户可见信息 → 展示来源 → 生成结构化跟进记录 → 用户确认 → 写入客户并产生审计`

完成标准：

- 已发布系统至少有一个可用助手策略；没有助手时只显示清晰空状态和管理员去配置入口。
- 助手理解当前系统、模块、记录和选择内容，不要求用户填写技术查询结构。
- 所有写入先展示结构化预览，明确字段变化，确认后才提交。
- 模型失败、无权限和外部依赖不可用时降级明确，不阻断普通业务操作。

## S7 全系统收口与生产验收

使用同一套客户运营中心数据，由平台管理员、系统管理员、销售成员、销售主管和只读审计角色连续执行 S1-S6。随后才进行统一设计系统、全路由语言、桌面/平板/移动、可访问性、部署升级、备份恢复、安全和性能收口。

最终完成只有一个含义：用户不需要开发人员解释，就能创建并配置系统、开展客户业务、完成审批协同、查看经营数据并使用受控助手；每一步均有真实持久化结果、权限边界、失败恢复和审计证据。
