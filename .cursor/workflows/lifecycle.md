# 软件工程生命周期

宏观阶段按 Gate 串行，阶段内部按依赖图敏捷并行。任何项目可以增加节点，但不能跳过同等约束。

```text
S0 实例初始化
 -> S1 需求理解与产品边界
 -> S2 产品/UI/工程设计
 -> S3 开发（垂直业务切片）
 -> S4 测试与集成
 -> S5 发布与用户验收
 -> S6 复盘与模板改进评审
```

## 交付节奏

`cadence_contract: baseline_target<=240m; task_estimate=10..120m; delivery_cycle=240m; cycle_package=exactly_once; verification=affected_tasks_then_cycle_then_release; parallel=disjoint_modules_by_default`

生命周期必须同时存在三层，不得把整个阶段当成一个执行任务：

| 层级 | 目的 | 时限 | 结束时必须看到什么 |
|---|---|---:|---|
| 项目阶段 | 从骨架逐步增加业务能力 | 由路线图定义 | 一组可解释的产品能力 |
| 模块交付周期/工程节点 | 依赖图决定数量的短任务组成一个模块增量 | 固定 4 小时 | 可启动、可进入、可操作、已打包的版本和完成/剩余清单 |
| 执行任务 | 单一模块内的实现、使能或验证结果 | 10 分钟..2 小时 | 受影响模块绿色、输出可读回 |

硬规则：

1. 初始需求理解、外部研究、产品边界和工程分期必须在首个 4 小时内形成可执行基线；未决问题进入 issue/待决项，不允许无限延长“理解阶段”。
2. coding task 预计超过 120 分钟必须按模块内可验证结果拆分，推荐 45..90 分钟；模块交付周期按墙钟固定为 240 分钟。到点必须停止扩范围、集成绿色子集、打包验收并结转剩余项。
3. 首个可运行骨架最晚在第一个可演示期结束前出现；之后每个工程节点都要保持系统可启动，每个可演示期都要提供用户可见或明确的工程使能结果。
4. 数据、接口、页面、生成代码或单一模块可以作为短任务并独立完成，但不能单独宣称 slice、旅程或阶段完成。
5. 需求和设计采用逐期细化：先冻结跨期边界和当前期契约，只对下一期保留概要；禁止为了开始一个小功能而一次冻结全部未来字段、表、接口和非功能矩阵。
6. 普通任务走“实现 + 独立验收”短循环；只有权限、安全、不可逆迁移、跨模块公共契约或高风险发布使用多角色重治理。
7. routine task 只记录受影响模块的自检结果，不单独打包；每个 4 小时周期只做一次累积回归、打包、重启/健康检查、关键浏览器路径与完成/剩余盘点；phase/release 再执行完整响应式、无障碍、性能和安全矩阵。

### 4 小时周期硬边界

周期开始必须一次性写清：模块最终能力清单、已有能力、当前周期承诺、明确不做、参考桌面 UI 基线、冻结契约、任务 DAG、并行写集、集成 owner、周期结束时间和包输出位置。没有这些输入，不创建实现任务。

周期执行只允许消费冻结输入。不同后端模块、前后端和测试写集互不重叠时默认同时开始；发现边界缺口时由产品/UI/技术 owner 在周期内收敛为明确决定，不允许实现者靠重复试错猜需求。

周期结束统一执行一次：合并并行结果、累积回归、生产构建、生成可运行包、冷启动/健康检查、关键角色入口和权限正反例。随后公布模块逐项 `completed/remaining/deferred`，未完成项携带原因和下一步进入下一周期；禁止为了让报告好看把剩余项静默删除。

周期包是滚动可运行快照，归属于当前正式里程碑。`CP1/CP2/CP3` 仍是三个正式发布检查点；滚动周期包不得伪装成新的正式检查点，也不得替代正式检查点的证据条件。

## S0 实例初始化

主责：Leader + PM。

必需产出：

- 已填写的实例配置。
- 路径和权威输入清单。
- 启用角色及项目 `update.md`。
- 初始状态、问题注册表和用户待决文件。
- 模板/实例校验结果。

退出 Gate：实例自包含、无未填写占位、事实源和下一节点明确。

## S1 需求理解与产品边界

主责：analyst 提取事实，product 形成产品包，PM 组织专业预审，Leader 验收。

工作顺序：

1. analyst 建立来源索引、冲突和缺口。
2. product 形成目标、范围、角色旅程、业务规则和验收结果。
3. uiux、architect、dba、backend、frontend、test、ops 按需独立预审可设计/可实现/可测试/可交付性。
4. PM 组织会审并收敛问题。
5. Leader 验收需求节点。

首个 4 小时只要求形成足以规划整个项目并启动第一期设计的基线：最终目标、角色旅程、模块边界、关键风险、阶段路线图和当前期验收。其余细节按可演示期 just-in-time 深化；发现会改变跨期架构的缺口再退回本 Gate。

主产出：一个 `requirement-package`。最终目标较大时同时建立 `final-goal-ledger` 和独立 `journey-gate`；复杂项目可引用专业附录但不能复制主结论。

退出 Gate：目标、范围、角色旅程、业务规则、权限/数据/状态/异常、非功能和开放问题清晰；下游无需猜测关键产品行为。

## S2 产品/UI/工程设计

主责：uiux + architect + dba，product 保持产品一致性，backend/frontend/test/ops 共同形成可实现与可验收契约。

可并行工作：

- UIUX：信息架构、交互、原型和状态矩阵。
- Architect：模块、集成、权限、状态、非功能和运行边界。
- DBA：数据模型、迁移和生成契约。
- Backend/Frontend/Test/Ops：分别审查接口、映射、验收和部署边界。

共享产品语义或消费所需的契约 artifact 冻结后即可并行；不要求等待整个上游 task 完成。共享主文件由声明 owner 单写。

主产出：一个 `design-package`，引用 UI、架构、数据、接口、测试和发布分片。

设计按期冻结。第一期必须先完成可运行骨架所需的项目模块/POM、路由壳、认证入口、数据库子集、生成器和部署方式；后续期只补本期会实现的详细原型、表、接口和验收，不得把所有远期业务设计成单个前置阻塞节点。

退出 Gate：首个开发任务不需要猜测关键需求、参考桌面视口行为、数据、接口、权限、状态、错误或部署方式。管理系统参考桌面基线至少冻结系统导航、页面头/工具栏、带表头和行操作的列表、标签页详情、动作层级以及 loading/empty/error/permission 状态；完整响应式、可访问性和跨模块视觉矩阵可以在功能开发后进入 S4 hardening。

## S3 开发

主责：PM 管项目，Planner 拆 DAG，DBA/Backend/Frontend/Ops 实现，Test 独立任务验收，Leader 验收批次节点。

任务执行顺序：

```text
现有工程模块 + 模块完整能力/已有/剩余清单
 -> 冻结当前周期边界、参考桌面 UI 和消费者契约 artifact
 -> 建立 module_scope/write_scope DAG
 -> 无依赖且写集不重叠的任务并行
 -> 各任务运行受影响模块自检
 -> 周期末一次集成、累积回归、打包和真实入口读回
 -> 发布 completed/remaining/deferred 清单
```

每项任务只需声明 `goal_or_slice`、`module_scope`、`write_scope`、`depends_on_artifacts`、`estimate_minutes`、`quality_stage`、验收命令和完成结果。DB/base generation、公共组件和契约可以先行；消费者在其所需 artifact accepted 后即可启动。

任务超过 120 分钟后，PM 记录一次偏差、剩余估算和串并行调整；可以在自然边界拆出后续任务。周期到达 240 分钟后不再继续扩范围，立即按周期 Gate 集成、打包并如实结转，不能丢范围或伪标通过。

routine task 不要求五类证据全集和逐检查点 SHA；只验证受影响层，允许以 `not_affected: reason` 说明其他层。standard/critical task 使用独立 verifier。周期保存一份集成/包/关键旅程结果，phase/release 保存完整矩阵证据并更新 completion ledger。

并行是无依赖、不同 `module_scope/write_scope` 任务的默认执行方式。只有共享 schema/migration、lockfile、公共契约、同一聚合根或运行资源实际冲突时串行或隔离。

退出 Gate：周期内承诺项逐项有状态；绿色子集已通过累积回归、生产构建、打包、冷启动/健康检查和关键入口；未完成项已明确结转；无开放 P0。短任务通过不等于模块周期、角色旅程或最终系统通过。

## S4 测试与集成

主责：Test，PM 管缺陷循环，专业角色修复，Leader 验收集成节点。

必需覆盖：

- 真实角色和真实入口。
- 前端、服务端、数据、权限和状态贯通。
- 正常、空、加载、禁用、校验、错误、异步、重试和并发（适用时）。
- 持久化后重载、重登或重启读回（适用时）。
- 关键非功能、安全、迁移和回归。
- 统一 responsive hardening：桌面/移动/关键断点、横向溢出、可访问性和视觉一致性；不在每个功能 task 重复执行。

失败循环：test 提 issue -> PM 分流 -> 责任角色修复 -> 原 test/独立 verifier 复核。结构性缺口退回 S1/S2，不在测试阶段临时发明需求。

退出 Gate：关键角色旅程工程证据通过，P0 缺陷关闭，发布候选具备进入条件。

## S5 发布与用户验收

主责：Ops 发布，Test 验证交付方式，PM 组织验收材料，Leader 确认工程 Gate，用户完成最终验收。

必需产出：

- 可追踪制品、外置配置和运行说明。
- 部署、健康、重启、迁移、备份、回滚和清理证据。
- 用户试用入口、账号/数据准备说明（不得泄露敏感值）。
- 验收清单、已知限制和用户签字位置。

退出 Gate：工程发布证据通过并且用户或指定验收人明确确认。工程角色不得设置用户签字状态。

## S6 复盘与模板改进评审

主责：Leader + PM，相关角色参与。

项目经验只有满足以下条件才进入模板候选：跨项目成立、实际执行过、有正向或失败证据、能去除项目路径/术语/技术假设、不会扩大默认角色权力。

项目特殊规则、临时方案和未验证建议继续留在实例，不进入公共模板。

## 节点通用循环

每个节点执行：

```text
声明目标/输入/输出/Gate
 -> 校验前置和上下文
 -> 角色独立工作
 -> PM 分流问题并组织必要会审
 -> 责任人修正
 -> 独立验证
 -> Leader 节点验收
 -> 同步状态和下一节点
```

重大节点使用三轮治理；普通小任务使用实现 + 独立验收的短循环。
