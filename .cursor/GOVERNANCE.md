# 工程治理规约

## 1. 事实优先级

从高到低：

1. 用户已确认决策和用户专属 Gate。
2. 当前 `session/state.json`。
3. 已通过节点验收的需求、设计和契约产出。
4. 当前问题注册表与会议决定。
5. 可复现的测试、运行和发布证据。
6. 当前任务输出。

聊天陈述、未落盘讨论、历史“已完成”标签、旧截图、旧代码和未声明文件不能覆盖以上事实。

## 2. 上下文隔离

- 每次角色执行使用新会话或等价的干净上下文。
- 启动包只传文件路径和任务元数据，不传上一角色的聊天摘要。
- 角色只读声明输入，只写声明输出；发现需要越界时先提交 issue。
- 同一输出同一时刻只有一个写入角色，其他角色写 review 或 issue。
- 推测必须标记为 assumption，不能写成已确认需求。
- 历史材料只有被当前节点显式列为输入时才能读取。
- 上下文压缩或中断后，必须从实例配置、状态和当前节点重新恢复，不能凭记忆续写。

## 3. Issue 流程

任何影响需求、范围、设计、数据、权限、接口、状态、副作用、验收或发布的问题都写入唯一问题注册表。

```text
提出人记录事实和影响
  -> PM 分类、定级、指定参与人
  -> 相关角色独立审查
  -> PM 组织会审并记录决定
  -> 责任角色修正
  -> 原提出人或 test 独立复核
  -> Leader 在节点验收时确认关闭
```

P0 问题阻断当前及下游节点。提出人不能单独关闭自己的 P0，PM 不能只凭会议结论把未验证问题标为关闭。

## 4. 会审协议

以下情况必须会审：

- 后端或前端认为需求、设计、接口或数据契约不可实现或互相冲突。
- 变更影响产品行为、界面流程、数据模型、权限模型、跨模块边界或验收标准。
- 同一问题修改两轮仍未通过。
- 编码阶段暴露出本应在需求或设计阶段解决的结构性缺口。

PM 是会审负责人。最低参与规则：

- 用户可见行为：提交人 + product + uiux + test。
- 跨层实现：提交人 + architect + backend + frontend，按需加入 dba/ops/test。
- 需求或范围：product + analyst + PM，按需加入 uiux/architect。
- 发布风险：ops + test + 受影响实现角色。

会审必须使用 `templates/meeting-decision.md`，记录证据、分歧、决定、行动项和复核人。没有落盘决定等于没有开会。

## 5. 决策权限

| 决策 | 主责 | 复核/验收 |
|---|---|---|
| 项目计划、依赖、会议和问题归属 | PM | Leader |
| 产品目标、范围建议和用户流程 | product | PM 组织，Leader 检查，必要时用户决定 |
| 需求来源、冲突和完整性 | analyst | product/PM |
| 架构、跨层和普通技术方案 | architect/专业角色 | Leader |
| UI/交互设计 | uiux | product/test，主观体验按实例要求由用户确认 |
| 数据设计 | dba | architect/backend/test |
| 实现 | backend/frontend/ops | test/独立验收者 |
| 工程节点通过 | Leader | 必须基于独立证据 |
| 最终满意、范围增删、重大产品取舍 | 用户或指定业务负责人 | 不可代签 |

## 6. 阶段与并行

- 需求、设计、开发、测试/集成、发布/用户验收的宏观 Gate 不得跳过。
- 阶段 Gate 决定“何时宣称阶段完成”，不阻止后续独立模块提前开发；提前开发的模块只能声明 task/slice 完成。
- 依赖已满足、模块和写入路径不重叠、共享契约已冻结的任务默认并行。只有共享 schema/migration、lockfile、公共契约或同一聚合根写入才要求串行或资源隔离。
- 共享文件实行单写者；多角色意见通过 review/issue/meeting 汇入，不并发改主文件。
- 并行任务如果发现共享前提变化，立即暂停并回到 PM 重新规划。
- 页面、接口、表、生成代码或单一模块可以作为短执行任务，但不能单独宣称 slice、旅程或阶段完成；slice 集成时再验证完整业务结果。

### 6.1 时间盒与治理强度

`governance_contract: routine|standard|critical; task_estimate=10..120m; delivery_cycle=240m; cycle_package=exactly_once; task_package=forbidden; parallel_default=disjoint_modules`

- coding task 目标估算为 10..120 分钟，推荐 45..90 分钟；超过 120 分钟必须按模块内可验证结果继续拆分。任务数量按依赖图决定，不设固定 2..3 个上限。
- routine task 由 owner 运行受影响模块的构建/单测并记录命令结果；standard/critical task 才要求独立 verifier。task 不再重复提交 API/DB/UI/Browser/Restart 五类全集。
- 240 分钟是物理交付周期，不是一个微小功能的宽松截止时间。每周期只选择一个可说明的模块结果，周期开始必须冻结模块完整清单、当前周期范围、剩余项、参考桌面 UI 结构、任务 DAG、并行写集和周期末可运行包目标。
- 周期内短任务只运行受影响模块的构建/单测并保持主干可编译；短任务不得各自触发全量回归、重启、浏览器矩阵或打包。周期末只集成一次，执行累积回归、构建/打包、启动/健康检查、关键真实入口和权限正反例，并报告模块已完成项、未完成项和下一周期输入。
- 禁止把一个接口、一个页面片段或一份证据单独升级成 4 小时工程节点；这些只能是同一模块周期 DAG 中的短任务。周期结束即使模块未全部完成，也必须打包当前绿色子集并如实结转明确剩余项，不得通过继续扩范围掩盖偏差。
- 任务证据按 `affected -> required`：仅变化层必须验证，未受影响层允许记录原因；真实入口、跨层读回和权限正反例在周期集成时验证一次，全量响应式、无障碍、性能和安全矩阵仍在 phase/release hardening 验证。
- `routine`：既有模式内的局部实现，owner 自检 + 一个独立 verifier；不召开多角色会议。
- `standard`：跨前后端或数据边界，相关专业角色做针对性评审，PM 只处理真实分歧。
- `critical`：认证授权、安全、不可逆迁移、公共契约或高风险发布，使用完整独立评审和 Leader Gate。
- 普通任务不得因“可能更严谨”自行升级为 critical；升级必须写明风险和受影响范围。
- 研究和设计结论先服务当前期。首个 4 小时形成项目基线，远期细节进入滚动规划，不能阻塞首个可运行增量。
- Planner 先按现有 Maven/前端 feature 模块建立 DAG。无依赖且 `module_scope/write_scope` 不重叠的 ready task 默认并行；只有明确冲突或集成成本高于收益时才串行，并记录理由。
- 并行组只强制无内部依赖和写集不重叠；仅在实际共享 migration、生成目录、lockfile、DB schema、测试数据或端口时声明并隔离对应资源。
- 用户可见模块编码前必须冻结参考桌面 UI 基线：沿用系统导航；页面头包含标题、上下文和主操作；列表有筛选/工具栏、表头、行操作以及空/加载/错误状态；详情/编辑按概览、配置、版本、运行数据等任务使用标签页；主次/危险操作层级明确。缺失或明显不合理时 uiux/frontend 必须登记问题并先修正设计，不能静默实现接口调试台式页面。
- 功能开发只要求参考桌面基线达到合理、可用和视觉层级清楚，不要求每个 task 重做移动端、断点、视觉一致性和无障碍矩阵。完整响应式、跨模块视觉收口和可访问性进入 `hardening` 批次，在 release 前统一完成。
- 完成状态必须由 `completionLedger` 逐级证明 `TASK -> SLICE -> PHASE -> JOURNEY -> RELEASE -> FINAL`；每级声明完整子节点集合和证据哈希，禁止只追加 accepted ID 或越级置位。

## 7. 产出与文档卫生

- 每个阶段只有一个主索引或主产出，专业分片由主文件引用。
- 节点关闭时，临时文件必须合并、登记保留理由或删除。
- 旧文件删除前先分类：仍是事实源、可提炼规则、历史证据、生成/缓存噪声、可删除、未知。
- 未完成盘点时不得批量删除未知材料。
- 状态只写在状态文件；问题只写在问题注册表；用户待决只写在待决文件。
- 同一结论修改后必须扫描并移除冲突旧结论。

## 8. 已知失败模式

以下规则来自多次真实失败，所有项目默认生效：

- 文件、页面、接口、表、生成 CRUD、构建和 HTTP 成功都不等于用户可用。
- 静态原型只能说明视觉和流程意图，不能代替真实功能、权限、持久化和失败处理。
- 不按用户角色和真实入口验收，会产生“管理员能跑、普通人不会用”的假完成。
- 配置态和使用态、平台态和业务态混在一起，会让权限和导航失真。
- 长聊天传话会把讨论当决定、把做过当完成；角色必须只读落盘输入。
- 实现者自验会掩盖缺口；验收必须独立。
- 需求和设计未冻结就编码，会把结构性问题变成反复局部补丁。
- 页面/API/模块优先的任务拆分会丢失完整业务结果；必须从最终目标和角色旅程向下拆。
- 假成功提示、演示数据、通用占位详情和只在截图中存在的功能都属于阻断问题。
- 用户指出一个问题时，必须推导通用规则并扫描同类位置，不能只修字面位置。
- 旧资料未经盘点直接删除会丢失经验；未经筛选全部保留又会污染上下文。
- 把响应式截图、重复重启、五类证据全集和流程文档绑定到每个小任务，会让治理成本超过实现成本；这些验证必须按 task/slice/phase/release 分层执行。

## 9. 完成声明

允许的声明必须与证据层级一致：

- 自检通过：实现者本地检查完成。
- 任务工程验收通过：独立验收者验证任务契约。
- 角色旅程通过：真实入口、数据、权限和状态证据完整。
- 发布验证通过：交付包在目标方式下启动、健康、回滚和清理可验证。
- 用户验收通过：用户或指定验收人实际确认。

低层级证据不能使用高层级完成措辞。
