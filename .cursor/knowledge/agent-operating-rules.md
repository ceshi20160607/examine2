# Agent 通用工作规约

> 目的：沉淀所有项目都适用的工作方法。项目专属产品规则必须放到项目自己的规约文件中，不能混入本文件。

## 1. 先恢复落盘事实

- 每次开始实质工作前，先读取当前项目声明的规范、状态、需求、设计、评审和知识库文件。
- 不依赖长聊天记忆做判断；聊天里的结论只有写入项目文件后才算事实。
- 如果上下文很长，先把用户的新纠偏写入项目的需求、评审、状态或知识库，再继续修改。
- 平台自动上下文压缩不可控，所以统一采用“落盘事实恢复”：让后续会话只读文件即可恢复关键上下文。

## 2. 不做字面补丁，要做连带推理

- 用户指出一个具体问题时，必须推导它背后的通用规则，并扫描同类位置。
- 修正动作必须覆盖“目标行为 + 去除冲突旧行为”。例如：某对象已经支持整块点击后，重复的同义按钮也要同步移除。
- 对新增入口、交互、状态、权限、布局，都要检查是否带来重复入口、遮挡、禁用态、空态、权限态、窄宽适配等连带问题。
- 修改后必须同步到项目的需求、brief、review 或 knowledge，不能只改当前界面文件。

## 3. 主动作唯一

- 同一个对象在同一上下文中只保留一个主动作入口。
- 列表数据行的主动作通常是查看详情；卡片的主动作通常是进入关联对象或展开内容。
- 行内按钮或卡片内按钮只承载与主动作不同的操作，例如编辑、删除、审批、转移、导出、归档、标记已读。
- 如果按钮只是重复“进入详情/打开对象/查看日志”，应移除，避免占空间和制造选择负担。

## 4. 对象和视图分离

- 先区分业务对象，再设计视图。
- 列表、看板、日历、时间线是同一对象集合的不同视图，不是新的业务对象，也不能重复造数据。
- 当两个概念拥有不同字段、生命周期、权限或业务目的时，应拆成不同对象或不同主标签，而不是塞进一个笼统标签。
- 视图切换应互斥展示：列表就是列表，看板就是看板；不应默认把两个大视图并排堆在同一屏。

## 5. 列表与详情

- 列表型页面的数据行应支持点击整行查看详情。
- 点击行默认打开右侧详情抽屉、右侧工作区或详情页，并保留列表上下文。
- 点击复选框、按钮、链接、输入框、下拉框时不得误触发行详情。
- 详情页必须使用专属业务内容，不能复用无关矩阵、占位表格或通用模板糊弄。

## 6. 设计自检顺序

1. 入口是否真实存在，而不是隐藏在演示按钮或不可见状态里。
2. 权限是否真实裁剪，未授权入口是否隐藏或禁用且说明原因。
3. 主对象是否分清，运行态和配置态是否混在一起。
4. 主动作是否唯一，是否存在重复按钮、重复导航或重复功能区。
5. 列表、筛选、排序、分页、空态、禁用态、失败反馈和审计是否完整。
6. 后台配置是否能支撑运行态：字段、列表、筛选、场景、动作、状态、标签、权限、流程、日志。

## 7. 验收要求

- 交付前至少做一次静态断链检查：页面、弹窗/抽屉、页签、视图切换目标必须存在。
- 对用户刚指出的问题，必须做同类问题扫描：改了哪里、移除了哪里、同步沉淀到哪里。
- 运行项目允许的可视化或自动化验收；无法运行时说明原因。
- `git diff --check` 必须运行；若只有 Windows LF/CRLF warning，要明确说明。
