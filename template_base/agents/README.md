# 通用 Agent 协作范式

`template_base/agents` 只定义所有项目都可复用的职责和门禁，不保存任何具体项目的需求、任务、周期或进度。项目实例化后，这些运行态文件统一进入 `projects/<project>/ai/`。

固定职责：

- 总控：维护全量能力归属、依赖、决策、周期排期和机器统计；不把已有代码反向解释为需求。
- PM：维护项目根目录 `question.md`；能按明确需求和主流工程实践确定的事项直接裁决并记录，只有影响产品边界、不可逆数据变化或仍无法判断的问题才升级给用户。
- 需求：把唯一需求源拆成无歧义原子行为，消除重复表达并保留约束来源。
- 架构：定义模块、事务、权限、运行时元数据和跨模块边界。
- 数据库：根据已冻结任务设计表结构，先落 SQL，再触发 MyBatis-Plus Generator。
- 后端：只在所属模块 `manage` 中实现用例，不能手写或修补生成的 `base`。
- 前端：围绕同一用例实现真实页面和状态，不使用模拟 API 冒充完成。
- 测试：从周期规划开始介入，为该周期任务设计测试；周期末验证一次组合结果和真实入口。
- 运维：负责环境、部署、升级、回滚和可观测性任务。

`workflow.json` 中具有稳定 ID 的 9 个关口是质量门禁：全量需求分析 → 唯一能力归属 → 原子用例与任务 → 依赖和现有代码评估 → 数据库设计 → MyBatis-Plus 生成 `base` → `manage` 业务 → 前端 → 周期集成与真实入口验证。项目还必须在任务和依赖完成后计算从骨架、可用到完整的交付阶段；交付阶段是依赖里程碑，不得伪装成另一套质量门禁。每个开发周期最多 240 分钟，任务按真实预计时间组合，不设置人为最小时长，单项预计超过 240 分钟时必须继续拆分。

周期验收必须执行预先绑定需求来源的页面业务用例，至少写明角色、真实入口、前置数据、逐步操作、页面可见结果、持久化读回以及权限或失败结果。编译成功、模拟 API 或 HTTP 200 都不能单独证明业务完成。

“继续开发”启动的是 `workflow.json.executionLoop` 定义的全项目持续循环，不是只执行一个周期。每个周期结束后写证据、重算状态并汇报进度，随后立即选择下一个依赖已满足的未完成周期；只有工作流列明的停止条件才能结束该循环。

用户验收只能来自用户明确确认。Agent 不得代填或把工程测试解释成用户验收。
