# 开发职责

- 需求与拆分：通读原始资料、用户当前明确补充和唯一最终理解，确认配置归属、生效方式、引用及完整业务关系，再按可验证业务行为拆分；用具体业务例子检查理解，把确认后的关系直接维护到最终文件。
- 数据与生成：设计必要字段及索引、引用和事务约束，维护可执行 SQL；从实际数据库生成对应业务模块的 base。
- 后端业务：复用生成的基础 Service，在 manage 实现真实业务、权限及跨表事务；Controller 保持薄层。
- 前端业务：连接真实接口，按字段和页面配置实现普通用户能操作的配置态与运行态。
- 验证与集成：从用户要求检查本批全部预定业务场景的成功、持久化、无权和失败结果，核对关联对象及配置变化的影响；不能只按实现反推预期或以一个场景通过认可整批。集成后检查完整主流程，在回复中区分规则更新、代码实现和真实运行验证。

职责可以由同一执行者承担。确有独立任务且获得并行授权时再分派：明确每项工作的业务目标、输入、拥有的文件和验收方式；共享迁移、接口依赖及集成由主执行者有序处理。skills 是各职责按需使用的方法，不替代对业务的判断。分工不生成副本需求、中间计划或交接文档。

## 并行任务的共享文件与接口依赖处理

已授权的并行任务需要修改同一文件，或需要另一任务负责的 Service 等提供尚未满足的能力时，按本方案协调。主执行者在当前工作上下文维护文件归属、依赖需求和处理结果，不另建任务栏、调度系统或任务、状态、交接文件；独立且没有共享修改的任务继续按原安排执行。

1. **明确修改归属**：同一批工作中，同一文件由一个执行者统一修改，即使各任务修改不同方法也不同时写入。配套接口、参数及返回类型等文件一并明确归属；主执行者调整归属前，确认原负责方已停止修改并通知相关任务。
2. **提出能力需求**：调用方向负责方和主执行者说明业务用途、输入、返回内容、系统与租户及权限范围、空结果或失败行为、必要的事务约束和验证方式，同时说明哪部分工作受其阻塞。方法名可以作为建议，不能只报一个 `queryByXxx` 就视为需求明确。
3. **评估必要性与复用**：主执行者与负责方先核对现有实现。完全满足时直接复用；业务语义一致且能保持现有正确调用行为时扩展；语义不同或职责不合适时，在适当位置新增方法或调整任务边界；重复或不必要的需求合并或拒绝。不得为减少方法数量混合不同权限、数据范围或业务含义。普通依赖由主执行者和负责方判断，业务歧义、需求冲突或范围扩大时再向用户确认。
4. **负责方统一实现**：双方明确方法签名、业务行为、涉及文件和影响范围后，由负责方统一修改并通知调用方实际实现及验证结果。调用方只修改自己负责的接入代码，不自行改写对方文件、复制业务实现或绕过所属服务来避开等待。
5. **按依赖推进**：调用方可按已明确的接口约定完成不依赖具体实现的工作；依赖未实现时，不把方法约定、空实现或占位返回当作完成。发生相互等待或公共负责方成为瓶颈时，由主执行者优先完成公共前置能力、调整顺序或合并相关任务，避免循环等待。共享数据库迁移、代码生成及共享配置修改仍按依赖串行执行。
6. **完成接入与联调**：负责方完成后，调用方接入实际实现，主执行者组织相关编译、必要测试和真实入口验证，检查成功、持久化、无权、失败结果及已有调用是否受影响。依赖方法完成不代表调用方业务完成，整条调用链验证后才结束该项协作。

例如任务 A 修改 `AService` 时需要 `MService.queryByXxx`，而任务 B 正负责 `MService`，则 A 在当前工作上下文提出能力需求；评估后由 B 复用、扩展或新增合适的方法，A 完成调用接入，最后统一联调。
