# 开发检查

1. 用户原始输入只读；开发方只维护一份最终需求理解，不保存其他版本的解释、计划、评审或验收历史。
2. 动固定业务表前，先合看用户原始需求、只读旧 SQL 的字段关系和用户给定表用途，再用完整业务流程、权限、状态与跨域引用核对当前 SQL、目标库及已有业务代码；不能由单张表名或局部需求倒推结构。优先利用用户给定的主要表骨架，新增表和抽象须有无法在现有结构合理表达的具体业务理由。表名、业务归属与项目定义一致；表和所有字段有中文备注。关联与依赖检查按需求由业务代码实现。
3. 数据库时间列用 `*_time`，Java 属性用 `*Time`；已有数据结构变更有可执行迁移，不直接删表重建。
4. Java 类、方法、业务字段和关键逻辑有中文业务注释，HTTP 接口有可读说明；简单 CRUD 不增加无用层。
5. 整套固定业务表的最终结构落入目标库并核对后才能运行生成器；只生成本批文件也不能绕过全表完整性及备注、时间命名、外键和触发器检查。生成结果直接进入业务模块 base；业务编排在同级 manage，Controller 只调用 Service。
6. 生成的基础 Service 实现 `queryPageList`、`addOrUpdate`、`queryById`、`information`、`deleteByIds`；配置驱动的详情复用保存的行、位置和宽度，不按宽度重新拼行或拉伸。业务字段权限由 manage 校验后传入，基础模板不自行推断角色或租户权限。
7. 编译测试执行相关范围；业务通过实际入口检查持久化、授权和失败结果。局部工程检查不等于整体功能完成；本批结果核对后沿完整业务依赖继续实施，不等用户重复下达“继续”。
8. 固定字段类型与基本校验复用 core；业务 Service 补齐唯一、引用和作用域检查，不能重复维护一套类型判断。权限结果统一约束动作、字段和负责人范围，过滤不重排布局。字典基础项逐条保存，字段 JSON 配置引用稳定基础项 ID；配置缓存按系统、租户及数据库版本隔离，事务提交后失效、故障回源，不能成为授权的唯一依据。
9. 已确认由理解错误产生的数据模型、字段、接口和调用应直接清除，不以兼容为由保留错误结构或平行执行分支。用户明确允许清空的开发数据库按正确最终结构重建；需要保留的真实数据按用户要求处理，清理不得超出授权范围。
10. 设计存储和接口前明确区分基础数据、配置及业务数据，逐项确认谁维护、如何引用和在哪里生效，不能依据旧代码反推需求。用户纠正业务模型时，原位更新唯一最终理解，检查数据库、生成器、Service、接口、缓存和验证用例中的相关假设，清除同源错误；使用用户给出的具体业务例子验证修正结果，不能只改术语或以编译通过代替理解正确。
