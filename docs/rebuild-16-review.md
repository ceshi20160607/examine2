# 第 16 次重构的依据核对

本文件从用户提供的旧对话汇总提炼**反复确认、且未被后续消息撤销**的方向。原汇总与第 15 次派生文档已移出活动工程；以后实现只以 `docs/user_requirement.md` 和 `docs/表意义.md` 为产品依据。

## 用户已确认

- 目标是整个可用产品：平台建立业务系统与租户，租户内可配置模块、表单、场景、流程与审批，并提供工作、数据展示、打印和应用接入。不能把一个接口编译成功当成整体进度。
- 按用户给定的 94 张原名表及用途建模型，字段不足时根据业务补齐；早期 SQL 只供研究。先完成后端全部基础接口，经用户验收后开发一个前端。后端固定 9999，使用本机 MySQL/Redis。
- 业务模块统一 `examine-*`；平台是 `examine-plat`，系统租户是 `examine-sys`，数据展示是 `examine-dashboard`，唯一服务入口是 `examine-web`。`base` 与 `manage` 平级；前者由生成器提供基础 CRUD，后者处理特殊逻辑。不要堆出 `foundation`/`identity` 等聚合层。
- 提交 `70a3979a` 的 Controller → Service 调用及 `simple` 五方法模板是分层参考。生成器应直接产出可用基础 CRUD；Controller 不能承担分页 SQL、保存、详情和删除的实现。接口要有可读的 `@Tag`、`@Operation` 与中文业务注释。
- 不过度封装，不复用此前反复重构产生的旧业务代码、旧接口结论或旧测试数据。

## 第 15 次偏差及本次纠正

- 之前生成了大量空 `IService/ServiceImpl`，只把 Controller 的 Mapper 调用改成 MyBatis-Plus 的 `save/page/getById`；业务查询和判断仍在 Controller。该做法只是换了调用对象，不是参考提交的分层。
- 后补的模板只有四个方法，缺少带字段布局的 `information`；并且当时没有从数据库重新生成所有基础服务。将“生成器可编译”描述为 CRUD 已纠正是错误的。
- 第 15 次的验收记录不能证明本次代码有效，前端也未进入用户可验收状态。因此本轮状态从零记录，旧库 `unexamine_r15` 不作为第 16 次验收证据。
- 第 16 次已把旧后端、派生接口文档和旧生成器移出活动目录；新生成器的五方法合同与样表生成编译单独验证。真实业务数据、授权和 HTTP 仍须按新库逐批验收。

## 已确认的详情布局

用户已明确：`queryById` 只查基础数据；`information` 要按模块自定义字段创建时设置的宽度和顺序展示，例如宽度 50% 的两个字段处在同一行。生成模板已接受布局及扩展值输入并计算行内位置；模块业务 Service 仍需从模块字段配置表和记录扩展值表实际读取这些输入，不能拿默认布局冒充真实模块布局。
