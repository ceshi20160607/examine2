# unexamine 全量重构产品方案

> 这是最终版综合方案。它以现有项目能看到的功能为参照，但不被旧代码限制。
> 重点是：完整产品应该包含哪些功能，现有功能应该如何升级，界面应该如何用更现代的方式呈现，系统如何更健壮、更好扩展。

## 1. 方案定位

unexamine 要做成一个“可配置业务系统平台”。

它要覆盖日常小型和中型内部系统的大多数需求：

- 搭业务表。
- 搭表单。
- 搭列表。
- 搭详情。
- 搭审批。
- 搭仪表盘。
- 分权限。
- 管成员。
- 上传附件。
- 导出数据。
- 外部系统接入。
- 查看日志。
- 稳定部署上线。

它不是单纯的“低代码演示项目”，也不是开发人员自己调接口的后台，而是一个普通企业团队可以长期使用的产品。

## 2. 总体目标

### 2.1 产品目标

- 管理员可以搭建一个业务应用。
- 普通用户可以顺手使用这个应用。
- 外部系统可以安全接入这个应用。
- 项目可以稳定部署、升级、维护。

### 2.2 覆盖范围

这套产品要能支撑：

- 客户管理。
- 合同管理。
- 订单管理。
- 项目管理。
- 任务管理。
- 报销审批。
- 请假审批。
- 采购申请。
- 资产管理。
- 工单处理。
- 设备巡检。
- 内部台账。
- 简单 CRM。
- 简单 OA。
- 简单进销存。
- 轻量 ERP 子场景。
- 轻量 MES 子场景。
- 简单售后系统。

说明：

- ERP 和 MES 不单独做重型行业套件。
- 通过模块、字段、子表、流程、规则、KPI、打印模板、仪表盘等能力，组合出轻量 ERP 和轻量 MES 场景。
- 例如采购、销售、库存台账、生产工单、质检记录、设备巡检，都可以作为普通模块配置出来。

### 2.3 核心判断标准

一个不会写代码的管理员，应该可以完成：

1. 创建一个系统。
2. 创建一个**模块组**（运行态顶栏导航分组）。
3. 在模块组下创建业务模块。
4. 配置字段。
5. 配置页面动作（含导出）。
6. 配置菜单与发布。
7. 配置角色权限。
8. 配置审批流程。
9. （可选）配置**对外应用**入口。
10. 邀请用户使用。
11. 导出数据或开放接口。

> **v2 澄清（2026-06-15）：** 建模主链是「模块组 → 模块」，不是「应用 → 模块」。应用用于**本系统对外访问入口**，见附录 A。

普通用户应该可以完成：

1. 登录。
2. 进入自己有权限的系统。
3. 打开业务菜单。
4. 新增和编辑数据。
5. 查询和筛选数据。
6. 查看详情。
7. 上传附件。
8. 处理审批。
9. 查看消息。
10. 导出自己有权限的数据。

## 3. 现有功能应该如何看待

现有项目已经有不少后端能力，这些能力不能浪费。

可以保留或参考：

- 平台登录。
- 系统和租户。
- 应用。
- 模块。
- 字段。
- 字典。
- 部门。
- 页面。
- 菜单。
- 角色权限。
- 数据记录。
- 记录历史。
- 字段关联模块和子表。
- 流程模板。
- 流程运行。
- 待办和抄送。
- 上传。
- 导出。
- OpenAPI。
- 数据库迁移。
- 启动和部署脚本。

但现有项目的问题也很明显：

- 页面散，不像产品。
- 配置态和使用态混在一起。
- 很多页面像接口测试页面。
- 中文显示和编码存在问题。
- 权限体验不完整。
- 流程设计不够产品化。
- 表单设计不够直观。
- 数据详情不够友好。
- 部署配置和密钥检查还不够稳定。

所以重构时不是“照着旧代码重写一遍”，而是：

- 用现有功能确认业务范围。
- 用现有表和接口确认已有积累。
- 用新的产品结构重新组织功能。
- 用新的页面和交互重新设计体验。
- 用更清楚的后端业务接口重新收敛能力。

## 4. 产品整体结构

产品分成五个大的区域。

## 4.1 平台层和自定义系统层

成熟项目必须先分清两个层级：

- 平台层。
- 自定义系统层。

平台层是产品本身的管理层，负责管理所有系统、账号、授权、部署和全局运维。

自定义系统层是用户创建出来的业务系统，负责这个系统内部的模块、字段、页面、流程、权限、数据和业务设置。

两者不能混在一起。

### 平台层负责什么

平台层负责：

- 平台账号。
- 平台管理员。
- 平台角色。
- 平台菜单。
- 系统创建。
- 系统启用、停用、删除。
- 租户管理。
- 平台级授权。
- OpenAPI 全局策略。
- 全局密钥和安全配置。
- 全局文件存储配置。
- 全局日志。
- 系统健康检查。
- 版本信息。
- 部署信息。
- 数据库脚本版本。

平台层不直接管理某个业务模块里的业务数据。

### 自定义系统层负责什么

自定义系统层负责：

- 当前系统内用户。
- 当前系统内部门。
- 当前系统内角色。
- 当前系统内权限。
- 系统基础信息。
- 系统登录入口。
- 系统参数。
- 系统功能开关。
- 系统待办。
- 系统消息。
- 登录日志。
- 业务日志。
- 应用。
- 模块。
- 字段。
- 页面。
- 菜单。
- 字典。
- 流程。
- 打印模板。
- KPI 目标。
- 自定义仪表盘。
- 模块数据。
- 附件。
- 模块数据导入导出。
- 系统内消息。
- 系统内登录日志。
- 系统内业务日志。
- 系统内 OpenAPI 授权。

自定义系统层只能管理当前系统自己的配置和数据。

### 层级边界

边界规则：

- 平台层创建和管理系统。
- 自定义系统层配置和使用业务。
- 平台账号可以进入多个自定义系统。
- 多系统进入统一通过顶部“系统切换”入口完成；个人信息里不再放“授权系统/进入系统”入口，避免和系统切换重复。
- 普通系统用户可以通过系统域名、系统编码或专属路径直接登录某个自定义系统。
- 一个自定义系统有自己的用户、部门、角色、权限、模块和数据。
- 自定义系统之间数据隔离。
- 平台管理员可以做平台运维，但不能绕过业务规则随意改业务数据，除非有明确的运维授权。
- 自定义系统管理员不能管理平台全局配置。

### 菜单划分

平台层菜单：

- 我的系统。
- 系统管理。
- 租户管理。
- 平台账号。

平台层权限：

- 管理租户。
- 管理平台账号。
- 管理平台角色。
- 查看平台日志。
- 管理全局配置。
- 查看系统健康。

自定义系统层权限：

- 管理**模块组**（v2）。
- 管理模块。
- 管理字段。
- 管理页面。
- 管理菜单。
- 管理**对外应用**（v2：本系统对外入口，见附录 A.2）。
- 管理系统内用户。
- 管理系统内部门。
- 管理系统内角色。
- 管理流程。
- 管理打印模板。
- 管理 KPI。
- 管理仪表盘。
- 管理 OpenAPI。
- 查看、新增、编辑、删除、导入、导出模块数据。

### 数据隔离

所有业务数据都必须带：

- systemId。
- tenantId。
- moduleId。

模块组仅用于运行态导航和发布关系，不作为业务数据父级；对外应用仅用于 OpenAPI 调用来源和审计来源，不作为业务数据父级。

平台数据和业务数据分开。

自定义系统 A 不能查到自定义系统 B 的数据。

同一个系统内，如果启用租户，也要按租户隔离。

### 页面入口

平台管理员和系统拥有者登录后进入平台层的“我的系统”。

选择一个系统后，进入自定义系统层。

普通系统用户通过系统域名、系统编码或专属路径登录后，直接进入该系统的运行台或默认首页。

在自定义系统层里，用户可以进入：

- 管理设置。
- 应用配置。
- 应用运行台。
- 流程工作台。

这个入口关系必须清楚，不能让用户在平台层和业务层之间迷路。

## 5. 全量功能清单

## 5.1 账号和登录

必须包含：

- 登录。
- 注册。
- 退出登录。
- 刷新登录状态。
- 修改密码。
- 重置密码。
- 当前用户信息。
- 登录日志。
- 登录失败限制。
- token 过期自动刷新。
- 登录、注册并创建系统、找回/重置密码必须有真实页面流程，不只是原型抽屉或演示按钮。
- 注册创建系统后，创建人成为该系统超级管理员并进入系统后台配置引导。
- 企业 SSO 必须有平台级统一认证配置，不只是登录页按钮或接口占位。
- 平台级身份源配置至少包含 OIDC、SAML 2.0、OAuth2、LDAP / AD、企业微信 / 钉钉、回调地址、证书/JWKS、域名白名单、属性映射、JIT、MFA、测试发布和登录审计。
- 系统后台必须有一级统一认证配置页，继承平台已发布身份源，配置可用身份源范围、租户域名限制、组织部门映射、员工绑定、系统成员映射、JIT 系统成员策略、无成员映射反馈和申请授权入口。
- 系统 SSO 配置必须和组织架构联动：外部部门映射系统部门树，externalUserId/email/mobile/employeeNo 绑定平台账号、系统员工和 systemMemberId；未匹配部门、未绑定员工必须有预检、草稿、人工确认、同步任务和登录日志 traceId。
- SSO 登录日志必须记录 identityProvider、externalUserId、账号绑定结果、系统成员映射结果、认证方式、MFA、IP、设备、requestId、traceId 和失败原因。

优化：

- 支持验证码或短信验证，按部署需要开启。
- 支持单点登录接口，并按企业身份源配置、系统继承和成员映射完整落地。
- 支持账号停用。
- 支持强制下线。

- 节点可以配置退回到发起人、退回到上一节点、退回到指定节点、重新提交后从头走或回到退回节点。
- 节点可以配置代理审批、委托、候选人领取、会签比例、会签顺序、审批意见必填、附件必填。
- 节点可以配置业务表单快照、节点内可编辑字段、节点完成后字段回写。

流程触发：

- 流程要绑定模块和事件点。
- 支持新建触发。
- 支持编辑触发。
- 支持删除前或删除后触发。
- 支持状态变化触发。
- 支持手动点击发起。
- 支持 OpenAPI 发起。
- 每个触发点可以配置条件，比如金额大于 5000 才走审批。
- 一个模块可以绑定多个流程，但同一个事件点要配置优先级和互斥规则，避免重复发起。
- 支持周期触发、外部应用触发、OpenAPI 触发、导入完成触发、数据异常触发。
- 支持办公流场景：请假、报销、采购、用印、合同审批、资产领用、工单派发、任务协作、跨部门会签。
- 流程能力目标是覆盖企业级工作流、审批流、办公流的大多数常见场景，不做只能跑单一审批链路的简版。

流程运行数据：

- 流程模板保存基础信息和启用停用状态。
- 流程版本保存发布快照，草稿修改不能影响已发布版本。
- 流程高级设置保存撤回、拒绝、重审、超时、异常兜底、是否允许加签加节点等规则。
- 流程节点保存节点类型、审批方式、审批人来源、外部节点配置、子流程配置。
- 流程连线和连线条件保存条件分支。
- 流程实例保存某条模块数据正在走哪一个流程模板版本。
- 流程实例创建时，要把模板版本的节点、连线、条件、字段权限和高级设置复制成运行快照。
- 流程任务保存当前待办、候选人、处理状态和处理意见。
- 流程提交快照保存节点内字段修改，支持审批过程中修改字段。
- 流程日志保存每一次节点进入、审批、拒绝、转办、加签、加节点、撤回、终止。
- 流程运行时必须使用发布版本快照，流程修改不能影响已发起实例。

模块事件触发流程：

- 模块数据新建、编辑、删除、状态变化时，由模块业务层产生事件。
- 根据系统、模块、事件点查询流程绑定。
- 按优先级判断绑定条件。
- 满足条件后读取启用的流程模板和最新发布版本。
- 创建流程实例并复制版本快照。
- 回写模块数据的审批状态和当前流程实例 ID。
- 如果绑定是互斥的，命中第一个流程后停止继续匹配。

手动增加节点：

- 流程运行中支持管理员或有权限的人手动增加审批节点、抄送节点。
- 手动节点要记录添加人、添加原因、插入位置、节点配置快照。
- 手动节点可以插在当前节点后，也可以插在指定节点前后。
- 手动节点不能破坏已完成节点的历史记录。

运行能力：

- 发起流程。
- 待办。
- 抄送。
- 我的申请。
- 实例详情。
- 同意。
- 拒绝。
- 转办。
- 领取。
- 取消领取。
- 撤回。
- 终止。
- 加签。
- 减签。
- 催办。
- 评论。

优化：

- 流程设计器用画布加右侧配置。
- 创建流程时选择系统内一个模块，审批、业务详情、流程状态都围绕这个模块的数据展开。
- 发布前检查是否有断线、死路、空审批人。
- 审批页面同时展示业务数据、流程图、历史、操作区。
- 拒绝、撤回、终止必须填写原因。
- 子流程不能卡住父流程。
- 流程状态变化要写日志。
- 流程设计要有流程列表、审批类型、流程版本、节点库、画布、属性面板、模拟运行、发布检查、错误定位、影响分析和回滚。
- 流程运行要能解释当前为什么走到这个节点、谁有权处理、哪些字段可见/可改、超时后怎么处理。

## 5.14 模块数据导入导出

理解：

导入导出是模块内的数据功能，不是独立中心。每个模块可以按自己定义的字段配置导入和导出。

导入场景：

- 客户模块导入历史客户数据。
- 合同模块导入历史合同数据。
- 资产模块导入盘点结果。
- 商品模块导入供应商商品清单。
- 模块数据需要批量更新时，通过导入按唯一字段匹配更新。

导出场景：

- 在客户模块导出当前筛选的客户。
- 在合同模块导出合同和回款数据做对账。
- 在资产模块导出资产台账。
- 在工单模块导出处理记录。
- 在审批模块导出审批记录做审计。

导出必须包含：

- 列表导出。
- 当前筛选导出。
- 按模块字段配置导出列。
- 异步任务。
- 任务状态。
- 下载结果。
- 失败原因。

导入包含：

- Excel 导入。
- 导入模板下载。
- 按模块自定义字段配置导入列。
- 导入预检查。
- 错误行下载。
- 导入历史。

优化：

- 大数据量导出异步处理。
- 导出权限独立控制。
- 导入失败不能污染数据。
- 导入前先预检查，告诉用户哪些行会成功、哪些行有问题。
- 导入支持新增和更新两种模式，避免重复造数据。
- 导入错误要能下载错误行和错误原因。
- 导入配置只读取当前模块允许写入的字段，系统字段、审计字段、自动编号字段不能被外部覆盖。
- 导出配置可以选择显示关联字段的展示值，而不是只导出 ID。

## 5.18 系统管理设置

理解：

系统管理设置是每个自定义系统内部的基础配置区，用于维护这个系统运行时必须配置的基础资料和业务设置。

必须包含：

- 系统内用户。
- 系统内部门。
- 系统内角色和权限。
- 审批配置。
- 字典配置。
- 打印模板。
- 打印预览。
- 模块导入导出配置。
- KPI 目标。
- 消息设置。
- 编号规则。
- 基础参数。

打印模板场景：

- 合同模块打印合同。
- 报销模块打印报销单。
- 采购模块打印采购申请单。
- 订单模块打印订单或出库单。
- 工单模块打印维修单或处理单。

打印模板配置：

- 模板归属某个模块。
- 模板使用模块内字段。
- 模板可以使用关联字段的展示值。
- 模板可以配置页眉、页脚、签章区、明细表格。
- 模板支持打印预览。
- 模板支持下载或导出 PDF。

KPI 目标场景：

- 销售模块设置销售目标。
- 项目模块设置交付目标。
- 工单模块设置处理时效目标。
- 客服模块设置满意度目标。

优化：

- 系统管理设置放在自定义系统内，不放到平台全局。
- 用户、部门、审批、字典、打印模板、KPI 目标都按当前系统隔离。
- 打印模板和模块绑定，避免模板不知道读取哪些字段。
- 打印预览要在正式打印前展示效果。
- KPI 目标可以和模块数据统计关联。

## 5.19 智能能力

智能能力作为正式扩展能力纳入架构，所有动作都受权限、审计和人工确认控制。

包含：

- 用一句话生成模块字段。
- 根据模块自动生成页面。
- 根据业务描述生成流程草稿。
- 智能解释错误原因。
- 智能生成打印模板和导出字段配置。
- 智能查询数据。
- 智能总结审批记录。
- 平台级 AI Agent 配置。
- 系统级 AI Agent 授权和配置。
- 通过 AI Agent 对话解析用户意图，并在权限范围内写入对应系统、模块、字段和子表。
- 通过 AI Agent 对话查询权限范围内的数据、统计、趋势、待办和业务摘要。

平台级 AI Agent：

- 平台后台提供 AI Agent 配置入口。
- 平台可以配置本地模型，也可以配置外部模型服务。
- 平台可以购买或开通模型授权，再分配给具体系统使用。
- 平台配置模型供应商、模型、API 地址、密钥、调用额度、并发限制、日志脱敏、数据出境策略。
- 平台可以配置默认 Agent 能力：对话理解、数据查询、数据录入、流程草稿、报表分析、错误解释。
- 平台级 Agent 默认不能绕过系统权限访问业务数据。
- 平台工作台运行态 Agent 只处理平台授权、平台日志、平台任务、模型额度、系统健康和系统切换引导；不能直接打开或写入系统业务模块。需要处理系统业务数据时，必须先通过系统切换进入目标系统，并取得系统成员、系统角色、字段权限和数据范围后，由系统 Agent 处理。

系统级 AI Agent：

- 系统可以使用平台购买授权的模型能力。
- 系统也可以在权限允许时配置外部第三方模型。
- 系统管理员配置 Agent 可访问的模块、字段、动作、数据范围和确认策略。
- 系统 Agent 录入数据前必须展示解析结果，用户确认后才保存。
- 系统 Agent 查询数据时必须按当前用户的系统角色、数据范围、字段权限和脱敏规则返回。
- Agent 的所有写入、查询、失败、人工确认、模型调用都要进入系统业务日志或平台日志。

AI Agent 运行入口：

- 平台工作台可以有平台 Agent，用于查询授权系统、平台日志、平台任务、模型额度、系统健康、平台 Flow。
- 平台 Agent 的写入确认只允许生成平台任务、平台消息和平台日志，不能复用系统业务写入确认，也不能携带系统业务模块写入 payload。
- 平台 Agent 涉及业务系统数据时，必须先引导用户通过系统切换进入对应系统，获得系统成员、系统角色、字段权限和数据范围后，再由系统 Agent 或业务页面处理。
- 系统运行态可以有系统 Agent，用于查询权限内业务数据、统计、待办、消息、工作任务和日报。
- 系统后台可以有配置 Agent，用于辅助生成模块字段、流程草稿、字段权限建议、字典项和筛选场景。
- 业务详情中可以出现上下文 Agent，用于总结当前数据、审批记录、附件、操作日志和下一步动作。
- 工作管理中可以出现工作 Agent，用于从消息、待办、会议纪要、聊天内容中提取任务，生成日报草稿，总结项目进度。

AI Agent 对话录入规则：

- Agent 解析用户对话后，必须展示结构化识别结果。
- 结构化结果要明确目标系统、目标模块、字段映射、关联对象、附件、负责人、截止时间、标签和置信度。
- 用户确认前不能直接写入业务数据。
- 低置信度字段必须要求用户补充或选择。
- Agent 写入后的数据要能回到原始对话、确认人、模型、提示词版本和日志。
- Agent 不能绕过必填校验、唯一校验、流程前置条件和角色权限。

AI Agent 查询规则：

- 用户可以通过对话查询统计、列表、趋势、待办、任务、日报、项目进度。
- 查询结果必须受当前用户权限、字段权限、数据范围和脱敏规则限制。
- 返回结果要说明口径，例如统计范围、时间范围、系统、租户、模块和筛选条件。
- 涉及导出、批量修改、发起流程等动作时必须二次确认。

AI Agent 配置和审计：

- 平台配置模型供应商、模型、调用额度、并发、脱敏、数据出境策略和授权系统。
- 系统配置 Agent 可访问模块、字段、动作、确认策略、失败降级、日志保留。
- 每次 Agent 查询、生成、写入、失败、人工确认都要记录审计日志。
- 外部模型不可用时要有降级策略，例如停用智能写入、只保留模板化查询或提示稍后重试。

设计落地顺序：

- AI Agent 必须建立在平台/系统/字段/流程/权限/日志等基础能力之上。
- 当前设计阶段要先把 AI Agent 的配置入口、运行入口、权限边界、人工确认、审计日志、失败降级和工作管理联动画出来。
- 具体模型接入、提示词编排和复杂自动化执行可以在基础能力确认后细化，但不能缺少产品入口和开发边界。

注意：

- 智能能力不能替代权限。
- 智能生成的东西必须让管理员确认后保存。
- 不能把敏感数据随便发送到外部服务。
- 外部模型调用必须有开关、脱敏、授权、审计和失败降级。

## 5.20 工作管理（项目、任务、日报、日历）

工作管理把“任务管理”和“日报管理”整合为一套工作协作能力，而不是两个孤立菜单。它服务于老板给员工派任务、员工每日记录工作、团队围绕项目协作、领导查看完成度和过程记录。

理解：

- 公司可以有项目，也可以没有项目。
- 项目下可以拆任务组、任务和子任务。
- 日常工作可以直接创建任务，不一定属于某个项目。
- 员工每天可以写日报，日报可以引用已完成任务、进行中任务、待办、业务对象、日志和附件。
- 任务、日报、日历、消息、待办、AI Agent 之间要能联动。
- 工作模块建议按主流协作产品拆成四个主标签：仪表盘、项目任务、普通任务、日报。
- 仪表盘负责项目进度、今日预警、完整月历和统计概览；项目/今日预警与月历采用上下布局，让预警和日历都能完整阅读。
- 项目任务页专门处理项目下任务。项目任务通过按钮在列表和看板之间切换，二者互斥显示；列表有分页，看板无分页，通过向下滚动自动加载更多数据；看板列、泳道或分组来自工作配置里已发布的下拉单选或多选字段。
- 普通任务可以只有一行描述，也可以后续补关联项目、任务组、业务对象、标签和截止时间；普通任务也支持列表和看板按钮切换，列表有分页，看板滚动加载。
- 日报页只展示我的日报列表，并提供日期、状态、项目、关键词等筛选项；手动填写日报和自动生成今日日报草稿作为操作入口。
- “待写入日报的工作记录”只是从完成任务、处理过的待办、消息和业务日志中整理出的日报草稿素材，不是新任务列表。
- 工作配置必须作为系统后台一级页面，不显示统计卡片，不直接配置状态/标签选项；主要配置项目任务字段列表、普通任务字段列表、日报字段列表、字段属性、字段权限、卡片字段、看板取数字段、发布检查和回滚。

工作管理必须包含：

- 我的工作台。
- 工作仪表盘。
- 项目列表。
- 项目详情。
- 任务组。
- 项目任务列表。
- 项目任务看板。
- 项目任务日历。
- 普通任务。
- 普通任务列表。
- 日报列表。
- 日报筛选。
- 日报填写。
- 日报详情。
- 工作统计。
- 标签管理。
- 任务模板。
- 日报模板。
- 权限配置。
- 字段配置。
- 数据字典配置。
- 看板配置。

项目：

- 项目名称。
- 项目编号。
- 客户或内部部门。
- 项目负责人。
- 项目成员。
- 项目阶段。
- 开始日期。
- 截止日期。
- 项目状态。
- 项目进度。
- 项目标签。
- 项目关联的系统、租户、模块或业务对象。
- 项目下任务组、任务、日报、附件、评论和日志。

任务组：

- 任务组用于把项目下的任务分组，例如需求确认、设计、开发、测试、上线。
- 任务组可以设置负责人、截止时间、排序、状态和完成度。
- 任务组完成度由组内任务加权或数量统计得出。

任务：

- 创建任务。
- 支持普通任务：只有一行描述也可以创建，后续可补项目、任务组、协作人、截止时间、业务对象。
- 支持项目任务：必须归属项目或任务组，可以参与项目进度、项目预警和项目日报统计。
- 编辑任务。
- 删除或归档任务。
- 指派任务。
- 分配任务给个人、多人、部门、角色或任务组。
- 设置负责人、协作人、关注人、验收人。
- 设置优先级、截止时间、预计工时、实际工时。
- 设置任务标签。
- 设置任务所属项目、任务组、系统、租户、模块和业务对象。
- 支持任务描述、附件、评论、进度记录、完成说明。
- 支持任务回复和评论，评论可以 @成员、引用附件、引用业务对象。
- 支持子任务或检查清单。
- 支持多人协作。
- 支持任务转交、延期申请、完成确认、重新打开。
- 支持任务提醒、逾期提醒和消息通知。
- 支持任务完成时间、实际完成时间、验收时间和逾期原因记录。
- 支持预警规则：临近截止、逾期、阻塞、无人负责、日报未同步。
- 支持任务状态：未开始、进行中、阻塞、待确认、已完成、已取消、已逾期。
- 支持任务完成度：0%、25%、50%、75%、100%，也可以按子任务自动计算。
- 任务列表、任务看板、任务日历是同一批任务的不同视图，不能重复成多套任务数据。
- 项目任务字段列表、普通任务字段列表、日报字段列表、字段权限、卡片字段、看板取数字段和发布回滚，都必须可以在后台“工作配置”中配置和发布。
- 状态、标签、类型等选项类字段通过数据字典维护；字典项包含颜色、图标、语义、排序、默认项、启停和引用影响。
- 看板可以按工作配置中选择的下拉单选字段生成列，也可以按下拉或多选字段生成泳道/分组；颜色和图标来自字段绑定的数据字典。

日报：

- 手动填写日报。
- 从今日完成任务生成日报草稿。
- 从待办、消息、日志、业务详情生成日报草稿。
- 日报页默认只展示我的最近日报列表，包括草稿、已提交、已撤回、补写记录，并提供日期、状态、项目、关键词等筛选项。
- 手动填写日报和自动生成今日日报草稿作为操作入口；当天完成任务、处理中任务、已处理待办、消息和业务日志整理出的候选内容，应在写日报抽屉或详情中确认，不在日报列表页常驻铺开。
- 团队日报统计或提交情况属于管理/统计视角，不替代“我的日报”主线。
- “待写入日报的工作记录”用于让用户确认哪些工作记录要进入日报，不能叫得像另一个任务列表。
- 日报包含今日完成、进行中、明日计划、问题风险、需要协助、关联任务、关联项目。
- 支持日报草稿、提交、撤回、补写、评论和反馈。
- 支持日报模板配置。
- 支持日报可见范围：仅自己、上级、项目成员、团队、指定角色。
- 支持日报和任务双向关联。
- 支持领导查看团队成员日报，按权限查看。

日历：

- 日历展示任务截止日期、任务完成情况、日报填写情况、项目里程碑、会议或提醒。
- 日历按日、周、月切换。
- 日历上可以快速新建任务、补写日报、查看某日工作记录。
- 日历上要展示完成度、逾期、今日需处理、多人协作任务。

统计：

- 按人统计任务数量、完成数量、逾期数量、进行中数量。
- 按项目统计完成度、任务分布、风险任务、延期任务。
- 按标签统计任务类型。
- 按日期统计日报提交情况、任务完成趋势。
- 支持老板查看团队工作概览，员工查看个人工作概览。

权限：

- 老板或管理者可以派发任务、查看团队任务、查看授权范围内日报和统计。
- 员工可以查看和维护自己负责或参与的任务。
- 项目负责人可以维护项目、任务组、项目任务和项目日报。
- 日报可见范围受角色、组织、项目成员和系统权限控制。
- 任务关联业务对象时，跳转和展示字段仍受对应系统的数据权限和字段权限控制。

AI Agent 联动：

- Agent 可以从聊天内容、会议纪要、消息、待办中识别任务。
- Agent 可以根据今日完成任务生成日报草稿。
- Agent 可以总结项目进度、风险任务、逾期原因和人员工作量。
- Agent 生成任务或日报前必须让用户确认。
- Agent 查询工作统计必须受角色和数据权限限制。

平台级与系统级：

- 平台工作台可以有平台级工作管理，用于平台运营、部署、授权、客户支持、配置变更等工作。
- 系统运行态可以有系统级工作管理，用于业务团队围绕具体系统、模块、项目和业务对象协作。
- 两者共享同一套工作管理模型，但数据范围、权限、日志和关联对象按平台/系统隔离。

## 6. 界面和交互方案

## 6.1 总体风格

推荐做成现代企业级后台，而不是传统老后台。

特点：

- 清爽。
- 密度适中。
- 操作路径短。
- 表格能力强。
- 表单清楚。
- 配置可视化。
- 移动端简单直接。

不要做：

- 大面积渐变装饰。
- 花哨但不实用的首页。
- 每个功能都塞卡片。
- 让用户看大量 JSON。
- 让用户记大量 ID。

状态颜色：

- 全系统状态颜色要统一，不能每个页面随意用色。
- 灰色表示草稿、待处理、未开始、待提交等低强调状态。
- 蓝色表示处理中、当前系统、当前节点、审批中等推进中状态。
- 橙色表示待确认、待验收、临期、待续期、低置信度等需要关注状态。
- 绿色表示完成、通过、成功、有效、健康等正向结果。
- 红色表示失败、拒绝、驳回、逾期、停用、暂停等异常或阻断状态。
- 项目标签、普通任务标签可以自定义颜色，但不能覆盖核心状态颜色语义。

## 6.2 Web 主布局

布局规则：

- 左侧主导航。
- 顶部系统和应用切换。
- 顶部消息入口。
- 顶部用户入口。
- 中间工作区。
- 右侧抽屉用于详情或配置。

运行台：

- 左侧显示业务菜单。
- 顶部显示当前应用。
- 内容区显示列表、表单、详情。

配置台：

- 左侧显示配置菜单。
- 顶部显示应用配置状态。
- 内容区显示设计器和设置页。

## 6.3 首页

平台首页：

- 我的系统。
- 我的待办。
- 最近访问。
- 系统消息。

系统首页：

- 应用列表。
- 待办统计。
- 数据统计。
- 最近操作。

应用首页：

- 管理入口。
- 运行入口。
- 模块数。
- 页面数。
- 流程数。
- 成员数。
- 最近数据。

## 6.4 列表页

高级表格体验：

- 顶部搜索。
- 高级筛选抽屉。
- 列设置。
- 保存视图。
- 固定列。
- 批量选择。
- 行内操作。
- 右侧详情预览。
- 快捷导出。

通用行点击规则：

- 所有列表型页面的数据行都必须支持点击整行查看详情。
- 行点击默认从右侧详情抽屉打开，保留列表上下文；复杂详情可以采用右侧工作区或整页详情。
- 行内按钮只承载编辑、删除、转移、审批、导出等不同于“查看详情”的动作，不能和行点击重复。
- 点击复选框、按钮、链接、输入框、下拉框时不得误触发行详情。

高级体验：

- 点击一行右侧打开详情抽屉，复杂详情使用整页。
- 常用筛选保存为视图。
- 支持键盘快速切换行。
- 支持列显示隐藏。

表单规则：

## 7. 技术方案

## 7.1 前端技术

推荐：

- Vue 3。
- TypeScript。
- Vite。
- Pinia。
- Vue Router。
- Ant Design Vue、Naive UI、Element Plus 或 Arco Design Vue 选一种作为基础 UI。
- TanStack Table 或 AG Grid 做高级表格。
- Vue Flow 做流程设计器。
- ECharts 做统计图。
- Monaco Editor 做高级 JSON 或表达式编辑。

技术选型：

- 如果要快速做企业后台，优先 Ant Design Vue 或 Element Plus。
- 如果要主题更灵活，优先 Naive UI。
- 如果要设计更年轻一些，可以考虑 Arco Design Vue。
- 如果表格要非常强，考虑 AG Grid。
- 如果想完全掌控表格样式，考虑 TanStack Table。
- 流程设计器使用 Vue Flow 这类成熟画布库，不从零手写画布底层。

## 7.2 后端技术

推荐：

- Java 21。
- Spring Boot。
- 自研认证和权限拦截，不使用 Spring Security。
- MyBatis-Plus。
- MySQL。
- Redis。
- Flyway。
- MinIO 或 S3 兼容对象存储。
- 后台作业和轻量事件使用 Redis 实现，不使用 Quartz，不使用消息队列。
- OpenAPI 文档。

数据库规则：

- 当前数据库使用 MySQL。
- SQL 尽量使用标准 SQL，减少数据库私有语法，保证数据库切换成本可控。
- MySQL 特有能力可以用，但必须控制范围，比如分页、JSON、索引等。
- 特殊 SQL 统一写在 mapper xml 中，便于替换和维护。
- 业务接口不要依赖数据库方言太深。

## 7.3 架构方式

后端按功能分清楚：

- 平台。
- 应用。
- 模块。
- 字段。
- 页面。
- 权限。
- 数据。
- 流程。
- 文件。
- 导出。
- OpenAPI。
- 日志。

代码结构分两部分：

第一部分是基础生成代码：

- 放在 `base` 包。
- `base.entity` 保存表字段。
- `base.mapper` 处理基础 SQL。
- `base.mapper.xml` 保存基础 SQL 和允许存在的特殊 SQL。
- `base.service` 保存基础增删改查。
- `base.controller` 可以由工具生成，但新版前端不直接依赖这些散接口。

第二部分是业务开发代码：

- 放在 `manage` 包。
- `manage.controller` 只提供产品需要的业务接口。
- `manage.service` 处理产品业务逻辑和核心业务编排。
- `manage.validator` 做保存前校验。
- `manage.permission` 做权限判断。
- `manage.event` 承载事件扩展点。

命名规则：

- 基础生成代码统一放在 `base`。
- 业务开发代码统一放在 `manage`。
- 如果某类业务特别复杂，可以在 `manage` 下再拆 `domain`、`validator`、`permission`、`event`。
- 业务 controller 和业务 service 都放在 `manage`，不要和生成代码混在一起。

规则：

- 基础代码可以由工具生成。
- 业务逻辑不要写进 `base.controller`。
- 复杂业务不要塞进一个大 service。
- 特殊 SQL 可以写在 `base.mapper.xml` 中，这是允许的特例。
- `manage.service` 可以调用多个 `base.service`、`base.mapper`、`manage.permission`、`manage.event`，负责把一个完整业务动作串起来。
- event 采用接口和本地扩展点承载统一事件机制。

## 7.4 数据保存方式

业务数据可以采用“主记录 + 字段值”的方式：

- 主记录保存系统、应用、模块、状态、创建人。
- 字段值保存每个字段的值。
- 常用字段可以有 typed value，方便查询。
- 附件、人员、部门、关联关系单独处理。

优化：

- 列表查询要有索引设计。
- 常用筛选字段要能建索引。
- 自动编号要单独序号表。
- 关联关系要有明确表，不要只塞 JSON。

## 7.5 流程引擎

流程引擎要支持：

- 模板。
- 版本。
- 节点。
- 连线。
- 条件。
- 实例。
- 任务。
- 日志。

关键要求：

- 已发布版本不可直接修改。
- 流程运行使用版本快照。
- 审批操作要事务安全。
- 子流程状态要正确回到父流程。
- 任务不能重复处理。

## 7.6 权限体系

权限必须做到：

- 前端隐藏。
- 后端拦截。
- 数据过滤。
- 字段控制。
- 操作审计。

权限不能只做菜单级。

完整权限至少包含：

- 菜单可见。
- 页面可见。
- 按钮可用。
- 数据范围。
- 字段可见。
- 字段可编辑。
- OpenAPI 可访问。

## 7.7 后台作业

后台作业包括：

- 导出。
- 导入。
- 文件处理。
- 流程通知。
- OpenAPI 异常重试。
- 数据统计。

实现方式：

- 系统只使用 Redis 做后台作业队列、作业锁、作业状态和重试记录。
- 不使用 Quartz。
- 不使用消息队列。
- 不引入复杂任务平台。
- 更多业务扩展统一进入 event 模块。

优化：

- 任务要有状态。
- 任务要有错误原因。
- 任务可以重试。
- 任务不能无限重试。
- 任务结果可下载。

## 7.8 可观测性

必须支持：

- 请求日志。
- 错误日志。
- 操作日志。
- 慢查询日志。
- 后台作业日志。
- OpenAPI 调用日志。

上线要求：

- 每个请求有 requestId。
- 前端错误带 requestId。
- 后端日志带 systemId、tenantId、userId。
- 关键异常写入系统消息。

## 8. 健壮性优化

## 8.1 配置健壮

必须：

- 启动前检查密钥。
- 启动前检查数据库。
- 启动前检查 Redis。
- 启动前检查文件存储。
- 配置缺失要报清楚原因。

## 8.2 数据健壮

必须：

- 业务编码唯一。
- 删除优先软删除。
- 数据保存失败要回滚。
- 文件上传和数据保存要有补偿。
- 导入导出要有任务状态。
- 流程操作防重复。

## 8.3 权限健壮

必须：

- 前端不能作为唯一权限。
- 后端接口必须校验。
- OpenAPI 必须验签。
- 数据范围必须在查询层生效。
- 权限变更要刷新缓存。

## 8.4 流程健壮

必须：

- 流程发布前检查。
- 审批任务只能处理一次。
- 拒绝、撤回、终止必须写原因。
- 子流程结束后父流程继续或结束。
- 异常节点要有处理策略。

## 8.5 部署健壮

必须：

- 部署包名称固定。
- 启停脚本稳定。
- 日志目录固定。
- 配置文件模板清楚。
- 数据库脚本可重复检查。
- 版本号可查看。

## 9. 新技术和超前能力

这些不是花哨功能，而是能明显提升使用体验的能力。

用户按快捷键后可以：

- 搜索菜单。

- 快速新增记录。
- 快速打开待办。
- 快速进入配置页。

## 9.2 右侧智能助手

- 根据描述生成流程草稿。
- 解释错误原因。
- 总结审批历史。
- 生成导出字段配置。

要求：

- 生成内容必须人工确认。
- 敏感数据要脱敏。
- 所有操作受权限控制。

## 9.3 Schema 驱动页面

字段、页面、表单都用统一 schema 描述。

好处：

- Web 和移动端可以共用配置。

## 9.4 高级表格

- 服务端排序。
- 服务端筛选。
- 保存视图。

## 9.5 流程模拟

管理员发布流程前，可以模拟：

- 某个人发起。
- 某个条件命中。
- 流程会走到哪些节点。
- 哪些人会审批。

## 9.6 打印模板可视化设计

打印模板可以做成可视化设计：

- 左侧选择模块字段。
- 中间预览打印页面。
- 右侧配置页眉、页脚、签章区、明细表格。
- 支持打印预览。
- 支持导出 PDF。
- 支持不同模块配置不同打印模板。

## 11. 实施顺序说明

实施顺序用于组织开发，不改变功能范围。

实施顺序：

1. 先做产品骨架。
2. 再做模块字段。
3. 再做数据运行台。
4. 再做权限。
5. 再做流程。
6. 再做文件和导出。
7. 再做 OpenAPI。
8. 再做系统管理设置、打印模板和智能能力。
9. 最后做部署和上线检查。

完整目标始终是全量功能，不是只做第一阶段。

## 12. 关键升级方向

这份方案的关键升级点：

- 不只做基础功能，而是覆盖完整产品能力。
- 不只修补旧页面，而是重做运行台、配置台、流程工作台。
- 不只做菜单权限，而是补齐页面、操作、字段、数据、OpenAPI 权限。
- 不只做记录增删改查，而是补齐字段关联、子表、历史、附件、模块数据导入导出、流程触发。
- 不只做流程数据表，而是做可视化流程设计、发布检查、审批工作台。
- 不只做能启动，而是补齐配置检查、日志、任务状态、部署脚本、版本信息。
- 不只做传统后台，而是加入命令中心、智能助手、Schema 驱动页面、高级表格、流程模拟等更现代的能力。

## 13. 最终效果

最终系统应该做到：

- 管理员搭系统不痛苦。
- 普通用户用系统不迷路。
- 审批人处理待办很顺手。
- 数据权限不会乱。
- 附件、导出、OpenAPI 都能稳定用。
- 页面像一个现代产品，不像临时后台。
- 后端接口清楚，功能边界清楚。
- 新增字段、页面、流程、模板都能扩展。

这才是重构后应该达到的目标。

## 14. 上线能力完善规则

这些能力用于保证产品上线后稳定、可维护、可扩展。

## 14.1 配置版本管理

关键配置必须有版本：

- 模块字段版本。
- 页面配置版本。
- 流程版本。
- 打印模板版本。
- 导入导出配置版本。
- 权限配置版本。

使用场景：

- 管理员改错字段后，可以回到上一版。
- 页面发布后，运行端使用发布版本，未发布草稿不影响用户。
- 流程发布后，老流程实例继续按老版本走，新实例使用新版本。
- 打印模板改版后，历史单据可以按历史模板打印。

## 14.2 配置发布机制

配置分成“草稿”和“已发布”：

- 管理员可以先在草稿里改。
- 预览没问题再发布。
- 普通用户只使用已发布版本。

适合的功能：

- 页面。
- 流程。
- 打印模板。
- 字段显示配置。
- 导入导出配置。

好处：

- 避免管理员改配置时影响正在使用的用户。
- 方便做预览和回滚。

## 14.3 模块生命周期

模块必须有清楚状态：

- 草稿。
- 已启用。
- 已停用。
- 已归档。

使用场景：

- 新模块配置中，不让普通用户看到。
- 模块停用后，保留历史数据但不允许新增。
- 模块归档后，只允许管理员查看。

## 14.4 业务规则配置

除了字段必填，还应该支持简单业务规则：

- 某字段满足条件时显示另一个字段。
- 某字段满足条件时必填。
- 某状态下不允许编辑。
- 某金额超过指定值时必须走审批。
- 某类数据只能指定角色删除。

实现规则：

- 使用结构化条件配置。
- 不引入复杂脚本。
- 条件规则要能预览和测试。

## 14.5 数据唯一性和重复检查

模块内可以配置唯一规则：

- 客户手机号不能重复。
- 合同编号不能重复。
- 资产编码不能重复。
- 工单号不能重复。

导入时也要检查重复：

- 和数据库已有数据重复。
- Excel 内部自己重复。
- 更新模式下找不到匹配数据。

## 14.6 导入回滚和预演

导入必须支持：

- 导入前先预演。
- 显示预计新增多少条、更新多少条、失败多少条。
- 真正导入后生成导入批次。
- 出问题时可以按批次回滚。

注意：

- 回滚只回滚本次导入影响的数据。
- 如果导入后数据又被别人改过，要提示不能直接回滚。

## 14.7 打印模板版本和套打

打印模板必须支持：

- 模板版本。
- 模板草稿。
- 模板发布。
- 套打位置调整。
- 明细表格自动分页。
- 打印前预览。
- PDF 下载。

使用场景：

- 合同版本变化。
- 报销单格式调整。
- 采购单需要固定签章区。
- 出库单需要固定纸张尺寸。

## 14.8 KPI 目标闭环

KPI 目标不只是录一个目标值，还应该能和模块数据联动。

必须支持：

- 目标对象：人员、部门、角色。
- 目标周期：月、季度、年。
- 目标来源：某个模块的某个字段汇总。
- 达成率计算。
- 目标看板。
- 未达标提醒。

使用场景：

- 销售目标按合同金额统计。
- 工单目标按按时完成率统计。
- 项目目标按任务完成数统计。

## 14.9 系统体检

管理端必须包含系统体检：

- 数据库连接。
- Redis 连接。
- 文件存储。
- 密钥配置。
- Redis 后台作业状态。
- 最近错误日志。
- 数据库脚本版本。
- 当前服务版本。

好处：

- 部署后能快速判断系统是否正常。
- 出问题时不用到服务器里翻半天日志。

## 14.10 权限预览

权限中心必须支持：

- 选择一个用户，预览他能看到哪些菜单。
- 预览他能操作哪些按钮。
- 预览他能看到哪些字段。
- 预览他能查看哪些数据范围。

使用场景：

- 管理员配置权限后，马上确认普通用户看到的效果。
- 排查“为什么某个人看不到菜单”。

## 14.11 数据归档和恢复

业务系统使用久了之后，数据会越来越多。

必须支持：

- 软删除。
- 恢复。
- 归档。
- 归档查询。
- 批量归档。

使用场景：

- 已完成很久的工单归档。
- 历史合同归档。
- 老项目归档。

## 14.12 审批和业务状态联动

审批通过或拒绝后，模块数据状态应该自动变化。

示例：

- 请假审批通过，状态变成“已通过”。
- 报销审批拒绝，状态变成“已拒绝”。
- 合同审批中，业务数据不能随意编辑。
- 审批撤回后，数据回到草稿状态。

这类状态联动要可配置，不能写死在某个模块里。

## 14.13 操作确认和风险提示

危险操作要有清楚提示：

- 删除模块。
- 删除字段。
- 停用字段。
- 发布流程。
- 停用流程。
- 导入覆盖数据。
- 批量删除数据。
- 修改权限。

提示内容要告诉用户会影响什么，不只问“是否确认”。

## 14.14 用户体验细节

必须包含：

- 全局搜索。
- 最近访问。
- 收藏菜单。
- 快捷创建。
- 表格列保存。
- 筛选条件保存。
- 表单草稿。
- 错误字段定位。
- 移动端扫码或拍照上传。

这些细节会明显提升日常使用手感。

## 14.15 开放扩展点

event 扩展点包括：

- 数据创建后。
- 数据更新后。
- 数据删除后。
- 流程发起后。
- 流程通过后。
- 流程拒绝后。
- 文件上传后。
- 导入完成后。
- 导出完成后。

event 采用本地接口承载，不接消息队列；统一承载通知和自动化能力扩展。

## 14.16 命名和编码规范

成熟项目需要统一命名和编码规则：

- 系统编码。
- 应用编码。
- 模块编码。
- 字段编码。
- 页面编码。
- 菜单编码。
- 角色编码。
- 流程编码。
- 打印模板编码。
- 字典编码。

规则：

- 编码只用英文、数字、下划线。
- 同一系统内编码不能重复。
- 编码创建后尽量不允许修改。
- 显示名称可以随时修改。
- 导入导出、OpenAPI、打印模板优先使用编码定位字段。

## 14.17 配置迁移和升级

系统升级必须考虑：

- 数据库脚本升级。
- 模块配置升级。
- 页面配置升级。
- 流程配置升级。
- 打印模板升级。
- 权限配置升级。

恢复规则：

- 配置变更有版本。
- 升级脚本可重复检查。
- 升级前能备份。
- 升级失败能回滚或给出明确处理方式。

## 14.18 备份和恢复

上线产品需要考虑备份：

- 数据库备份。
- 文件备份。
- 配置备份。
- 打印模板备份。
- OpenAPI 密钥备份策略。

恢复场景：

- 误删业务数据。
- 配置改错。
- 文件丢失。
- 部署升级失败。

注意：

- 密钥不能明文导出。
- 备份和恢复要记录操作日志。

## 14.19 多环境管理

成熟项目通常至少有：

- 开发环境。
- 测试环境。
- 生产环境。

要求：

- 不同环境配置分开。
- 生产环境不能使用占位密钥。
- 测试数据不能混入生产。
- 部署包和配置文件分开。
- 前端 API 地址按环境配置。

## 14.20 安全策略

安全策略要覆盖：

- 密码加密存储。
- token 过期。
- 刷新 token。
- 登录失败限制。
- 敏感操作二次确认。
- OpenAPI 签名。
- IP 白名单。
- 文件上传类型限制。
- 文件大小限制。
- 防止越权访问。
- 防止跨系统访问数据。

## 14.21 成熟项目文档

除了代码，还需要文档：

- 部署说明。
- 配置说明。
- 数据库说明。
- 启停脚本说明。
- 管理员手册。
- 普通用户手册。
- OpenAPI 接入说明。
- 常见问题。
- 错误排查说明。
- 升级说明。

## 14.22 API 规范

成熟项目需要统一 API 规范：

- URL 命名统一。
- 请求方式统一。
- 分页参数统一。
- 排序参数统一。
- 筛选参数统一。
- 返回结构统一。
- 错误码统一。
- requestId 统一。
- 时间格式统一。
- 金额和数字精度统一。

实现规则：

- 内部接口和 OpenAPI 分开。
- 平台层接口和自定义系统层接口分开。
- 所有接口返回都带 requestId，方便排查。
- 错误信息要给用户看得懂，错误码给开发和运维定位。

## 14.23 错误码和异常规范

错误不能都叫“参数错误”或“系统异常”。

按模块划分：

- 账号错误。
- 系统错误。
- 应用错误。
- 模块错误。
- 字段错误。
- 权限错误。
- 流程错误。
- 文件错误。
- 导入导出错误。
- OpenAPI 错误。

要求：

- 后端抛出明确错误码。
- 前端展示人能看懂的话。
- 日志记录详细原因。
- 用户提示和技术日志分开。

## 14.24 幂等和重复提交

成熟项目必须处理重复提交：

- 表单重复点击保存。
- 审批按钮重复点击。
- OpenAPI 重复请求。
- 导入任务重复提交。
- 导出任务重复提交。

实现规则：

- 使用 requestId 或 idempotencyKey。
- Redis 保存短时间幂等记录。
- 审批任务按任务状态防重复处理。
- OpenAPI 必须支持幂等键。

## 14.25 限流和防刷

需要限制：

- 登录接口。
- 注册接口。
- OpenAPI。
- 文件上传。
- 导入任务。
- 导出任务。
- 高频查询接口。

实现规则：

- 用 Redis 做限流计数。
- 按 IP、账号、appKey、系统维度限流。
- 超限时返回明确提示。

## 14.26 缓存策略

可以缓存：

- 当前用户权限。
- 系统配置。
- 字典项。
- 菜单。
- 页面发布配置。
- 字段发布配置。
- 打印模板发布配置。

要求：

- 缓存 key 带 systemId、tenantId。
- 权限变更后清缓存。
- 配置发布后清缓存。
- 不缓存敏感明文。
- 缓存失效时能自动回源。

## 14.27 前端设计系统

成熟项目要统一前端设计：

- 颜色。
- 字体。
- 间距。
- 按钮。
- 表格。
- 表单。
- 弹窗。
- 抽屉。
- 空状态。
- 错误状态。
- 加载状态。
- 图标。

要求：

- 不同页面不要各写各的样式。
- 运行台和配置台风格统一但重点不同。
- 移动端组件单独适配。
- 按钮主次关系清楚。

## 14.28 前端权限和路由守卫

前端需要：

- 路由守卫。
- 菜单过滤。
- 按钮权限。
- 字段可见控制。
- 字段可编辑控制。
- 直接访问无权限页面时提示。

注意：

- 前端只是体验优化。
- 后端必须再次校验。

## 14.29 性能优化

重点关注：

- 大表格查询。
- 字段值查询。
- 关联字段查询。
- 权限数据过滤。
- 导入导出。
- 文件上传下载。
- 流程待办查询。
- 仪表盘统计。

配置规则：

- 列表必须服务端分页。
- 仪表盘统计可以缓存。
- 常用筛选字段支持索引。
- 大导出走 Redis 后台作业。
- 前端表格支持虚拟滚动。

## 14.30 数据统计和报表基础

仪表盘之外，还应有基础统计能力：

- 按模块统计数量。
- 按字段分组统计。
- 按时间趋势统计。
- 按人员或部门统计。
- 按状态统计。

这些统计可以服务：

- 仪表盘。
- KPI。
- 运行台首页。
- 管理员概览。

## 14.31 变更审计

业务数据变更要记录：

- 谁改的。
- 什么时候改的。
- 改了哪个字段。
- 修改前是什么。
- 修改后是什么。
- 来源是 Web、移动端还是 OpenAPI。

使用场景：

- 业务追责。
- 数据恢复。
- 审计检查。
- 排查误操作。

## 14.32 灰度和功能开关

支持功能开关：

- 某个系统启用某功能。
- 某个角色可见新功能。
- 某个模块启用新页面。
- 某个流程启用新版审批页。

功能开关使用结构化配置：

- 系统级开关。
- 应用级开关。
- 模块级开关。

## 14.33 部署回滚

上线部署要考虑回滚：

- 后端版本回滚。
- 前端静态资源回滚。
- 配置回滚。
- 数据库脚本失败处理。

注意：

- 数据库结构升级要谨慎。
- 破坏性脚本必须单独确认。
- 部署前备份。
- 部署后记录版本。

## 14.34 容量和配额

平台可以设置配额：

- 每个系统最大用户数。
- 每个系统最大应用数。
- 每个应用最大模块数。
- 每个模块最大字段数。
- 单文件最大大小。
- 每日导出次数。
- OpenAPI 调用次数。

好处：

- 防止某个系统误操作拖垮平台。
- 支撑不同版本授权。

## 14.35 数据脱敏

敏感字段必须支持脱敏：

- 手机号。
- 身份证号。
- 银行卡号。
- 地址。
- 密码类字段。
- secret。

规则：

- 列表显示脱敏。
- 详情按权限显示。
- 导出按权限决定是否脱敏。
- OpenAPI 按授权决定是否返回明文。

## 14.36 可访问性和移动适配

虽然是后台系统，也要考虑：

- 文本可读。
- 表单错误清楚。
- 按钮大小合适。
- 移动端不拥挤。
- 关键操作不依赖鼠标悬停。
- 表格在小屏下有替代展示。

## 14.37 落地级数据设计原则

成熟产品的表结构不能只满足增删改查，还要满足真实上线后的配置变更、运行追溯、权限解释、性能查询和失败恢复。

必须做到：

- 配置类能力要有草稿、发布、版本和回滚。
- 运行类能力要保存快照，不能被配置修改影响。
- 模块字段、页面、流程、打印模板、仪表盘、数据源都要支持发布版本。
- 列表常用筛选字段要有索引值表，不能所有查询都扫字段值表。
- 自动编号要有独立序号表，不能查询最大值加一。
- 导入导出要有任务明细，能看到每一行成功或失败。
- KPI 要有计算记录，能解释实际值来自哪里。
- 仪表盘要有组件表、版本表、权限表和缓存表。
- OpenAPI 要有密钥版本、幂等、限流、调用日志。
- 文件要有分片、预览、引用关系。
- 权限要能解释为什么能看、为什么不能看。
- 大日志和大任务明细要支持归档。

这些不是内置能力，而是重构版从一开始就要按这个方向设计。

### A.1 模块组（运行态二级导航）

**是什么：** 将多个业务模块归为一组，在**运行态**形成「顶栏组名 + 左侧模块列表」的导航结构。

**运行态交互（车系统示例）：**

```
顶栏：[ 仪表盘 ] [ 车辆管理 ▼ ] [ 人事管理 ]
         │
         └─ 点击「车辆管理」后
              左侧栏：车辆档案 | 维保记录 | 驾驶员   （组内 3 个模块）
              右侧：当前选中模块的列表/表单
```

**配置顺序（强制）：**

1. 先建**模块组**（如「车辆管理」）
2. 再在组下建**模块**（如车辆档案、维保记录、驾驶员）
3. 再配置字段 → 页面动作 → 菜单绑定 → 发布
4. 发布后，有权限用户运行态顶栏可见组名

**不是什么：**

- 不是字段分组、不是折叠表单分组
- 不是把模块挂在「应用」下面
- 不是仅在仪表盘卡片里分类（仪表盘可展示组，但**顶栏组导航**是主交互）

**参考模式：** 企业后台常见的「顶部分组 Tab + 左侧功能树」（类似 SAP/用友分模块域、Notion 多 workspace 切换后左侧页面树）。

### A.2 应用（自建系统对外入口）

**是什么：** 自建系统提供给**外部系统**访问的入口；外部通过该应用凭证/接口调用本系统已授权的数据与能力。

**配置位置：** 系统后台 → **对外应用**（或「应用管理」但文案须标明「对外访问」）

**配置内容（MVP 可简版）：**

- 应用名称、状态（启用/停用）
- 访问凭证（appKey/secret 或等价）
- 授权范围：可访问哪些模块、哪些动作
- 调用日志入口（可只读列表）

**不是什么：**

- 不是模块的父级容器
- 不是在应用下创建模块
- 不是普通用户日常进入业务功能的入口（业务入口是仪表盘 + 模块组导航）

**与平台层关系：** 平台层可维护全局对外策略/审计；**具体对本系统开放哪些能力**，在自建系统后台的「对外应用」里配置。

### A.3 平台层待办/消息导航

- **顶栏**：待办、消息（图标 + 角标）
- **侧栏**：不得重复待办/消息菜单项
- 侧栏：我的系统、Flow、应用、日志

### A.4 设计阶段流程

见 `.cursor/workflows/phase-1-internal-design-complete.md`：团队内部完成设计包后，再请用户调用 Open Design。

### A.5 可配置仪表盘与数据源

- 仪表盘由**后台配置**发布：统计卡、筛选按钮、图标、绑定数据源。
- **数据源**独立管理，类型：**系统内**（含公式计算）、**外部 API**、**数据库直连**。
- 运行态仪表盘展示配置结果，不是写死欢迎页。

### A.6 数据字典

- 系统后台维护字典类型与字典项。
- 模块字段和工作字段中的下拉、单选、多选、状态、标签可**关联字典**作为选项来源。
- 字典类型至少包含普通字典、树形字典、级联字典、状态字典、标签字典、字段选项字典。
- 字典项需要支持颜色、图标、语义、排序、默认项、启用/停用、停用历史、适用对象、是否可用于看板。
- 工作配置不直接维护状态和标签选项，只将字段绑定到数据字典。
- 任务看板的列、泳道和分组依据已发布的下拉或多选字段构建，字段选项的颜色和图标来自绑定的数据字典。

### A.7 系统基础参数

- 系统名称、系统图标、系统编码。
- **域名/访问地址**配置（子域名或自定义域名及解析说明）。

### A.8 平台层 Flow 与平台层应用（2026-06-15 补充）

- **平台 Flow**、**平台应用**在**平台后台**独立配置，与系统后台 Flow/对外应用解耦。
- **平台 Flow 可通过平台应用对外开放**（应用 scope 授权流程相关 API）。
- 侧栏 Flow/应用 = 用户入口；平台后台 = 管理员配置入口。

### A.9 业务列表高级能力（2026-06-15 补充）

- 高级搜索（含高级搜索抽屉）、列表场景/保存视图、表头自定义（含用户个人偏好）。
- 表格：**序号列 + 勾选列**；批量：编辑、转移、删除、导出；工具栏 **导入**。
- 行点击 → **右侧详情抽屉**；建模页须配置列表场景与默认表头。

### A.10 开发前六角色评审修正（2026-06-23 补充）

- **系统切换必须对象化**：平台账号进入系统业务页前必须生成 `SystemSwitchContext`，包含 `systemId`、`tenantId`、`systemMemberId`、有效角色、数据范围和权限快照；平台身份没有系统成员上下文时不能直接打开系统业务页。
- **平台消息与系统消息拆分**：平台消息中心只能处理平台授权、平台任务、平台日志、系统切换引导和平台 Agent 结果；涉及系统业务详情的消息必须先系统切换。系统消息中心只能在当前系统成员上下文中跳转业务对象。
- **行点击范围收敛**：只有明确数据列表或业务核心列表支持整行点击；说明表、配置矩阵、状态表不显示可点击手势，避免开发误做假交互。
- **流程节点专属配置**：流程画布必须有条件分支标签；条件、字段更新、外部 API、超时提醒等节点必须有专属属性和发布检查字段，不能都复用普通审批节点配置。
- **导入导出闭环**：导入必须包含模板下载、字段匹配、预检查、错误文件、确认导入、批次结果和回滚/不可回滚原因；导出必须包含范围、格式、字段权限、后台任务、结果文件和失败反馈。

### A.11 开发前细节补齐（2026-06-23 补充）

- **消息模板与通知渠道必须配置化**：消息、待办、审批通知、导入导出结果、AI Agent 结果统一由消息模板驱动，包含 `templateCode`、平台/系统层级、变量、发送渠道、跳转目标、去重键、已读回执、免打扰、失败重试和 `message_delivery_log`；平台消息模板不得直接跳系统业务详情。
- **密钥必须引用化和版本化**：SSO、OpenAPI、Webhook、外部模型等密钥不在页面和日志中回显明文，使用 `IdentityProviderSecretRef`、`OpenApiSecretRef`、`ModelCredentialRef` 等引用；轮换使用 `SecretRotationJob`，覆盖新版本、双写验证、切换生效、旧版本停用、失败回滚和审计。
- **无系统成员映射必须申请化**：认证成功但没有目标系统 `systemMemberId` 时，只能生成 `NoMemberAccessRequest`，由系统管理员审核并绑定员工、角色和数据范围；审核前不能进入业务页，不能自动授权。
- **关键按钮必须有结果链路**：保存草稿、发布检查、审批处理、AI 写入、模板发布、密钥轮换、体检、恢复演练、部署策略等按钮必须明确接入同步保存结果、后台任务、发布检查、日志追踪或专属抽屉，不能只给泛化“操作已响应”。

### A.12 干净上下文开发前复审补齐（2026-06-23 补充）

- **反复复审仍发现明显缺口时必须干净复审**：审阅者只读取落盘需求、brief、review、原型和知识库，不继承聊天上下文；至少按产品架构、UX、权限流程、开发验收四个视角合并问题后再给用户看。
- **系统切换必须重绘业务壳**：进入不同系统时不仅生成 `SystemSwitchContext`，还要按 `accountMemberBindingId/systemMemberId` 刷新系统名称、顶部模块分组、左侧模块、业务列表、待办、消息、字段权限和数据范围。
- **租户切换必须对象化**：多租户系统内必须有 `TenantSwitchContext`，包含 `tenantId`、`tenantRoleIds`、`tenantDataScope`、`isTenantSwitchable`、`disabledReason`；单租户隐藏租户切换。
- **无成员申请必须有完整生命周期**：`NoMemberAccessRequest` 至少包含 `requestId`、`status`、`identityProvider`、`externalUserId`、`targetSystemId`、`tenantId`、`requestRole`、`approverId`、`approveResult`、`roleIds`、`dataScope`、`rejectReason`、`traceId`。
- **系统 AI Agent 必须保存策略范围**：系统级 Agent 使用 `AgentPolicyScope` 表达 `moduleScope`、`fieldScope`、`actionScope`、`dataScopeExpression`、外发限制、脱敏策略和策略版本；运行日志记录策略版本、模型授权版本、提示词版本和权限快照。
- **外部应用密钥必须 OpenApiSecretRef 化**：对外应用页面和 API 只展示 `OpenApiSecretRef`、版本、轮换状态、到期和最近使用，不展示明文 appKey/secret。
- **日报自动草稿必须规则化**：自动生成今日日报使用 `DailyReportAutoSourceRule`，来源可包含任务、待办、消息、业务日志和审批记录，只读取当前成员有权限数据，提交前必须人工确认。
- **消息和分页按钮必须有状态结果**：消息筛选、全部已读、归档、上一页、下一页、加载更多、筛选应用、列设置保存、批量处理等都必须有可见状态变化或结果承接。
- **defaultDrawer 是阻断态**：原型入口如果落到 default/generic 且没有专属字段、状态、权限、失败反馈和 traceId，视为设计缺口，不能进入 coding。
