## 产品目标

这是一个平台层与用户创建的业务系统层组成的可配置业务系统。用户注册平台账号后可以创建或加入多个系统，进入系统时选择一个获权系统或默认进入一个。系统后台配置组织、权限、模块组、模块、字段、表单、场景、流程等；普通成员进入后看到配置好的模块组及模块，使用这些模块创建、查询和流转业务记录。后台配置与日常业务入口分别呈现。

系统还包含工作管理、数据源与仪表盘、KPI、打印、文件、公告、AI 配置，以及通过应用标识和密钥控制的对内、对外接入。目标是整套基础功能可用，不能把生成文件、单个 CRUD 或编译通过当作产品完成。

## 账号、系统与租户

- 平台账号是统一身份，平台层可查看账号基础信息；系统成员在此基础上扩展本系统的信息，同一账号可属于多个系统。
- 创建系统的人为该系统所属人和最高管理员，可查看和配置系统内全部内容，不受普通角色数据范围限制。若实现所属转让，原所属人失去该最高管理员身份；转让不是基础业务实施的前置条件。
- 创建系统时建立根租户，默认关闭多租户。多租户只是系统管理员在后台直接设置的开关，不需要平台另行授权。
- 关闭时只显示和允许访问根租户，保留其他租户和共享配置及数据；再次开启时恢复原有访问状态，不要求先合并或迁移数据。
- 开启时才可配置租户共享。数据和各租户仪表盘/KPI 按租户隔离；非根租户新增专属模块只能加入根租户已有模块组。

## 配置如何驱动业务

- 表结构承载基础数据，生成器提供这些表的基础 CRUD。模块自定义字段是用户在系统后台建立的配置；不能把自定义字段配置误当成固定实体字段，也不能只做配置表 CRUD 而没有对应的业务功能。
- 代码生成发生在工程开发期，按物理表生成 `base`；用户配置模块、字段和表单发生在系统运行期，由配置及数据驱动页面和业务，不是每配置一个字段就重新生成 Java 代码。
- 字段配置包含字段类型、校验要求、拖拽确定的所在行、行内位置、占位宽度及分组等。新建、编辑与详情复用同一份已保存并发布的配置。所在行与宽度是独立配置：一行只配置一个占宽 30% 的字段时，这一行仍只有这个字段，使用该行的 30%，其余位置留空；不能把后续行的字段拼进这一行，也不能自动拉伸为 100%。50% 也不意味着自动把任意两个字段排成同一行。
- 新建表单接口返回已保存的字段与表单配置；编辑和详情读取该配置并绑定已有数据。`queryById` 只查询基础记录；`information` 将基础值和自定义字段值填入已有配置，保留配置中的位置、顺序、宽度等属性，由页面据此展示。
- `manage` 业务 Service 读取实际字段/表单配置与主记录、扩展值；保存时校验字段类型及业务规则，在同一业务事务中保存主数据和自定义数据。Controller 只接收参数并调用 Service。
- 字段配置不是每个登录人都可直接读取的完整表单。先检查系统、租户、模块入口和菜单/动作权限，再按当前登录人的有效角色计算字段可见、可编辑等权限；跨租户访问还须同时满足有效租户字段权限和共享授权，租户共享不能绕过字段限制。新建、编辑、详情、列表、导出、打印均使用对应动作下的有效字段范围。
- 服务端不返回无读取权限字段的值，并拒绝对无编辑权限字段的写入；字段权限不能只靠前端隐藏或禁用控件。权限过滤后仍保留其他可见字段原有的行、位置和宽度，不自动补位、跨行拼接或拉伸字段。`information` 的职责是对当前有权读取的已保存配置绑定值，不能承担另一套布局计算。
- 列表、表头及表头排序、数据排序、筛选、场景及场景配置、新建表单、保存、编辑、详情、删除、导入导出等接口须形成可使用的完整业务过程。保存的场景、字段或权限配置必须实际影响查询和操作结果。

## 共用字段规则、权限和字典

- 字段类型是固定目录，模块不能自行定义新类型。`un-core` 提供类型定义、规则配置校验和业务值校验；模块字段、记录保存、导入、转化、应用写入等使用同一入口。范围、长度、精度、格式、必填、默认值及选项等规则来自字段已发布配置；不能在各 Controller 或业务方法里各写一套类型判断。唯一、关联存在性和引用授权由业务 Service 在对应数据作用域与事务内检查。
- 共用不等于隐藏业务差异。类型的基本值形态与格式可以公共；人员、部门、文件、关联、公式和子表仍须执行所属业务的完整规则。未实现完整执行能力的类型不能以保存任意 JSON 代替实现，运行态明确拒绝并说明原因。
- 权限使用统一的动作、可读字段、可写字段和负责人范围结果，业务入口先鉴权，再用于查询条件、详情过滤与写入检查。菜单操作、模块字段和记录数据范围分别由 role_menu、role_field 和 role_data 管理。有效角色的菜单和模块字段正向授权分别求并集，操作的数据范围按对应菜单求并集，再受租户字段许可和系统边界等硬限制约束；默认无授权即拒绝。负责人数据范围按当前组织归属求值，创建人不能替代负责人。系统所属人和租户管理员按已确定的管理身份授权，不能靠角色名称提升身份。
- 数据字典基础表逐条保存可复用的基础值及名称，例如“1 → 是”“0 → 否”；每个基础项有稳定 ID，值、名称及必要的父级关系使用普通表字段逐条保存。基础项只允许新增和修改名称等资料，不允许删除或回收、复用其 ID；同一 ID 不得改作另一种业务含义。已有引用始终能按 ID 查到基础项。
- 自定义字段的下拉、单选、多选及级联选项从字典基础表中选择。某个字段使用哪些字典项、选项顺序及字段自身的展示设置，才保存在该字段的 JSON 配置中；引用稳定的字典项 ID，不另复制一套基础值和名称。字段草稿修改不影响已发布配置，发布后使用本字段确定的可选范围。字典增加基础项不自动扩大已配置字段的可选范围；某字段移除可选项不删除字典基础项，也不修改其他字段的可选范围。
- 业务字段保存实际选中的字典项 ID，多选保存 ID 集合；级联按字段配置保存末级 ID 或 ID 路径，服务端统一核对来源、父子关系和允许范围。列表、详情等按 ID 读取当前发布名称；字典改名后已有记录也显示新名称，不以每条记录保存历史名称和完整字典版本作为默认机制。
- 字段选项引用、可选范围或值类型等变动发布前检查旧数据及关联配置。仅改名称、排序和布局不重写业务值；移除或替换被使用的基础项引用、缩小级联范围及不兼容类型变更，需要列出受影响的旧值、数量和对应业务记录，由管理员指定旧值到新值的迁移办法。目标必须属于新配置的有效范围，并满足权限、必填、唯一及级联关系等规则；迁移办法未确定或检查未通过时不发布受影响变更，不能静默清空或自行替换旧值。执行时重新核对影响数据，不能只依赖预览结果。
- 模块字段配置调整引发的数据迁移，必须在每条受影响业务记录下产生操作记录，使用独立操作类型“模块字段变更”，展示格式为“模块字段变更：张三于某时间将「客户等级」从「普通客户」迁移到「重点客户」。”；不能只在配置后台保存总数。日常编辑业务记录中的字段属于普通业务修改，使用独立的业务修改操作类型及文案，不归入“模块字段变更”；两类操作在同一业务记录的操作历史中明确区分。复用业务变动日志保存字段标识、迁移前后选项 ID 和当时名称、实际操作人及操作时间；日志中的当时名称不随以后字典改名而变化。记录值更新与对应日志写入在同一事务中完成，失败不能留下无日志的迁移结果；日志读取遵守记录、租户和字段权限。
- Redis 缓存配置、权限规则和字典基础项，键包含系统、租户及数据库提交版本。字典基础项资料保存即生效，名称修改后按当前名称展示；字段自身的选项范围按字段配置发布。授权撤销、配置发布和基础项修改在事务提交后失效缓存；回滚不切换缓存，事务内不填入未提交配置。Redis 异常时回数据库；数据库版本避免失效失败、并发回填或进程重启复用旧授权。登录账号、系统和租户状态实时检查，缓存不保存业务数据或敏感明文。

## 模块动作与转化

- 菜单是导航与功能授权的统一资源，区分目录、页面和操作等类型；新建、编辑、列表、详情、导入、导出、删除、转移、打印、转化以及自定义动作均建立各自独立的菜单权限节点。目录和模块节点组织树形结构，不代表侧栏必须显示所有操作；动作的实际位置来自展示配置。
- 系统模块的权限资源统一由 `un_sys_menu` 定义，名称、稳定权限编码和父子层级不在多处重复维护。`un_module_menu` 关联模块与统一菜单，承载模块内展示位置及相关配置，不另建立一套权限身份。`un_module_action` 按菜单 ID 关联对应执行配置，描述执行类型、输入字段、条件、转化映射或 Flow 等；同一个操作菜单只有一份对应动作配置，action 的记录主键不再作为另一套授权资源。
- `un_sys_role` 定义角色，`un_sys_member_role` 关联成员与角色；`un_sys_role_menu` 直接按角色 ID 与菜单 ID 授权，唯一关系为“角色 + 菜单”。动作已经是具体菜单节点，不能再在同一授权上通过 action_code 重复定义一次动作，也不新增 role_action 维护平行授权。多个有效角色对相同菜单的正向授权求并集；拥有模块或目录节点不隐式取得所有子动作，授权界面的全选是批量写入具体菜单授权，后来新增的动作不自动授予原角色。
- `un_sys_role_field` 单独维护角色对模块字段的控制，关联角色 ID、模块 ID 和字段 ID，控制可读、可编辑、可导出。字段按稳定 ID 授权，改名不改变授权归属；角色属于当前系统租户，字段必须属于该角色可配置范围内的模块。字段权限不再塞进 role_data 的负责人范围配置，也不通过 role_menu 重复保存。
- 模块字段权限在成员当前全部有效角色间按正向授权求并集，未授权的标记不作为否决其他角色的显式拒绝；可编辑和可导出均不得超出最终可读范围，合并结果再受当前租户字段许可等硬限制约束。新增字段默认不向普通角色自动开放。列表、表单、详情、筛选、导入导出、打印、转化、自定义动作及操作日志统一使用该字段许可；自定义动作只能写入动作指定字段与有效可编辑字段的交集，字段许可本身不授予动作执行权。
- `un_sys_role_data` 以“角色 + 操作菜单”关联负责人及组织记录范围；菜单节点已经能确定模块和具体动作，不能另用一套动作身份造成权限错配。没有对应 role_menu 授权时，单独存在的数据范围或 role_field 字段许可不能取得执行权。运行入口统一解析实际模块及其菜单，校验系统租户、发布和启停状态及角色菜单授权，按 role_data 检查可操作记录，再按 role_field 和租户字段上限过滤读取与校验写入；前端展示与后端执行使用同一菜单权限身份。授权修改在提交后递增数据库权限版本并失效缓存。
- 每次创建业务模块时自动初始化十个默认基础动作：新建、编辑、列表、详情、导入、导出、删除、转移、打印、转化；同时建立对应菜单节点、模块菜单关联及动作执行配置。这是每个模块实际拥有的配置，不能只在页面写死一组按钮；初始化幂等且不覆盖管理员后续配置。动作建立后仍受配置发布、启停、角色、字段、数据及租户范围约束，不自动给所有成员授权；转化等需要额外参数的动作，完成目标模块及映射等必要配置后才可执行。
- 列表和详情是两个独立动作，分别授权并配置对应动作的数据范围；字段按模块 role_field 许可结合各动作配置取用，不能共用一个笼统的查看动作替代独立动作。动作按页面入口、列表工具栏、批量操作区、行操作区或详情头部等配置位置展示，默认动作自动创建不表示全部堆在同一个按钮区。管理员可以配置动作名称、展示位置、启停、权限、执行类型、所需参数、执行条件及相关 Flow，并建立满足业务需要的自定义动作。默认与自定义动作使用实际配置的稳定标识进行授权和执行，不能只用固定默认动作枚举排除自定义动作。
- 自定义动作支持修改业务字段值。例如管理员建立“更新状态”动作，选择要更新的状态字段；操作人点击后按该字段当前已发布的下拉及字典可选范围选择状态，提交后保存到当前业务记录。动作输入由目标字段类型和配置决定，不能每建立一个动作就另写一套表单或保存规则。服务端检查该动作本身的授权、执行条件、记录负责人范围和目标字段写入许可，复用公共字段校验及业务保存服务，只允许更新动作配置指定的字段。
- 自定义字段更新动作在业务记录下保存动作名称、实际操作人、时间以及字段前后值，属于业务数据修改操作。只有模块字段配置调整引发的旧数据迁移才使用“模块字段变更”操作类型和文案，两者不能混淆。动作执行条件在服务端按当前记录重新判断，条件不满足时不保存；修改记录与相应操作日志在同一事务中完成。
- 打印与详情、转移、转化、导入导出一样属于模块动作。打印模板继续使用原名表 `un_print`，模板配置和动作执行归 `un-sys` 内部相应业务包，不建立独立 `un-print` Maven 模块或服务。
- 转移动作变更当前业务记录的负责人、部门等归属，不改变记录所属模块，并记录转移前后值及实际操作人。
- 转化动作由管理员选择来源模块 A、目标模块 B，并配置 A 字段到 B 字段的对应关系及执行条件。操作人点击该动作后，服务端核对当前条件，按映射读取 A 记录字段值，使用目标模块当前发布的字段类型、必填、唯一、字典和关联等规则完成校验，在 B 模块创建一条业务记录。映射使用稳定字段标识，页面展示字段名称，不能让用户手写数据库字段或接口载荷；条件不满足或校验失败时不创建目标记录。
- 转化须同时检查来源记录的读取/转化权限、来源字段读取权限、目标模块新增权限及目标字段写入权限，并遵守系统、租户和数据范围限制。配置缺失、目标配置变化导致映射失效或目标必填字段无法补齐时，明确拒绝并给出原因。
- 同一来源记录对同一目标模块只能成功转化一次，可以转化到不同目标模块。目标记录、字段值、转化关系和操作日志在同一事务中完成，失败时整体回滚。成功后来源与目标独立；后续编辑及逻辑删除不自动同步或级联删除另一方，转化历史保留。共享记录不允许转化。

## 权限、负责人和应用

- 系统内角色、模块动作权限和数据权限由本系统后台配置。业务数据可见范围结合记录负责人及其组织归属、当前成员角色的数据权限判定；不能把创建者直接当成负责人。
- 表单、导入或应用写入未提供负责人/创建人时，按已确认规则以系统所属人补齐，避免产生没有归属的业务数据。
- 租户共享扩充对应动作的数据范围，仍须拥有对应模块动作权限；总范围为本身范围与有效共享范围之和。共享记录不允许转化为其他模块记录。
- 应用通过 appId/secret 提供对内、跨系统和对外调用入口，调用范围由应用配置的接口授权和负责人/部门范围确定，不继承所选人员后续变化的系统角色权限。系统应用从系统组织选范围，平台应用从平台组织选范围。
- 应用选人员时访问负责人为这些人的数据，选部门时访问负责人归属该部门的数据。异常人员从有效范围排除，其他有效范围仍可调用；无有效范围时报错。配置部门失效时报错并要求管理员修正配置。
- Flow/审批可供系统内部使用，也可经应用向外提供接口；完全外部办理审批时，审批人员标识由外部传入并与配置比较。审批节点可配置调用外部 API。

## 数据模型

- 以《表意义.md》的 94 张表作为用户提供的业务范围和命名参考，保留已有表名及用途；这不是不可调整的表数量上限。按完整业务过程推导必要字段、关联和确有业务需要的补充表，不建立只有主键的占位表，也不为凑数量创建表。
- 早期 SQL 有字段参考价值但不是可执行迁移。缺失的字段按目标功能补齐；表和所有字段写中文备注，数据库时间字段使用 `*_time`，Java 属性使用 `*Time`。
- 不建立数据库外键和触发器。表以关联 ID 表达关系，由业务代码完成查询、依赖检查和事务；删除有引用的数据时明确拒绝或执行用户选择的业务转移，不能直接级联删除。
- 先按整条业务主线梳理各模块的表与必要字段，再按依赖实施；不因眼前一个接口临时拼出表结构。SQL 按业务模块组织，并提供汇总的 `final.sql` 与变更的 `update.sql`。
- 项目使用独立库 `unexamine_r16`。旧库和测试数据不作为需求或完成证据；当前结构纠偏已获用户授权清空该库并按最终结构重建，清除错误模型及其兼容迁移代码。以后涉及需保留的真实业务数据时，依据用户明确的数据保留要求提供迁移，不自行扩大清理范围。

## 后端业务范围

- 基础列表须有分页、必要筛选、允许字段的排序和表头配置；模块记录须支持场景及场景配置、字段和表单布局、新建、保存、详情及权限范围。不能只保存配置而不执行对应查询。
- 平台、系统、租户、模块、流程、审批、工作、数据展示、打印、应用和公共资源按《表意义.md》中的表用途划分业务所有权。审批与通用流程各自保留定义和运行数据，不混为一套表。
- 仪表盘使用权限内已有数据源/模块，或按模块关联关系及条件配置的新数据源；不提供数据库直连数据源。外部接入按后台已配置能力使用，未配置时不启用，不擅自新增企业接入、JIT 开通或历史打印文件等需求。
- 后端完成所有当前基础功能所需接口，核对成功结果、真实持久化、越权拒绝和失败结果，再由用户验收。之后才在 `font_web/` 开发一个前端，并验收真实页面。
- 复用本机 Docker MySQL 3306 和 Redis 6379；后端固定 9999。产品只运行一个后端和一个前端，不增加 Nginx 或新数据库容器。

## 工程与分层

仓库同时包含产品实现和为产品开发服务的工程框架，二者职责如下：

| 目录 | 职责 |
| --- | --- |
| `docs/` | 用户原始输入，以及这一份最终需求理解 |
| `template_base/` | 可复用的开发流程、职责、编码规则和代码生成工具，不承载产品业务和开发历史 |
| `back/` | 后端 Maven 多模块工程，物理表、生成的 base、manage 业务及唯一服务入口 |
| `font_web/` | 唯一前端，复用配置实现管理页面和业务页面 |

后端使用 Maven 多模块的单体工程。只有 `un-web` 是 Spring Boot 启动和打包入口，其余模块作为普通依赖 JAR 加入同一应用，在同一进程中注入和调用 Java Service，使用同一业务事务。模块拆分用于约束业务归属、依赖和复用，不引入微服务、远程调用、服务注册或分布式事务。域内继续分包，不按单个动作继续拆 Maven 模块：

| Maven 模块 | 业务所有权 |
| --- | --- |
| `un-plat` | 平台账号、组织、角色、菜单、配置、日志和消息 |
| `un-sys` | 系统、租户、成员、组织、权限，以及关联的模块组、模块定义、字段、表单、场景、业务记录、动作和模块 Flow；按系统、模块、Flow、打印动作等业务分包 |
| `un-work` | 项目、任务、成员、工作日志、评论及历史 |
| `un-dashboard` | 自定义仪表盘、自定义数据源、组件、KPI 及其访问范围 |
| `un-app` | 应用配置、受控访问授权与事件接入 |
| `un-examine` | 审批定义、配置、节点、人员、审批实例及模块审批关联 |
| `un-core` | 真实共用的基础能力、异常响应、分页、公共配置与文件元数据等；保持业务归属清晰，不堆入各域专属业务 |
| `un-file` | 可独立被引用的文件上传和存储接入能力，按 starter 方式提供配置接入；调用业务负责文件业务归属和授权，仍随同一个后端进程运行 |
| `un-web` | 唯一 Spring Boot 服务入口，组合依赖并提供服务级运行配置 |

- 仓库根目录的 `back/` 是后端 Maven 工程，模块统一使用 `un-*`。`un-sys` 内通过 `sys.module`、`sys.flow`、`sys.action.print` 等业务包组织相关能力；每个业务包的 `base` 与 `manage` 平级，生成归属和 Java 包同步调整，原始数据库表名不变。不建立独立 `un-module`、`un-flow`、`un-print`，不建 `foundation`、`identity` 聚合模块。平台独立 Flow 的原有需求继续保留，与系统/模块 Flow 复用同一套定义和运行能力，按所属作用域授权，审批仍由 `un-examine` 承担。
- `un-core` 不反向依赖业务模块，`un-file` 的上传存储接入保持可复用；业务模块按实际需要声明编译依赖，避免相互依赖成环。`un-web` 负责装配，跨模块调用仍是本地 Service 调用。只有出现独立部署、团队边界或容量隔离的实际需要时再评估服务拆分。
- 代码生成器按业务表生成 `base` 的 Entity、Mapper、`IService` 和 `ServiceImpl`。基础 CRUD 不能只是空接口与空实现：参照提交 `70a3979a` 的 `examine-core/src/main/resources/simple`，应在 Service 中有 `queryPageList`、`addOrUpdate`、`queryById`、带字段布局的 `information`、`deleteByIds` 的真实实现。Controller 接收 HTTP 参数并调用 Service；特殊规则、授权和跨表编排放同业务包的 `manage`，不把 CRUD 查询与保存逻辑堆进 Controller。新代码和模板须有适当的中文业务注释、`@Tag` 和 `@Operation`。
- `manage` 中业务 Service 调用本模块 `base` Service，特殊逻辑在 `manage` 内按 Controller、Service 等职责分层，不能改用 JdbcTemplate 绕开基础服务。字段配置的业务归属不写进每张表的通用模板。
- 先从表和模板建立可复现的生成链，再开发业务接口；不从旧 Controller 或旧 SQL 复制业务实现。简单 CRUD 不增加多余抽象。任务按不超过 240 分钟的可观察业务结果划分，每批核对结果是否符合原需求；局部测试通过不能证明业务理解正确。

## 工程框架如何服务交付

- 工程框架的目标是提高需求理解、任务拆分、实现及联调的正确性和速度；它是开发工作方式与工具，不是产品运行时新增的一层系统，也不以文档数量、agent 数量或完成标记衡量效果。
- 先理解整条业务主线及各域关系，再拆任务。每个任务说明要交付的业务行为、所属模块、前置依赖、涉及的数据和接口，以及成功、无权和失败结果。按可观察的业务结果拆分，不把一张张表的 CRUD 当成完整产品功能。
- 单批估算不超过 240 分钟；超过时沿业务依赖继续拆分。任务安排保留在当前工作上下文中，直接更新最终代码，不生成计划、状态、交接、评审、验收历史等中间文件。
- agent 表示职责承担者，skills 表示按需使用的具体方法或工具。同一 agent 可承担多项职责；有独立工作且适合并行时才分工，共享迁移、接口依赖和联调保持有序，不为使用某种机制另建框架。各执行者读同一份最终需求理解并修改同一套最终实现。
- 修改表结构后，先在目标库执行并核对，再通过统一生成器更新对应模块 base，最后适配 manage 和接口。生成器直接产出正确包结构及基础实现；避免手工修补生成文件造成下次生成退化。
- 验证先执行相关编译和有意义的测试，再用实际接口核对配置保存、查询效果、持久化、授权和失败行为。模块集成后回到完整业务过程检查，不能只验证自设算法或把文档存在当作通过。
- 工程工具只从当前最终文件和实际代码读取上下文、运行检查，不保存或回放历史理解。用户补充需求时原位更新本文件对应内容及最终实现，原始需求文件仍由用户维护。
- 已确认源自需求理解错误的实现，直接清除错误的数据模型、字段、接口、调用和规则，按正确需求维护唯一最终实现；不能以兼容旧代码为由保留错误结构、旧协议或平行执行分支。已获授权清空的开发数据库直接按最终结构重建，不为错误测试模型增加兼容迁移代码。
- 存储和接口设计先区分基础数据、配置及业务数据，明确维护者、引用关系和实际生效位置。用户纠正模型后，把正确关系原位更新到本文件，并检查数据库、生成结果、业务 Service、接口、缓存和用例中的同源假设；以用户给出的具体业务例子验证修正，不能仅改名称或局部补丁。可复用的防错规则维护在工程框架中，不另建学习历史或副本需求。

整体实施顺序是：理解完整产品和表关系 → 按业务依赖建表并生成 base → manage 实现真实业务 → 后端接口整体验收 → 前端使用真实接口实现配置态与运行态 → 实际页面与完整业务验收。分批开发只改变执行顺序，不缩减完整交付目标。
