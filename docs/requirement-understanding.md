## 产品目标

这是一个独立平台层与用户创建的业务系统组成的可配置业务系统。平台继续独立，沿用 `un-plat` 的平台作用域，不把平台实现为特殊业务系统。用户注册平台账号后可以创建或加入多个系统，进入系统时选择一个获权系统或默认进入一个。一个系统可配置多个业务模块，并独立决定是否开启多租户。系统后台配置组织、权限、模块组、模块字段、模块页面、模块动作和模块阶段；普通成员进入后看到配置好的模块组及模块，使用这些模块创建、查询和流转业务记录。后台配置与日常业务入口分别呈现。

系统还包含工作管理、数据源与仪表盘、KPI、文件、公告、运维、AI 配置，以及通过应用标识和密钥控制的对内、对外接入。导入、导出、打印等属于模块菜单中的基础动作，不作为与模块、Flow、应用并列的独立产品能力。现有原型用作页面视觉和交互参考，页面应易读、易操作；业务规则、字段和接口以本文件及实际后端为准，不照搬原型中的模拟请求和演示数据。目标是整套基础功能可用，不能把生成文件、单个 CRUD 或编译通过当作产品完成。

## 账号、系统与租户

- 平台账号是统一身份，平台层可查看账号基础信息；系统成员在此基础上扩展本系统的信息，同一账号可属于多个系统。
- 当前只实现账号密码登录及相应的账号、会话管理；其他登录方式或外部身份接入留待后续扩展，不作为当前前后端交付的依赖。
- 创建系统的人为该系统所属人和最高管理员，可查看和配置系统内全部内容，不受普通角色数据范围限制。若实现所属转让，原所属人失去该最高管理员身份；转让不是基础业务实施的前置条件。
- 创建系统时建立根租户，默认关闭多租户。多租户只是系统管理员在后台直接设置的开关，不需要平台另行授权。
- 关闭时只显示和允许访问根租户，保留其他租户和共享配置及数据；再次开启时恢复原有访问状态，不要求先合并或迁移数据。
- 开启时才可配置租户共享。数据和各租户仪表盘/KPI 按租户隔离；非根租户新增专属模块只能加入根租户已有模块组。

## 配置如何驱动业务

- 表结构承载基础数据，生成器提供这些表的基础 CRUD。模块自定义字段是用户在系统后台建立的配置；不能把自定义字段配置误当成固定实体字段，也不能只做配置表 CRUD 而没有对应的业务功能。
- 代码生成发生在工程开发期，按物理表生成 `base`；用户配置模块、字段和表单发生在系统运行期，由配置及数据驱动页面和业务，不是每配置一个字段就重新生成 Java 代码。
- 一个明确的业务实体先落实其主表、稳定主键及实际业务字段，主表基础 CRUD 由 MyBatis-Plus 生成；关联、明细、配置及运行记录在确有独立关系和生命周期时使用必要的表。建表和生成只提供数据基础，模块配置、权限、动作、审批及 Flow 的业务结果由 manage 完成，不能以“每张表都有 CRUD”代替完整业务。
- 模块、字段、模块菜单/动作、页面及表单配置保存后即为当前有效配置，不设置产品层面的草稿、发布、版本和回滚步骤。保存前完成权限、引用与数据影响检查，保存成功后即可用于查询、表单与动作执行；Flow 和审批的修改按下文的新流程启用、旧流程保留关联规则处理。模块、字段、菜单和页面等配置的新增、修改、启停及删除均记录实际操作人、时间和变动内容。
- 模块配置以模块信息为根，下分模块字段、模块页面、模块动作和模块阶段四块。模块字段定义业务值及校验；模块页面配置列表、详情和模块关联场景的字段展示、布局及审批状态展示；模块动作配置默认与自定义操作，并可配置动作执行后发起的审批；模块阶段配置阶段顺序、推进条件、关联模块补充资料及阶段审批。应用授权在应用中配置模块及其动作的对内或对外访问，不作为模块的父容器；审批定义、节点、分支和办理规则归审批自身配置，不在模块动作或阶段中重复维护。
- 字段配置以 `un_module_field` 为根，保存英文 `field_key`、显示名称、整数类型编号、必填/唯一/隐藏/只读、提示、默认值文本和展示样式等字段自身属性；列表、详情及关联场景是否使用该字段、显示位置和宽度由模块页面配置决定。当前固定类型编号从 1 开始：文本 1、富文本 2、数字 3、日期时间 4、选项 5、级联选择 6、人员 7、部门 8、附件 9、关联模块 10、自动编号 11、公式 12；不兼容旧编号和旧字符串类型。选项类型通过 `multiple` 配置决定单选或多选，单选、多选、开关、单选框、标签等属于同一类型的展示或校验样式；多行、金额、百分比、评分、进度、电话、邮箱、网址、身份证号和条码等属于基础类型的展示或校验样式。日期和日期时间使用同一类型并由样式控制。创建人与创建时间等系统资料由业务记录提供，不由管理员新增为普通字段。类型目录、专属规则和当前可用能力由 `un-core` 与业务 Service 共同校验，未实现的类型不能静默保存。
- 类型属性按列保存：文本长度和正则、数字范围/总位数/小数位/舍入/单位/货币、选项字典编码、关联目标模块、默认值等可检索或有固定含义的字段属性使用明确列。字段仅保留一个 `config_json`，只承载选项/级联联动、关联方式及必要写入规则、自动编号和公式等结构化配置；不使用默认值 JSON、布局 JSON 或重复的目标字段 ID JSON。关联模块保存目标模块 ID，关联目标在列表、详情及选择摘要中显示哪些字段由模块页面的对应关联场景配置，均引用目标模块的稳定字段标识；关联值只保存目标记录稳定 ID，业务服务检查目标记录存在性、租户范围、逻辑删除状态和读取权限。模块页面按使用场景保存字段的行号、列号和占位宽度，不自动补位、拉伸或跨行拼接。动态字段不再增加存储模式、分组或槽位元数据列，`field_key` 本身就是稳定的存储路由。自动编号规则使用 `autoNumberConfig` 的前后缀、补零位数、起始值、重置周期和规则编码，由独立序列表原子递增；按周期重置时前后缀必须包含对应日期占位符。公式规则使用 `formulaConfig`，数字结果只允许安全四则运算表达式，文本结果使用 `${fieldKey}` 模板，保存记录时按依赖顺序计算并写入字段槽位。`optionDisplayRules` 只描述选项联动后的字段显示/只读效果，服务端保存并校验结构，页面按当前表单值执行展示规则。
- 新建表单接口返回已保存的字段定义及对应模块页面配置；编辑和详情读取各自适用的页面配置并绑定已有数据。base 的 `queryById` 只查询基础记录；manage 的 `information` 将基础值和自定义字段值填入详情页面配置，保留该页面中的位置、顺序、宽度等属性，由页面据此展示。
- 管理员在模块页面配置中拖拽选择、排列字段，分别确定列表、详情和模块关联场景的可展示字段及位置；同一字段定义可在不同页面按需展示。新建、编辑使用相应表单页面配置。页面需有清晰的层级、间距、对齐和操作反馈，让配置和日常使用都易读、易操作；权限过滤不补位或改变已保存的布局。
- 模块业务记录主表分别固定保存 `status` 和 `check_status`。`status` 只是业务记录的状态标识，系统预置“草稿、正常、删除”三个稳定状态；管理员可在本模块增加其他状态并配置动作条件及目标状态，不能改动或挪用预置状态的编码与含义。除逻辑删除固定写“删除”外，业务状态变更由实际配置的动作、条件或 Flow 决定，不在代码中为模块写死其他流转。“归档”不是全系统固定状态；需要归档标识的模块可把它作为自定义状态，按本模块动作配置变更，不因此自动启用全局归档查询、只读或恢复规则。`check_status` 专用于记录当前审批状态，固定以数值 `0` 表示“审批未提交”并作为默认值；没有发起审批时保持 `0`，审批发起后才随当前审批从办理到终态更新。这里的“未提交”只指审批未提交，不代表业务记录仍是草稿。两者均为主表固定字段，不由管理员另建为普通自定义字段。草稿保存与提交是新建、编辑默认表单动作中的两种执行方式，目标状态默认分别为“草稿”和“正常”，管理员可在相应动作配置中调整目标状态；草稿保存允许暂缺必填项且不发起审批，提交时校验完整表单并按动作配置决定是否发起审批，这些行为依据执行方式判断，不靠 `status` 值推断。审批被拒绝或撤回后，业务记录保留该动作已写入的 `status`，只更新 `check_status`。列表、详情和关联筛选分别按两个字段的实际含义读取持久化状态。
- 草稿记录的可见与可操作范围继续按负责人、负责人组织范围、角色菜单与字段权限及该记录的团队成员授权计算；默认负责人为当前有效登录提交人。草稿不额外收紧为“仅创建人可见”，也不因创建人身份自动扩大权限；登录态不存在的应用写入仍按已确定的系统所属人回退与应用授权规则处理。
- 全系统业务数据删除继续以 MyBatis-Plus 的逻辑删除标记为实际删除依据，普通查询、关联查询和统计按逻辑删除条件过滤。对模块业务记录执行删除时，`status` 的内置“删除”只是补充的记录标识；成功设置 `deleted_time` 的同一事务中把 `status` 更新为“删除”，任一步失败则整体回滚，不让两个字段代表相反结果。普通状态动作不能只把 `status` 改成“删除”来绕过逻辑删除及其权限、审计和关联规则；其他自定义状态只是模块业务标识。现有 `archived_time` 不再作为全局归档字段保留，结构纠偏时核对受影响代码并清理。变更已被记录使用的扩展状态前检查引用和旧值处理，不能静默改写历史业务数据。
- 同一条业务记录同一时刻只能有一个使用中的审批流程。新建、编辑、删除、自定义动作或阶段触发审批前，服务端须检查该记录是否已有进行中的审批；并发发起也不能产生两个使用中的实例。该审批进入终态后才能为同一记录发起下一次审批，`check_status` 随当前审批进度及终态更新，不需要在模块页面指定一个“主审批状态组”。
- 模块页面另配置各动作审批状态的展示和关联筛选来源，不预设新建、编辑、删除等动作共用一个状态。管理员可把不同动作触发的审批归入同一状态组，也可分别配置独立状态组；例如新建、编辑、删除三个审批既可共用一个“审批状态”，也可分别形成三个状态字段，其他动作亦按配置处理。一个模块可同时有多个审批状态字段，列表按配置分别展示，详情和关联模块筛选使用相同的状态组标识及口径；不同组的审批状态互不覆盖。固定审批状态 `check_status` 与页面各状态组分别展示，历史终态仍能按动作所属状态组查看；审批定义、实例、节点和历史由 examine 独立办理。
- `manage` 业务 Service 读取实际字段/表单配置与主记录、扩展值；保存时按“权限检查→字段类型及业务规则校验→默认值、公式和自动编号计算→唯一性及关联检查→主表与扩展值保存→操作日志→动作后的 Flow/examine 处理”顺序在同一业务事务中完成。计算字段不接受外部直接写入，Flow/examine 只消费已经保存且通过校验的值；触发条件不命中不创建实例，已启用绑定或发布快照配置错误则回滚本次保存。Controller 只接收参数并调用 Service。
- 字段配置不是每个登录人都可直接读取的完整表单。先检查系统、租户、模块入口和菜单/动作权限，再按当前登录人的有效角色计算字段可见、可编辑等权限；跨租户访问还须同时满足有效租户字段权限和共享授权，租户共享不能绕过字段限制。新建、编辑、详情、列表、导出、打印均使用对应动作下的有效字段范围。
- 服务端不返回无读取权限字段的值，并拒绝对无编辑权限字段的写入；字段权限不能只靠前端隐藏或禁用控件。权限过滤后仍保留其他可见字段原有的行、位置和宽度，不自动补位、跨行拼接或拉伸字段。`information` 的职责是对当前有权读取的已保存配置绑定值，不能承担另一套布局计算。
- 列表、表头及表头排序、数据排序、筛选、场景及场景配置、新建表单、保存、编辑、详情、删除、批量删除、导入导出等接口须形成可使用的完整业务过程。批量删除使用删除动作权限，对所选记录逐条核对角色数据范围及共享写入范围；团队成员的查看或编辑权限本身不授予删除。整批检查通过后在同一事务内逐条软删除并写入各自的操作历史；任一条失败则整批不生效。保存的场景、字段或权限配置必须实际影响查询和操作结果。

## 共用字段规则、权限和字典

- 字段类型是固定目录，模块不能自行定义新类型。`un-core` 提供类型定义、规则配置校验和业务值校验；模块字段、记录保存、导入、转化、应用写入等使用同一入口。范围、长度、精度、格式、必填、默认值及选项等规则来自字段当前保存的有效配置；不能在各 Controller 或业务方法里各写一套类型判断。唯一、关联存在性和引用授权由业务 Service 在对应数据作用域与事务内检查。
  - 共用不等于隐藏业务差异。固定字段类型枚举逐项声明对应的物理值列，保存、读取、筛选、排序和展示共用该映射。为了避免少量动态字段全部拆成扩展行，`un_module_record` 预留固定主表键：`item_number01` 至 `item_number15` 为数字，`item_text01` 至 `item_text10` 为短文本，`item_long_text01` 至 `item_long_text02` 为长文本，`item_time01` 至 `item_time10` 为日期时间，`item_user01` 至 `item_user05`、`item_dept01` 至 `item_dept05`、`item_module01` 至 `item_module05` 均为单个引用 ID，`item_select01` 至 `item_select10` 为单选字符串。人员、部门、关联模块和选项只有单个值时才分配对应的 `item_*` 主表键；多选值统一保存到 `un_module_record_data`，按字段类型写入对应值列。数字、文本、日期时间等单值字段也按相应 `item_*` 键保存；长文本只预留两个槽位。固定字段如 `create_user_id` 继续使用原有列，不占用 `item_*` 槽位。
  - 自定义字段创建时，若对应的 `item_*` 槽位仍有空位，系统直接把该物理键作为字段的 `field_key`；对应槽位耗尽、字段值为多选/级联/结构化数据或不适合主表列时，生成稳定的 `field_*` 键并只保存到 `un_module_record_data`。`item_*` 和 `field_*` 是唯一存储路由，不增加 `storage_mode` 等重复元数据，也不允许同一字段同时写两处。`field_key` 创建后保持不变；主表槽位不因逻辑删除自动复用，只有显式清理并逐条留痕的迁移才能回收。扩展表按字段当前类型保存原始业务值：附件批次的32位小写UUID和其他固定短字符串写可索引的 `value_varchar`，文本和富文本写 `value_text`，数字及人员、部门、关联模块等引用 ID 写 `value_number`，单选值字符串写 `value_varchar`，所有日期相关值写 `value_time`（日期样式按零时保存），多选值数组、包含完整 ID 路径的级联对象和其他结构化值才写 `value_json`。同一行只填充对应的值列，不为短字符串再复制一列索引值。共用规则校验值形态与格式，业务规则校验成员、字典、文件及关联记录的存在性、归属和权限；筛选、比较和详情展示也按同一类型定义执行。`information`、列表和打印按当前有效的人员成员资料、部门组织资料及关联记录权限解析引用 ID，并把字典引用解析为展示项，存储值本身不改写为展示快照。未实现完整执行能力的类型不能以保存任意 JSON 代替实现，运行态明确拒绝并说明原因。
- 权限使用统一的动作、可读字段、可写字段和记录范围结果，业务入口先鉴权，再用于查询条件、详情过滤与写入检查。角色的菜单操作、模块字段和负责人数据范围分别由 role_menu、role_field 和 role_data 管理；记录团队成员另提供针对指定业务记录的查看或编辑权限。有效角色的菜单和模块字段正向授权分别求并集，角色操作的数据范围按对应菜单求并集。团队的“查看”允许读取指定记录及租户字段上限内的字段；“编辑”在此基础上允许修改该记录中本身可编辑且未超出租户写入上限的字段，不要求额外取得该记录的角色字段许可；两者均不扩充删除、转移及自定义动作权限。团队授权不扩充同模块其他记录，仍受有效系统/租户成员身份、模块状态和字段本身规则约束。默认无有效授权即拒绝。负责人数据范围按当前组织归属求值，创建人不能替代负责人。系统所属人和租户管理员按已确定的管理身份授权，不能靠角色名称提升身份。
- 数据字典基础表逐条保存可复用的基础值及名称，例如“1 → 是”“0 → 否”；每个基础项有稳定 ID，值、名称及必要的父级关系使用普通表字段逐条保存。基础项只允许新增和修改名称等资料，不允许删除或回收、复用其 ID；同一 ID 不得改作另一种业务含义。已有引用始终能按 ID 查到基础项。
- 自定义字段的下拉、选项（单选/多选）及级联选项从字典基础表中选择。某个字段使用哪些字典项、选项顺序及字段自身的展示设置，才保存在该字段的 JSON 配置中；配置引用稳定的字典项 ID，不另复制一套基础值和名称。字段选项配置保存成功后即使用本字段确定的可选范围，不保留草稿和发布两套配置。字典增加基础项不自动扩大已配置字段的可选范围；某字段移除可选项不删除字典基础项，也不修改其他字段的可选范围。
- 业务字段的单选和多选值保存字典基础项的稳定 `value` 字符串，不保存显示名称；多选保存 value 集合，单选主表使用 `item_select` 字符串。级联保存 `{"path":[上级ID,下级ID]}` 形态的对象，服务端统一核对来源、父子关系和允许范围。列表、详情等按字典编码和值读取当前名称；基础 value 不能改作其他含义，字典改名后已有记录也显示新名称，不以每条记录保存历史名称和完整字典版本作为默认机制。
- 字段选项引用、可选范围或值类型等变动保存前检查旧数据及关联配置。仅改名称、排序和布局不重写业务值；移除或替换被使用的基础项引用、缩小级联范围及不兼容类型变更，需要列出受影响的旧值、数量和对应业务记录，由管理员指定旧值到新值的迁移办法。目标必须属于新配置的有效范围，并满足权限、必填、唯一及级联关系等规则；迁移办法未确定或检查未通过时不保存受影响变更，不能静默清空或自行替换旧值。执行时重新核对影响数据，不能只依赖预览结果；处理成功后新配置直接生效，不另设发布步骤。
- 模块字段配置调整引发的数据迁移，必须在每条受影响业务记录下产生操作记录，使用独立操作类型“模块字段变更”，展示格式为“模块字段变更：张三于某时间将「客户等级」从「普通客户」迁移到「重点客户」。”；不能只在配置后台保存总数。日常编辑业务记录中的字段属于普通业务修改，使用独立的业务修改操作类型及文案，不归入“模块字段变更”；两类操作在同一业务记录的操作历史中明确区分。复用业务变动日志保存字段标识、迁移前后选项 value 和当时名称、实际操作人及操作时间；日志中的当时名称不随以后字典改名而变化。记录值更新与对应日志写入在同一事务中完成，失败不能留下无日志的迁移结果；日志读取遵守记录、租户和字段权限。
- Redis 缓存配置、权限规则和字典基础项，键包含系统、租户及数据库提交版本。字典基础项资料和字段选项配置均在保存成功后生效。授权撤销、配置保存和基础项修改在事务提交后失效缓存；回滚不切换缓存，事务内不填入未提交配置。Redis 异常时回数据库；数据库提交版本仅用于避免失效失败、并发回填或进程重启复用旧授权，不是产品配置的草稿、发布或回滚版本。登录账号、系统和租户状态实时检查，缓存不保存业务数据或敏感明文。

## 模块动作与转化

- 模块动作就是模块菜单，展示、授权与执行使用同一菜单身份，不维护另一套平行的动作权限。菜单是导航与功能授权的统一资源，区分目录、页面和操作等类型；新建、编辑、列表、详情、导入、导出、删除、转移、团队成员、打印、转化以及自定义动作均建立各自独立的菜单权限节点。目录和模块节点组织树形结构，不代表侧栏必须显示所有操作；动作的实际位置来自展示配置。
- 系统模块的权限资源统一由 `un_sys_menu` 定义，名称、稳定权限编码和父子层级不在多处重复维护。`un_module_menu` 关联模块与统一菜单，承载模块内展示位置及相关配置，不另建立一套权限身份。`un_module_action` 按菜单 ID 关联对应执行配置，描述执行类型、输入字段、条件、转化映射或 Flow 等；同一个操作菜单只有一份对应动作配置，action 的记录主键不再作为另一套授权资源。
- `un_sys_role` 定义角色，`un_sys_member_role` 关联成员与角色；`un_sys_role_menu` 直接按角色 ID 与菜单 ID 授权，唯一关系为“角色 + 菜单”。动作已经是具体菜单节点，不能再在同一授权上通过 action_code 重复定义一次动作，也不新增 role_action 维护平行授权。多个有效角色对相同菜单的正向授权求并集；拥有模块或目录节点不隐式取得所有子动作，授权界面的全选是批量写入具体菜单授权，后来新增的动作不自动授予原角色。
- `un_sys_role_field` 单独维护角色对模块字段的控制，关联角色 ID、模块 ID 和字段 ID，控制可读、可编辑、可导出。字段按稳定 ID 授权，改名不改变授权归属；角色属于当前系统租户，字段必须属于该角色可配置范围内的模块。字段权限不再塞进 role_data 的负责人范围配置，也不通过 role_menu 重复保存。
- 模块字段权限在成员当前全部有效角色间按正向授权求并集，未授权的标记不作为否决其他角色的显式拒绝；可编辑和可导出均不得超出最终可读范围，合并结果再受当前租户字段许可等硬限制约束。新增字段默认不向普通角色自动开放。列表、表单、详情、筛选、导入导出、打印、转化、自定义动作及操作日志统一使用该字段许可；自定义动作只能写入动作指定字段与有效可编辑字段的交集，字段许可本身不授予动作执行权。
- `un_sys_role_data` 以“角色 + 操作菜单”关联负责人及组织记录范围；菜单节点已经能确定模块和具体动作，不能另用一套动作身份造成权限错配。单独存在的 role_data 范围或 role_field 字段许可不能取得执行权；有效团队成员只通过该记录的团队授权获得列表、详情及所选的编辑权限，不因不在角色负责人范围内而被拒绝，也不由此获得其他动作。运行入口统一解析实际模块及其菜单，校验系统租户、逻辑删除和启停状态，合并角色菜单及数据范围与指定记录的团队授权，再按字段和租户字段上限过滤读取与校验写入；前端展示与后端执行使用同一菜单动作身份。角色或团队授权修改在提交后失效相关权限缓存。
- 每次创建业务模块时自动初始化十一个默认基础动作：新建、编辑、列表、详情、导入、导出、删除、转移、团队成员、打印、转化；同时建立对应菜单节点、模块菜单关联及动作执行配置。这是每个模块实际拥有的配置，不能只在页面写死一组按钮；初始化幂等且不覆盖管理员后续配置。菜单/动作配置保存即生效，执行仍受启停、角色、字段、数据及租户范围约束，不自动给所有成员授权；转化等需要额外参数的动作，完成目标模块及映射等必要配置后才可执行。导入、导出、打印与其他默认动作一起归入模块配置和执行链，不能因暂未实现而改成独立业务中心。
- 列表和详情是两个独立动作，分别授权并配置对应动作的数据范围；字段按模块 role_field 许可结合各动作配置取用，不能共用一个笼统的查看动作替代独立动作。动作按页面入口、列表工具栏、批量操作区、行操作区或详情头部等配置位置展示，默认动作自动创建不表示全部堆在同一个按钮区。管理员可以配置动作名称、展示位置、启停、权限、执行类型、所需参数、执行条件及相关 Flow，并建立满足业务需要的自定义动作。默认与自定义动作使用实际配置的稳定标识进行授权和执行，不能只用固定默认动作枚举排除自定义动作。
- “团队成员”是增强指定业务记录权限的动作。业务记录自身的负责人仍由主记录维护，不作为额外团队成员类型。向该记录加入当前系统的有效成员时，只能选择“查看”或“编辑”之一并保存；查看允许在列表和详情读取该记录，编辑包含查看及修改该记录业务数据。团队授权不授予删除、转移、自定义动作或管理其他团队成员的权限，这些仍按各自动作授权。团队成员不再区分协作人、只读成员或关注人，也没有“全部”档位；不能从旧成员类型推导权限。团队授权只作用于指定记录，执行时仍检查系统、租户、模块状态及字段边界。移除或停用团队关系后，相应的记录授权即时失效；团队成员管理须核对操作者的管理权限并留下变更记录，不改变记录所属系统、租户或负责人。
- 自定义动作支持修改业务字段值。例如管理员建立“更新状态”动作，选择要更新的状态字段；操作人点击后按该字段当前有效的下拉及字典可选范围选择状态，提交后保存到当前业务记录。动作输入由目标字段类型和配置决定，不能每建立一个动作就另写一套表单或保存规则。服务端检查该动作本身的授权、执行条件、角色或共享数据范围以及目标字段写入许可，复用公共字段校验及业务保存服务，只允许更新动作配置指定的字段；团队“编辑”权限本身不授予自定义动作。
- 模块新建、编辑、删除及自定义动作可配置执行后是否发起指定审批；这是该动作的增强配置，按当前模块、动作、事件和条件引用审批定义，未配置时不发起。动作触发的审批还要按模块页面配置归入共享或独立的状态组，供列表展示和关联筛选；状态组不改变审批实例本身。删除动作命中审批时先保留业务记录，审批通过后才实际逻辑删除；拒绝或取消保留记录，未命中审批时按原删除动作直接删除。整批删除先校验所有记录，再在同一事务内创建命中的审批请求及执行未命中的直接删除，失败则整批回滚。业务值及审批期间待变更字段按各自已确定的保存与提交规则处理；审批结果需要再推进模块阶段或改变业务字段时，由相应配置决定，不把所有动作强制纳入审批。
- 自定义字段更新动作在业务记录下保存动作名称、实际操作人、时间以及字段前后值，属于业务数据修改操作。只有模块字段配置调整引发的旧数据迁移才使用“模块字段变更”操作类型和文案，两者不能混淆。动作执行条件在服务端按当前记录重新判断，条件不满足时不保存；修改记录与相应操作日志在同一事务中完成。
- 打印与详情、转移、转化、导入导出一样属于模块动作。打印模板继续使用原名表 `un_print`，模板配置和动作执行归 `un-sys` 内部相应业务包，不建立独立 `un-print` Maven 模块或服务。
- 转移动作变更当前业务记录的负责人、部门等归属，不改变记录所属模块，并记录转移前后值及实际操作人。
- 转化动作由管理员选择来源模块 A、目标模块 B，并配置 A 字段到 B 字段的对应关系及执行条件。操作人点击该动作后，服务端核对当前条件，按映射读取 A 记录字段值，使用目标模块当前有效的字段类型、必填、唯一、字典和关联等规则完成校验，在 B 模块创建一条业务记录。映射使用稳定字段标识，页面展示字段名称，不能让用户手写数据库字段或接口载荷；条件不满足或校验失败时不创建目标记录。
- 转化须同时检查来源记录的读取/转化权限、来源字段读取权限、目标模块新增权限及目标字段写入权限，并遵守系统、租户和数据范围限制。配置缺失、目标配置变化导致映射失效或目标必填字段无法补齐时，明确拒绝并给出原因。
- 同一来源记录对同一目标模块只能成功转化一次，可以转化到不同目标模块。目标记录、字段值、转化关系和操作日志在同一事务中完成，失败时整体回滚。成功后来源与目标独立；后续编辑及逻辑删除不自动同步或级联删除另一方，转化历史保留。共享记录不允许转化。

## 模块 Flow 与审批

- 模块阶段是模块配置入口，现有 Flow 定义与运行能力承载阶段线路及实例；审批是独立的流程能力。模块动作和模块阶段都可以按各自配置引用审批定义并发起审批，不在 Flow 内复制审批节点，也不让审批定义承担模块页面、动作或阶段配置。
- 系统模块的审批定义在基础信息中明确关联所属模块；审批节点及分支条件引用该模块当前可用的字段配置，并在配置保存时检查字段、条件和权限范围。发起实例时固定实际使用的审批配置和相关字段条件，后续配置变化不改写已发起实例。平台内部不依附系统模块的审批仍按平台资源和应用授权边界处理。
- 模块阶段是关联模块业务记录的阶段流程，可配置“了解、深入、投标、投标结果”等阶段及“投标成功、投标失败”等结果线路。每个阶段可关联其他模块的记录，用于补充或记录该阶段的信息，也可关联指定审批流程；推进由阶段配置选择管理人员手动操作或业务事件、条件、审批结果自动触发，不能把阶段名称和结果写死在代码里。阶段配置只负责何时发起审批及如何消费审批结果，审批节点、分支、审批人和办理仍由 examine 负责。
- 模块 Flow 是围绕关联业务记录配置的业务流程，负责按菜单动作、业务条件、关联数据变化或审批结果触发后续线路、推进流程阶段，并在流程节点执行配置的字段变更。examine 独立负责审批节点、审批人、条件和抄送；Flow 可以在节点上启动 examine，但不承载审批通过、拒绝或取消的办理语义。
- 例如为商机模块配置 Flow：关联该商机的合同审核通过后，该条商机进入合同阶段；也可配置商机新建提交动作后执行指定 examine 审批流程。配置和执行均使用明确的模块、记录关联和审批结果，不把其他商机的合同结果混入当前记录。
- Flow 配置须覆盖关联条件后来失效的场景，例如合同撤回或作废后，是保留当前节点、回退还是进入其他线路，由配置的事件、条件及目标线路决定，不能写死统一回退行为。菜单动作还可按配置直接执行业务、业务执行后触发 Flow，或仅启动 Flow；Flow 节点配置了 examine 时由 examine 审批，审批结束后将最终状态作为 Flow 事件，按配置进入下一阶段、回退线路或结束。
- 关联模块的详情页展示顶部重要数据、标签和功能菜单；有 Flow 时展示该记录关联的 Flow、当前节点及配置允许的操作。流程阶段按关联 Flow 展示，不因此自行新增一个固定业务阶段字段；业务字段变更按实际节点配置执行。
- 节点是否允许手动推进、允许执行哪些 Flow 操作，在 Flow 配置页配置；按 Flow 配置的管理人员执行节点操作，并继续遵守业务数据和字段的访问范围。节点推进、手动操作及相关业务变动均记录实际操作人、时间、原因或结果。审批通过、拒绝、取消及审批意见由 examine 的节点策略和运行记录负责。
- 模块 Flow、平台 Flow 和 examine 审批配置保存即生效。修改形成新的流程配置并启用，旧流程配置停用；后续新关联的数据使用新启用流程，已经关联的数据继续使用原来的流程及其节点线路，不原地覆盖旧配置。旧流程停用只影响新关联，不终止旧实例，也不能成为拒绝原有关联数据继续执行的理由。不另设产品层面的草稿发布、版本选择或回滚操作。
- 记录新建或编辑成功后，业务保存链按绑定的模块、动作、事件和条件筛选已启用 Flow/examine；命中后以绑定的发布版本或审批发布快照建立运行实例、业务值快照和首节点待办。运行处理器不读取草稿节点，Flow 候选人由发布快照中的明确账号、外部应用身份及公共候选人解析器在节点进入时解析并写入实例快照；审批候选人按审批节点规则解析。审批节点未解析出处理人时，按该审批节点配置的异常处理规则转给固定人员、角色、部门或发起人的上级等有效处理人；未配置时由该审批定义的管理员兜底。审批定义可指定管理员账号，未指定时以定义创建账号为管理员；兜底规则和管理员随审批定义写入运行快照，在节点进入时解析并留痕；兜底目标仍无有效处理人时整体失败并回滚，不能生成无人可办的悬挂待办。保存、实例和首节点写入同一事务，任一已命中的配置无效则整体失败并回滚，未命中则不产生实例。
- examine 节点按策略解析器处理：普通审批、条件审批和抄送分别实现节点是否需要人工办理、办理动作、会签完成规则、处理人状态和节点状态。增加新的审批节点类型时只增加并注册一个节点策略，不把类型分支堆到运行服务；审批节点的条件、审批人和抄送配置都保存在发起时的审批快照中。
- 条件审批节点可以作为分支容器继续嵌套普通审批、条件审批和抄送节点；每个审批节点独立保存可见字段、可编辑字段和必填字段配置。审批期间字段可见和可编辑范围以审批节点快照为准，不叠加业务字段数据权限，但进入审批实例仍须通过记录和租户边界检查。审批处理人支持或签、并签、指定人、固定人、角色、部门和直系上级等来源，直系上级默认从当前租户成员关系的 `supervisor_account_id` 解析，也允许节点显式指定固定上级；发起时解析为实例处理人快照，运行时不重新读取草稿人员配置。
- 审批办理支持通过、拒绝、取消、转交和回退。转交可以转给内部账号，也可以保存外部邮件审批身份；原处理人保留已转交状态，新处理人建立待办。回退必须指定发布快照中的目标节点，按新轮次生成目标节点及处理人，当前节点保留回退记录。审批拒绝或取消时不提交运行快照中的待变更字段，只有审批通过并进入终态才提交最终值。
- 审批实例、节点、处理人和独立实例日志分别保留状态与操作轨迹。运行快照保存审批中字段的当前值和按节点顺序的 `fieldChanges`（字段、修改前、修改后、节点、操作人、时间），后续审批人读取最新快照值并能看到之前每次修改；日志记录审批意见、字段修改、转交、回退、外部节点响应和 Flow 回调。逻辑删除不清除历史日志。
- API 节点是可注册的自动节点策略，配置请求地址、方法、请求头、认证 token、超时和响应字段映射。调用成功后按映射更新审批运行快照，审批通过进入终态后才使用模块字段校验、唯一性、槽位和日志一次性写回业务字段，再继续后续 Flow/examine 处理；调用失败进入事务失败路径，由审批异常处理机制记录和处置。认证 token、密码和敏感请求头只保存在服务端配置中，管理查询和审计返回脱敏占位值；编辑未更换时沿用已保存密钥，提交新值时才轮换。
- 创建、更新、删除业务记录，Flow 发起与完成，审批发起与通过、拒绝、取消，文件上传以及模块导入、导出完成等扩展点统一通过 `un-core` 的本地同步事件接口承载。监听器在当前事务内按注册顺序执行，不能依赖消息队列或异步请求上下文；监听器失败随当前事务回滚。已发布的应用事件在同一监听器内按资源和作用域匹配回调，使用发布快照中的地址、过滤、超时和有限重试；回调保留订阅配置 `eventId`，并额外携带本次业务事件实例的 `eventOccurrenceId` 及 `X-Event-Id`，接收方按事件实例幂等，重试沿用同一标识。这是同步投递并随事务失败回滚的明确语义，不宣称具备独立消息队列的投递保障。
- 记录详情可以读取关联 Flow/examine 实例及节点历史；Flow 办理接口重新校验模块记录权限、租户边界和当前待办候选人，使用请求号幂等写入操作快照，按发布快照的连线条件创建下一节点。examine 办理接口负责普通审批、条件审批、抄送等节点，并处理通过、拒绝、取消及审批意见；审批节点办理只核对系统、租户、模块和记录边界，节点字段可见/可编辑范围以审批快照为准，不因办理人缺少模块详情动作而重复拦截；审批终态通过跨模块事件回到 Flow，已删除业务记录不能继续办理但历史实例保留。系统与平台分别提供分页审批待办和 Flow 待办工作台，候选人、上下文及已删除记录由后端重新核对。系统应用的外部待办也按独立 TODO 授权查询；有绑定或定义主键时按该资源授权，未指定时需资源级授权，返回前按当前业务记录负责人及部门范围过滤并在过滤后分页，不向调用方暴露其他候选身份。
- 平台 Flow 和 examine 可在平台内部使用；平台 Flow 可不属于任何业务系统。平台或系统内部的 Flow、examine 需要向外提供服务时，由对应应用授予资源、操作及数据范围等访问权限。平台 Flow 与审批的应用授权资源主键是流程定义主键，系统模块 Flow 的资源主键是触发绑定主键，系统审批的资源主键是审批定义主键；外部实例查询、办理请求同时带授权资源主键和实例主键，先按资源授权，再核对实例所属资源、业务记录边界与实际外部参与身份，不能用实例主键冒充配置授权。业务线路与审批办理各保留自身定义和运行数据，不能把模块 Flow 的业务阶段与审批结果混为同一状态。

## 统一逻辑删除与模块删除

- 整个系统中允许执行的删除统一为逻辑删除，使用 MyBatis-Plus 的逻辑删除配置和实体映射落实；复用符合时间命名规则的删除标记，不以物理 DELETE 代替产品删除。逻辑删除规定实现方式，不自动增加原本禁止删除对象的删除权限，字典基础项及不可删除审计等限制继续有效。
- 删除模块先检查其未删除的业务数据。没有业务数据时直接逻辑删除模块；有业务数据时提示“导出数据后删除”或“直接删除”。前者在导出成功后逻辑删除模块及所属业务数据，导出失败不删除；后者按用户选择直接逻辑删除模块及所属业务数据，不额外要求先完成审批、终止 Flow 或解除所有关联。 导出必须覆盖本模块待删除的完整有效业务数据并执行相应的数据及字段导出权限检查，不能用当前筛选的部分导出代替。先生成可下载的备份，确认后提交删除；删除前重新检查，若导出后模块配置或业务数据已变化，则重新导出，避免旧备份遗漏新数据。
- 模块及业务数据被逻辑删除时，关联的 Flow、examine 审批、实例、任务及其历史保持原样，不级联删除、终止、撤回或改写它们。其他模块中独立存在的业务记录也不因本模块删除而被连带删除。
- 普通查询、关联查询、列表、详情、数据源、下钻和查询统计凡涉及业务数据时，都检查相关数据的逻辑删除状态并过滤已删除数据；仪表盘和 KPI 不再把已删除业务数据计入结果。自定义 SQL、关联连接和聚合不能仅依赖单表自动过滤，也不能因为流程仍保留就继续把已删除业务数据作为正常结果返回。
- 模块和业务数据删除、导出处理、配置修改及 Flow 新旧启停等变动均留下对应操作 log。逻辑删除不清除操作日志、原有流程记录和关联历史；历史读取仍执行授权，不将历史记录混入正常业务查询和统计。
- `un_sys_log_opt` 的系统操作日志查询由 `sys/manage` 集中处理系统、租户、操作账号、模块、时间和日志内容条件，并在查询前检查管理权限。模块筛选须依据明确的模块归属或可验证的对象关系，不能通过任意日志文本模糊匹配推断；生成的 base 不承载这些业务条件。

## 权限、负责人和应用

- 系统内角色、模块动作权限和数据权限由本系统后台配置。业务数据可见与操作范围结合记录负责人及其组织归属、当前成员角色的数据权限和该记录有效团队成员权限判定；团队授权只扩充指定记录，不扩充同模块其他记录或整个负责人范围，不能把创建者直接当成负责人。
- 全系统创建业务资料时，负责人和创建人未显式提供的默认身份均先看本次操作是否有有效登录成员：有则使用当前成员，没有登录态则使用系统所属人。表单、导入和应用写入遵守同一规则；显式指定的负责人仍须通过当前系统和租户的有效成员及权限检查，创建人不能由普通请求任意冒填。实际操作人另行记录，不因默认归属回退而伪造登录身份。
- 租户共享扩充对应动作的数据范围，仍须拥有对应模块动作权限；总范围为本身范围与有效共享范围之和。共享记录不允许转化为其他模块记录。
- 应用通过 appId/secret 提供对内、跨系统和对外调用入口，调用范围由应用配置的接口授权和负责人/部门范围确定，不继承所选人员后续变化的系统角色权限。系统应用从系统组织选范围，平台应用从平台组织选范围。启用签名时使用 Unix 秒时间戳和 HMAC-SHA256，签名覆盖应用标识、请求号、资源、动作、系统/租户上下文及调用方业务参数；服务端补入的负责人和部门不要求调用方预知，调用幂等摘要仍保留真实范围值。外部 Flow/examine 记录入口先执行无副作用的凭据、安全和作用域预检，再读取真实记录负责人/部门并执行完整授权；预检不写调用审计，但计入应用限流，完整授权阶段不重复计数。
- 应用选人员时访问负责人为这些人的数据，选部门时访问负责人归属该部门的数据。异常人员从有效范围排除，其他有效范围仍可调用；无有效范围时报错。配置部门失效时报错并要求管理员修正配置。
- 平台内的 Flow 和 examine 可供平台内部使用，系统内的 Flow/审批按系统与租户范围使用；向其他系统或外部提供这些能力时必须经对应应用授权。应用也承载系统间的受控访问，不另设平行接口开放中心。完全外部办理审批时，审批人员标识由外部传入并与配置比较；审批节点可配置调用外部 API。

## 数据模型

- `un_module_record` 的负责人字段是记录归属来源；`un_module_teamer` 只保存额外加入的成员与该记录的“查看”或“编辑”权限，同一记录与成员只保留一条当前有效关系，不再用成员身份类型表示权限。现有 `member_type` 及重复关系按最终结构纠正；旧关系数据可清空后按新权限重新建立，运行代码不从旧类型猜测权限或保留兼容。
- 每张主表以 `id` 为主键，按实际业务增加必要字段；通用审计信息保留创建人、创建时间、更新人、更新时间，不因习惯预埋无业务用途的字段。租户、系统归属、逻辑删除、状态、关联 ID、唯一约束等只有在相应业务和已确认的全局规则需要时设置；已有结构不符合最终模型时直接调整，较大变动可清空受影响的开发数据后重建。时间列统一使用 `*_time`，表及所有字段写中文备注。
- 以《表意义.md》的 94 张原始表和后来明确的 `un_sys_role_field`（合计 95 张）作为主要业务骨架，保留已有表名及用途。结合用户原始需求和只读旧 SQL 中有价值的字段、关系，先在这套骨架内推导必要字段和关联；仅在明确业务无法由现有表合理表达时补表，不为预想中的扩展堆砌版本表、日志表或抽象结构，也不建立只有主键的占位表。
- 物理模型另需 `un_module_share`（跨租户记录或范围授权）、`un_module_sequence`（并发编号）、`un_module_exchange_job` 与 `un_module_exchange_row`（导入导出作业及逐行结果）、`un_kpi_result`（指标计算口径和结果历史）、`un_app_call`（应用调用幂等及审计）。`un_module_record` 的 `item_*` 预留列由 `field_key` 直接定位，不新增存储分配元数据列；`un_module_record_data` 只承载 `field_*` 溢出字段或多选、级联等结构化值。文件直接在 `un_common_file` 保存所属 `module_id`、业务 `data_id` 和附件字段 `batch_id`；批次 ID 是独立生成的32位小写UUID，不是首个文件的自增 ID，同一附件字段值保存这个UUID，同批文件共享它，不另建多对多引用表。新增物理表须有原 95 张表无法表达的明确业务关系；不以新增表数量代表功能完成。
- 早期 SQL 有字段参考价值但不是可执行迁移。缺失的字段按目标功能补齐；表和所有字段写中文备注，数据库时间字段使用 `*_time`，Java 属性使用 `*Time`。
- 不建立数据库外键和触发器。表以关联 ID 表达关系，由业务代码完成查询、依赖检查和事务，引用变动按对象的明确业务规则处理。模块删除遵守上文的统一逻辑删除规则，不因保留的 Flow、审批或关联记录额外阻断，也不级联改写这些记录；其他业务对象已有的引用检查与转移规则继续有效。
- 先按整条业务主线梳理各模块的表与必要字段，再按依赖实施；不因眼前一个接口临时拼出表结构。SQL 按业务模块组织，并提供汇总的 `final.sql` 与变更的 `update.sql`。
- `un_module_tenant` 记录租户能否使用模块，不能代替指定业务记录或数据范围的跨租户共享授权。共享关系需表达来源和目标租户、模块、记录或范围、独立允许的动作、生失效时间、状态和操作者，并留下可追溯审计；共享不改变原记录的所属租户。
- 项目使用独立库 `unexamine_r16`。旧库和测试数据不作为需求或完成证据；结构纠偏按最终模型执行，变动较大时可清空受影响的旧数据，按最新结构重新建立。清理前核对实际库和受影响范围，不自行扩大到无关数据；运行代码不保留错误模型的兼容迁移分支。

## 后端业务范围

- 基础列表须有分页、必要筛选、允许字段的排序和表头配置；模块记录须支持场景及场景配置、字段和表单布局、新建、保存、详情及权限范围。不能只保存配置而不执行对应查询。
- 平台、系统、租户、模块、流程、审批、工作、数据展示、应用和公共资源按《表意义.md》中的表用途划分业务所有权。导入、导出、打印等按模块菜单动作实现，不因独立表或代码包拆成独立产品中心。审批与通用流程各自保留定义和运行数据，不混为一套表。
- 工作域中，普通任务可不属于项目，快速创建后再补充负责人、协作人和截止时间；项目任务归项目或任务组，二者共用任务表但按项目成员规则区分授权。平台任务与系统租户任务在同一能力模型内按作用域隔离；项目编号在所在作用域内由数据库保证唯一，不能只在新增前查重。本人列表、看板和日历来自同一批任务数据。普通任务创建人、负责人及有效协作/关注/验收成员可见任务；只有创建人或负责人维护任务内容与成员，协作和关注成员不能借可见性取得编辑或转交权，验收成员可在待确认状态执行完成确认。状态流转、编辑、指派转交、评论和延期申请须记录实际操作者及操作历史；负责人变更必须核对目标账号在当前作用域的有效成员关系。负责人申请延期，创建人处理当前有效申请；截止时间直接调整或负责人转交使原申请失效，负责人不能绕过延期申请直接修改截止时间。项目负责人维护项目、任务组和项目任务，任务组可配置项目内负责人、排序、状态和期限；项目有效成员按项目授权查看任务。移除成员的最后一项项目关系前，须先转交其未结束的项目任务。项目及任务组完成度按未归档、未取消任务中已完成任务的比例计算；阻塞、临期、逾期和无人负责预警从当前任务值计算，不改写任务状态。每日工作日志始终由用户手动创建，与任务状态变化分离；用户主动选取当前有权查看的项目、任务作为关联，保存其稳定 ID 并可按关联筛选，不因任务状态变化重写日志。草稿由用户编辑，提交、撤回和再次恢复草稿均保留旧版本，当前列表只取有效版本。
- 仪表盘使用权限内已有数据源/模块，或按模块关联关系及条件配置的新数据源；不提供数据库直连数据源。外部接入按后台已配置能力使用，未配置时不启用，不擅自新增企业接入、JIT 开通或历史打印文件等需求。
- 运维能力先于 AI 扩展实施。平台后台和系统后台分别提供运维配置与审计入口，按实际作用域管理数据库、Redis、文件存储、后台作业、版本、部署、备份、健康检查和异常信息。平台管理员可导出整个平台项目的数据库表结构和数据；系统管理员可导出当前系统的配置、业务数据及相关表结构，不能只备份配置而漏掉业务记录、流程实例和操作历史。两种备份的产物均为可下载的 SQL 文件，不加密；当前只提供导出和下载，不提供恢复入口。备份须检查权限、核对作用域与文件完整性，并记录操作者和影响范围。实际操作须接入真实后端、权限与日志；原型中的演示入口不直接成为产品接口要求。
- AI 扩展安排在其他主要模块基本完成之后；AI 可按实际业务需要接入其他模块，只能在当前身份获权的系统、租户、模块、动作、记录和字段范围内完成简单操作。当前已有基础能力可保留，其他接入方式和跨模块能力随后按真实使用场景实现，不提前扩展为绕开现有权限的独立通道。
- KPI 以已发布的模块或数据源查询口径计算月、季度、年度结果，周期可指定根模块的日期时间字段，未指定时按业务记录创建时间归期；只统计本租户未删除且当前有权读取的业务记录。全租户实际值与每个人员、部门、角色目标的实际值分别计算：人员按记录负责人，部门按记录保存的负责人部门，角色按当前有效租户成员角色关系归属；目标值、实际值、达成率及每次计算的周期、来源配置和匹配记录数可追溯。无有效目标值时不伪造达成率。
- 后端完成所有当前基础功能所需接口和业务实现后，在现有 Docker MySQL 中建立一个新的、空的项目专用数据库，按最终 SQL 初始化；通过真实接口重新创建系统、租户、人员、模块、动作、阶段、Flow、审批、应用及业务数据，不沿用开发库的配置或测试记录。以新库核对完整业务链的成功结果、真实持久化、越权拒绝和失败结果，排除旧数据对验收的影响。清理旧项目数据前核对数据库归属和范围，不清理 MySQL 系统库或归属未明确的库。新库验收通过后再由用户验收后端，之后才在 `font_web/` 开发一个前端，并验收真实页面。
- 复用本机 Docker MySQL 3306 和 Redis 6379；后端固定 9999。产品只运行一个后端和一个前端，不增加 Nginx 或新数据库容器。

## 工程与分层

仓库同时包含产品实现和为产品开发服务的工程框架，二者职责如下：

| 目录 | 职责 |
| --- | --- |
| `docs/` | 用户原始输入，以及这一份最终需求理解 |
| `template_base/` | 可复用的开发流程、职责、编码规则和代码生成工具，不承载产品业务和开发历史 |
| `back/` | 后端 Maven 多模块工程，物理表、生成的 base、manage 业务及唯一服务入口 |
| `font_web/` | 唯一前端，复用配置实现管理页面和业务页面 |

后端使用 Maven 多模块的单体工程。只有 `un-web` 是 Spring Boot 启动和打包入口，其余模块作为普通依赖 JAR 加入同一应用，在同一进程中注入和调用 Java Service，使用同一业务事务。模块拆分用于约束业务归属、依赖和复用，不引入微服务、远程调用、服务注册或分布式事务。域内继续分包，不按单个动作继续拆 Maven 模块：

| Maven 模块 | 业务所有权 |
| --- | --- |
| `un-plat` | 平台账号、组织、角色、菜单、配置、日志和消息 |
| `un-sys` | 系统、租户、成员、组织、权限，以及关联的模块组、模块定义、字段、表单、场景、业务记录、动作和模块 Flow；按系统、模块、Flow、打印动作等业务分包 |
| `un-work` | 项目、任务、成员、工作日志、评论及历史 |
| `un-dashboard` | 自定义仪表盘、自定义数据源、组件、KPI 及其访问范围 |
| `un-app` | 应用配置、受控访问授权与事件接入 |
| `un-examine` | 审批定义、配置、节点、人员、审批实例及模块审批关联 |
| `un-core` | 真实共用的基础能力、异常响应、分页、公共配置与文件元数据等；保持业务归属清晰，不堆入各域专属业务 |
| `un-file` | 可独立被引用的文件上传和存储接入能力，按 starter 方式提供配置接入；调用业务负责文件业务归属和授权，仍随同一个后端进程运行 |
| `un-web` | 唯一 Spring Boot 服务入口，组合依赖并提供服务级运行配置 |

- 仓库根目录的 `back/` 是后端 Maven 工程，模块统一使用 `un-*`。`un-sys` 内通过 `sys.module`、`sys.flow`、`sys.action.print` 等业务包组织相关能力；每个业务包的 `base` 与 `manage` 平级，生成归属和 Java 包同步调整，原始数据库表名不变。不建立独立 `un-module`、`un-flow`、`un-print`，不建 `foundation`、`identity` 聚合模块。平台独立 Flow 的原有需求继续保留，与系统/模块 Flow 复用同一套定义和运行能力，按所属作用域授权，审批仍由 `un-examine` 承担。
- `un-core` 不反向依赖业务模块，`un-file` 的上传存储接入保持可复用；业务模块按实际需要声明编译依赖，避免相互依赖成环。`un-web` 负责装配，跨模块调用仍是本地 Service 调用。只有出现独立部署、团队边界或容量隔离的实际需要时再评估服务拆分。
- 代码生成器按业务表生成 `base` 的 Entity、Mapper、`IService` 和 `ServiceImpl`。基础 CRUD 不能只是空接口与空实现：参照提交 `70a3979a` 的 `examine-core/src/main/resources/simple`，应在生成的基础 Service 中有接收 core 公共 `SearchBO` 的 `queryPageList` 和简单的 `addOrUpdate`、`queryById`、`deleteByIds` 真实实现，不逐字段枚举筛选和排序；业务查询对象可继承 `SearchBO`，需要简单定制查询时按需增加 Mapper 方法。租户、系统、人员、模块、时间和内容等业务查询由对应 manage Service 实现，配置布局与字段值绑定的 `information` 也由 manage 实现。core 统一提供 `Result`、响应码接口及枚举、`BaseException` 和分页查询对象；接口 JSON 成功和失败统一返回数值 `code`、文字 `msg`、`data`，异常在公共入口处理；二进制下载保持文件响应。Controller 接收 HTTP 参数并调用 Service；特殊规则、授权和跨表编排放同业务包的 `manage`，不把 CRUD 查询与保存逻辑堆进 Controller。新代码和模板须有适当的中文业务注释、`@Tag` 和 `@Operation`。
- 所有分页结果统一使用 MyBatis-Plus `Page<T>`，不为每个业务列表另建相同字段的分页类型；常规和高级业务查询继承公共 `SearchBO` 并增加自身筛选字段。JSON Controller 在方法签名中明确返回 `Result<T>`，成功由 `Result.ok` 构造，失败由公共异常入口转换为 `Result.error`，不用响应后置包装掩盖接口声明；下载与明确的 204 响应保留 HTTP 原语义。HTTP 请求和返回模型放在所属业务的 `manage/dto`，Controller 不把 Service 的内部成员类型作为接口契约。系统/租户上下文和权限在业务入口统一解析；全局过滤器、拦截器及时间格式配置只处理确实跨域共用的规则，不复制业务鉴权或增加无用途的层。
- `manage` 中业务 Service 调用本模块 `base` Service，特殊逻辑按职责放在 `manage/controller`、`manage/service`、`manage/enums`、`manage/util` 等实际需要的子包；Controller 只负责接口参数和调用，枚举、工具类不与业务 Service 平铺。不能改用 JdbcTemplate 绕开基础服务。字段配置的业务归属不写进每张表的通用模板。
- 先从表和模板建立可复现的生成链，再开发业务接口；不从旧 Controller 或旧 SQL 复制业务实现。简单 CRUD 不增加多余抽象。任务按不超过 240 分钟的可观察业务结果划分，每批核对结果是否符合原需求；局部测试通过不能证明业务理解正确。

## 工程框架如何服务交付

- 工程框架的目标是提高需求理解、任务拆分、实现及联调的正确性和速度；它是开发工作方式与工具，不是产品运行时新增的一层系统，也不以文档数量、agent 数量或完成标记衡量效果。优先完善当前公共核心和统一业务能力，工程优化随实际交付缺口进行，不把另建框架、任务栏或状态文件作为开发前置条件。
- 先理解整条业务主线及各域关系，再拆任务。先确认配置由谁维护、保存后如何生效、数据如何关联、动作如何执行业务与 Flow，再说明每项任务的业务行为、所属模块、前置依赖、数据和接口，以及成功、无权和失败结果。以用户原始要求及当前明确补充核对具体业务例子，不按代码目录、表名或功能名罗列互不关联的开发阶段，也不把一张张表的 CRUD 当成完整产品功能。
- 单批估算不超过 240 分钟；超过时沿业务依赖继续拆分。任务安排保留在当前工作上下文中，直接更新最终代码，不生成计划、状态、交接、评审、验收历史等中间文件。
- 当前目标持续覆盖整套后端业务与真实验收；每批完成后根据完整主线接续有前置条件的下一批。完成一个接口、CRUD、生成文件或一次编译只说明该批局部结果，不能宣布产品完成，也不把“请用户再说继续”当作推进条件。需要用户验收后才进入前端的边界仍按前述规则执行。
- agent 表示职责承担者，skills 表示按需使用的具体方法或工具。同一 agent 可承担多项职责；有独立工作且适合并行时才分工，共享迁移、接口依赖和联调保持有序，不为使用某种机制另建框架。各执行者读同一份最终需求理解并修改同一套最终实现。
- 已授权的并行任务遇到共享文件或 Service 能力依赖时，采用[共享文件与接口依赖处理方案](../template_base/agents/README.md#并行任务的共享文件与接口依赖处理)：调用方在当前工作上下文提出业务能力需求，由主执行者与负责方评估直接复用、扩展现有方法、新增方法、合并或拒绝需求，负责方统一修改，调用方接入后验证完整调用链。同一文件不同时由多个任务修改，循环依赖由主执行者调整顺序或合并任务；不新增任务栏、调度系统或中间任务文件。
- 修改表结构后，先在目标库执行并核对，再通过统一生成器更新对应模块 base，最后适配 manage 和接口。生成器直接产出正确包结构及基础实现；避免手工修补生成文件造成下次生成退化。
- 验证先执行相关编译和有意义的测试，再用实际接口核对配置保存即生效、查询效果、持久化、授权和失败行为。逐项核对本批预定业务场景及其关联场景，不能只验证其中一个场景或自设算法就认为整批完成。流程修改后分别检查新数据使用新流程、旧数据继续旧流程；逻辑删除后检查关联流程保持原样且业务查询和统计已过滤。相关代码或配置变化时重新检查受影响结果，集成后回到完整业务过程验证。
- 工程工具只从当前最终文件和实际代码读取上下文、运行检查，不保存或回放历史理解。用户补充需求时原位更新本文件对应内容及最终实现，原始需求文件仍由用户维护。
- 已确认源自需求理解错误的实现，直接清除错误的数据模型、字段、接口、调用和规则，按正确需求维护唯一最终实现；不能以兼容旧代码为由保留错误结构、旧协议或平行执行分支。开发库旧数据不需要迁移；较大结构调整时核对范围并清空受影响数据，按最终结构重新建立，不为错误测试模型增加兼容迁移代码。
- 存储和接口设计先区分基础数据、配置及业务数据，明确维护者、引用关系和实际生效位置。用户纠正模型后，把正确关系原位更新到本文件，并检查数据库、生成结果、业务 Service、接口、缓存和用例中的同源假设；以用户给出的具体业务例子验证修正，不能仅改名称或局部补丁。可复用的防错规则维护在工程框架中，不另建学习历史或副本需求。

整体实施顺序是：理解完整产品和表关系 → 按业务依赖建表并生成 base → manage 实现真实业务（含模块主状态与运维）→ 后端接口整体验收 → 前端使用真实接口实现配置态与运行态 → 实际页面与完整业务验收 → 其他主要模块基本完成后再扩展 AI。登录阶段先使用账号密码。分批开发只改变执行顺序，不缩减完整交付目标。
