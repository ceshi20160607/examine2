# 最终用户目标基线

状态：`frozen-pm-alignment`

更新时间：2026-06-12

## 1. PM 必须理解的最终目标

本项目的最终目标不是“接口都能调通”，也不是“页面能点、能构建、能打包”。

最终目标是交付一个普通人可以部署后直接使用的可配置业务系统平台：

- 平台管理员能创建和管理多个业务系统，维护平台账号、平台权限、平台级对外应用、平台审计和运维信息。
- 系统管理员能进入某个业务系统，在系统内完成成员开通、角色授权、业务应用、模块、字段、页面、菜单、发布、系统审计和系统级对外授权。
- 普通业务用户登录后能自然进入自己所属业务系统的业务运行台，只看到被授权模块和数据，在页面里完成新增、查询、编辑、提交和查看业务数据。
- 集成管理员能配置平台级对外应用，把某个业务系统的数据、模块动作、字段范围、数据范围、流程、文件或平台能力安全开放给外部系统，并能追踪调用日志。

PM 的核心职责是让这些用户在真实页面里自然完成任务，而不是让用户理解底层表、接口、权限编码或前端路由。

## 2. 用户不应该理解的底层概念

以下概念可以存在于系统内部，但不能成为普通用户使用系统的前置理解：

- 平台账号和系统成员的底层拆分。
- `systemId`、`tenantId`、`memberId`、`moduleId`、`appId` 等技术 ID。
- API 编号、scope 编码、权限编码、schema 快照、请求头。
- 后端模块名、表名、生成器、base 包、接口路径。
- 前端路由、接口调试地址、nginx 转发细节。

页面必须把这些概念翻译成业务动作，例如“开通成员账号并加入当前系统”“创建车辆档案模块”“发布到业务运行台”“授权外部应用访问车辆档案”。

## 3. 主流系统 UI 的最低标准

PM、UI/UX、frontend、reviewer 必须按以下标准判断页面，而不是只判断功能是否存在。

### 3.1 信息架构

- 平台层和系统层必须清楚分离。
- 平台级对外应用和系统内业务应用必须清楚分离。
- 普通业务用户默认只看到业务运行台、被授权模块、个人相关入口和退出入口。
- 系统管理员默认看到系统首页、成员与权限、建模配置、业务运行、协同与文件、系统审计、系统对外授权。
- 平台管理员默认看到平台首页、我的业务系统、平台账号、平台角色、平台级对外应用、平台审计、运维诊断。

### 3.2 页面布局

- 页面不能是表单、卡片、表格随意堆叠。
- 每个页面必须有明确标题、当前上下文、主要动作、筛选区、列表区、分页区、详情或编辑入口。
- 新建和编辑默认使用主按钮触发抽屉、弹窗、独立页面或分步向导，不得把大块新建表单长期堆在表格上方。
- 列表必须有分页、空态、加载态、错误态、权限禁用态和可恢复提示。
- 详情必须有详情页、详情抽屉或详情分区，不能只靠表格行承载全部信息。
- 危险操作必须有确认和影响说明。

### 3.3 视觉和文案

- 当前默认中文界面，除 OpenAPI、appKey、secret、requestId 等技术专有词外，不得散落英文文案。
- 风格应是现代、克制、清晰的企业级业务系统，不是营销页，也不是接口调试台。
- 页面要减少技术 ID 暴露；必要 ID 放到详情或诊断区，不作为主视觉信息。
- 主按钮、次按钮、危险按钮、状态标签、表格、筛选、表单、抽屉和提示要一致。

## 4. 必须跑通的连续验收剧本

最终完成只能由连续用户剧本证明，不能由多个割裂 smoke 拼起来证明。

### 4.1 平台管理员到普通用户完整剧本

1. 平台管理员登录。
2. 创建一个业务系统，例如“车”。
3. 创建成功后进入该系统首页，页面告诉管理员下一步该做什么。
4. 在系统内直接开通 `che` 成员账号并加入当前系统，不要求用户先绕到平台账号页。
5. 创建业务应用，例如“车辆业务”。
6. 创建业务模块，例如“车辆档案”。
7. 添加字段，例如车牌号、车型、颜色、登记日期、状态。
8. 配置列表页、表单页、详情页和菜单入口。
9. 发布模块到业务运行台。
10. 给 `che` 授权车辆档案的菜单、查看、新增、编辑、提交和必要字段权限。
11. 平台管理员退出。
12. `che` 登录。
13. 如果 `che` 只属于一个系统，直接进入“车 / 业务运行台”；如果属于多个系统，进入业务系统选择页。
14. `che` 只看到车辆档案等被授权模块，看不到平台管理、系统建模、字段设计、页面发布、权限配置。
15. `che` 能新增、查询、编辑、提交车辆档案数据。
16. 列表能分页，详情能查看，错误能恢复，退出入口清晰可见。

### 4.2 对外应用剧本

1. 平台或集成管理员进入平台级“对外应用中心”。
2. 创建外部接入应用，例如“车联网外部接入”。
3. 生成 appKey/secret，secret 只展示一次。
4. 给该对外应用授权访问“车”系统的车辆档案模块。
5. 选择可访问字段、可执行动作、数据范围、IP 白名单、限流和过期策略。
6. 外部系统调用 OpenAPI 成功。
7. 平台日志和系统日志都能按 requestId 追踪调用、授权、限流、签名和结果。

### 4.3 恢复和异常剧本

1. 登录失败时能区分账号不存在、密码错误、账号停用、服务异常。
2. 用户没有系统时，页面说明如何联系管理员或创建系统。
3. 用户没有模块时，页面说明当前系统尚未开放业务模块。
4. 用户没有权限时，入口隐藏或禁用，并给出可理解原因。
5. 发布失败时列出缺字段、缺页面、缺菜单或缺权限。
6. 外部调用失败时能按 requestId 查到原因。

## 5. PM 不得通过的情况

任一情况成立，PM 必须判定未完成：

- 普通用户登录后不知道自己在哪个业务系统、下一步做什么。
- 普通用户看到平台管理、建模配置、字段设计、页面发布或权限配置入口。
- 系统管理员仍需要跨到平台账号页才能完成系统成员开通。
- 新建入口仍主要是表格上方常驻大表单。
- 列表没有分页或分页信息不清楚。
- 页面需要用户理解技术 ID、接口、请求头、权限编码才能操作。
- 当前 UI 只是表单、卡片、表格堆叠，没有主次动作和任务路径。
- 只有构建通过、接口通过、局部 E2E 通过，没有真实浏览器连续剧本证据。
- 没有部署到目标 nginx 后验证静态前端、`/api/` 转发和真实用户流程。
- PM、test、reviewer 任一角色无法用普通用户语言解释“这个系统怎么用”。

## 6. 角色执行规则

- PM：先确认本文件目标，再裁决范围、验收口径和是否能进入实现。
- UI/UX：先输出页面级设计、流程图、主动作、列表/表单/详情/空态/错误态，再允许 frontend 实现。
- Frontend：按页面任务实现，不按 API 模块堆页面；需要拆出可维护组件和页面结构。
- Backend：把底层模型封装成业务动作，避免让前端和用户拼装技术流程。
- Test：用真实浏览器跑连续剧本，必须覆盖平台管理员、系统管理员、普通业务用户和对外应用。
- Validator：只证明构建和包，不替 PM 宣称用户可用。
- Reviewer：主动推翻 PM 结论；只要用户目标、页面证据和状态文件矛盾，就判定 fail。
