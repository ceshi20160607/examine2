# P16 最后一次 UI/UX 与可用性返工章程

状态：`frozen-before-implementation`

更新时间：2026-06-12

## 1. PM 裁决

P16 是一次最终目标对齐后的完整返工，不是继续给 P15 做局部补丁。

PM 必须以 `docs/product/final-user-goal.md` 为最高目标基线。P16 的成功标准不是“页面更好看一点”，而是：

> 一个普通人部署后能自然使用的可配置业务系统平台，平台管理员、系统管理员、普通业务用户、集成管理员和审计/运维人员都能在各自工作空间完成真实任务。

P16 不能再走“发现一个问题修一个问题”的模式。必须一次性完成页面级设计、前端重组、必要后端补齐、完整浏览器验收和部署包闸门。

## 2. 本次返工不再允许的行为

- 不允许直接在现有工程化页面上继续堆表单、卡片和按钮。
- 不允许只因为构建通过、接口通过或局部 E2E 通过就打最终包。
- 不允许把平台层、系统层、业务运行台、对外应用混成一个后台菜单。
- 不允许让普通用户看到平台管理、系统建模、字段设计、发布和权限配置入口。
- 不允许让系统管理员为了开通系统成员先绕到平台账号页。
- 不允许新建入口继续作为表格上方常驻大表单。
- 不允许没有页面级 UI/UX 设计就让 frontend 临场决定页面结构。
- 不允许 reviewer 只看测试通过；必须主动推翻 PM 结论。

## 3. P16 必须重做的页面范围

### 3.1 全局壳层

- 登录页。
- 工作空间选择和落点规则。
- 平台工作空间壳层。
- 系统工作空间壳层。
- 普通业务运行台壳层。
- 全局退出、当前账号、当前系统、当前成员、权限摘要。

### 3.2 平台管理员页面

- 我的业务系统：创建系统、进入系统、最近访问、空态。
- 平台账号：账号列表、创建、编辑、重置密码、停用。
- 平台角色：角色权限分组、授权、影响说明。
- 平台级对外应用中心：创建外部应用、凭证、授权入口、调用日志。
- 平台审计与运维：requestId 追踪、登录日志、平台操作日志、健康状态。

### 3.3 系统管理员页面

- 系统首页：配置进度、下一步、快捷入口。
- 成员与权限：直接开通成员账号并加入当前系统、角色、数据范围、字段权限。
- 建模配置：业务应用、模块、字段、页面、菜单、发布检查和发布。
- 系统对外授权：把当前系统数据和能力授权给平台级对外应用。
- 系统审计：配置日志、数据日志、系统内 OpenAPI 调用日志。

### 3.4 普通业务用户页面

- 业务运行首页：只显示被授权模块、待办、最近数据。
- 模块列表页：筛选、分页、主按钮新建、详情入口。
- 新建/编辑页或抽屉：按字段权限渲染，可写/只读/隐藏清晰。
- 详情页：字段详情、附件、流程、历史、操作日志。
- 提交/审批动作：状态、反馈、错误恢复。

### 3.5 集成管理员页面

- 对外应用创建向导。
- appKey/secret 一次性展示。
- 系统、模块、字段、动作、数据范围授权。
- IP 白名单、限流、过期和签名策略。
- 调用示例与 requestId 日志追踪。

## 4. P16 交付顺序

1. UI/UX 输出页面级设计：信息架构、导航、关键流程、线框、主按钮、列表/表单/详情/空态/错误态、中文文案。
2. PM 对照 `docs/product/final-user-goal.md` 逐条验收 UI/UX；不通过则不得进入前端实现。
3. Frontend 重构页面结构，把超大 `App.ts` 拆为页面、组件和状态模块；保留可复用 API 和动态 schema 能力。
4. Backend 只补必要业务动作接口或聚合接口，不把底层模型暴露给用户流程。
5. Test 用真实浏览器执行连续剧本，至少覆盖平台管理员、系统管理员、普通业务用户、对外应用。
6. Validator 执行前端 build、后端 package、包内清单和启动脚本权限校验。
7. Reviewer 按最终目标基线审查，发现页面像调试台、流程割裂、普通用户不懂怎么用，一律 fail。
8. PM 只有在 UI/UX、frontend、backend、test、validator、reviewer 全部 pass 后，才能允许最终包。

## 5. P16 验收矩阵

| 角色 | 必须交付 | 不通过条件 |
| --- | --- | --- |
| PM | 最终目标对照结论、范围裁决、打包许可 | 不能用普通用户语言说明系统怎么用 |
| UI/UX | 页面级设计和原型流程追踪矩阵 | 只有概念框架，没有具体页面结构 |
| Frontend | 主流可用页面、组件化结构、真实交互 | 继续在单个超大文件里堆页面 |
| Backend | 必要业务聚合接口和权限上下文 | 需要用户或前端拼底层流程 |
| Test | 连续浏览器验收记录和截图/证据 | 只跑接口或局部页面 smoke |
| Validator | clean build、package、包内权限和 nginx 指南 | 只跑类型检查或漏前端产物 |
| Reviewer | 最终目标基线审查 | 没有主动推翻 PM 结论 |

## 6. 最终包闸门

P16 通过前，不再生成“最终部署包”。如必须给用户试用，只能标记为“技术试用包”。

最终包必须同时满足：

- `docs/review.json.status=pass`
- `docs/review.json.frontendUsable=true`
- `docs/review.json.fullProjectDeployable=true`
- `docs/review.json.packageGate=allowed`
- `docs/test_runs/` 中有连续浏览器剧本证据
- `docs/ui/` 中有 P16 页面级 UI/UX 冻结产物
- `frontend/dist/` 和后端 jar 均来自最终 build
- 包内包含前端、后端、start.sh、nginx 说明、测试证据、review 和 progress
- 部署到目标 nginx 后验证 `/api/` 转发、静态资源和真实用户流程

## 7. PM 对用户的承诺边界

PM 可以承诺：P16 开始后不再把半成品包装成最终系统，不再用局部通过替代整体可用，不再跳过 UI/UX 和真实浏览器验收。

PM 不能提前承诺：在未完成 P16 设计、实现、部署验证前，当前系统已经是最终可用系统。

这就是“最后一次”的真实含义：不是说一句保证，而是把后续所有角色都锁到同一个最终目标和同一套验收闸门上。
